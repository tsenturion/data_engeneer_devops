# Практическое задание. Развертывание и настройка рабочей среды PostgreSQL

## Цель

Создать небольшой рабочий контур PostgreSQL для серверного приложения и закрепить навыки работы с базами данных, ролями, пространствами имен, временными таблицами, локальным и удаленным подключением, стандартными административными утилитами PostgreSQL и внешним пулером соединений PgBouncer.

В результате работы должен получиться не набор отдельных команд, а воспроизводимая конфигурация: базу можно создать, подготовить SQL-скриптами, проверить под разными пользователями, подключить локально и удаленно, создать резервную копию и протестировать подключение через PgBouncer.

---

# Задание

Для учебного сервиса технической поддержки необходимо подготовить базу данных `helpdesk_lab`. Сервис будет хранить пользователей и обращения в поддержку. Приложение должно работать под отдельной учетной записью, а сотрудник аналитики должен иметь только доступ на чтение.

Основную часть работы необходимо оформить кодом. SQL-команды сохраните в `.sql`-файлы, административные команды Linux — в `.sh`-файл.

Рекомендуемая структура файлов работы:

```text
postgresql_lab/
    01_database.sql
    02_structure.sql
    03_roles.sql
    04_permissions.sql
    05_temp_tables.sql
    06_checks.sql
    admin.sh
    pgbouncer.ini
    README.md
```

## Шаг 1. Проверить используемый кластер PostgreSQL

Определите, к какому серверу и кластеру выполняется подключение.

Получите текущую базу, текущего пользователя, каталог данных, порт сервера и версию PostgreSQL.

Используйте SQL-команды PostgreSQL, а не значения, записанные вручную.

В файл `06_checks.sql` добавьте запросы, позволяющие проверить эту информацию повторно.

В результате должны определяться как минимум:

```sql
current_database()
current_user
```

Дополнительно получите значения:

```sql
SHOW data_directory;
SHOW port;
```

и версию сервера.

Не изменяйте основной каталог кластера в рамках задания.

## Шаг 2. Создать базу данных

Создайте базу:

```text
helpdesk_lab
```

Владельцем базы должна быть отдельная роль:

```text
helpdesk_owner
```

Не используйте роль `postgres` как владельца объектов приложения.

Создание роли-владельца и базы оформите так, чтобы было понятно, в какой последовательности необходимо выполнять команды.

После создания базы подключитесь именно к:

```text
helpdesk_lab
```

и проверьте:

```sql
SELECT current_database();
```

## Шаг 3. Создать пространства имен

В базе `helpdesk_lab` создайте два пользовательских пространства имен:

```text
app
audit
```

`app` предназначено для основных объектов приложения.

`audit` предназначено для служебных данных приложения.

Владелец обоих пространств имен:

```text
helpdesk_owner
```

После создания получите список пространств имен базы SQL-запросом через системный каталог PostgreSQL.

В результате запроса должны быть видны как пользовательские, так и специальные пространства имен PostgreSQL.

Не ограничивайтесь командой `\dn`: в итоговом SQL-файле должен присутствовать обычный SQL-запрос.

---

## Шаг 4. Создать таблицы приложения

В пространстве имен `app` создайте таблицу пользователей:

```text
app.users
```

Она должна содержать идентификатор, имя пользователя, электронную почту и дату создания записи.

В пространстве имен `app` создайте таблицу обращений:

```text
app.tickets
```

Она должна содержать идентификатор обращения, ссылку на пользователя, тему обращения, текст сообщения, статус и дату создания.

Используйте подходящие типы данных PostgreSQL.

Для идентификаторов используйте автоматически генерируемые значения.

Для связи обращения с пользователем создайте внешний ключ.

Для поля статуса задайте разумное значение по умолчанию.

Пример данных, которые должна поддерживать таблица:

```text
Пользователь: Иван
Email: ivan@example.com

Обращение:
Тема: Не удается войти
Статус: new
```

Вставьте не менее пяти пользователей и не менее десяти обращений.

## Шаг 5. Создать служебную таблицу аудита

В пространстве имен:

```text
audit
```

создайте таблицу:

```text
audit.events
```

Она должна позволять хранить информацию о действиях приложения.

Предусмотрите идентификатор события, текст события и время его возникновения.

Добавьте несколько тестовых записей.

После этого выполните запрос, который показывает отдельно данные:

```text
app.tickets
```

и:

```text
audit.events
```

Так должна быть продемонстрирована работа одинаковой базы с несколькими пространствами имен.

## Шаг 6. Создать пользователей PostgreSQL

Создайте роль приложения:

```text
helpdesk_app
```

Она должна иметь возможность подключаться к PostgreSQL.

Создайте роль:

```text
helpdesk_readonly
```

Она также должна иметь возможность подключения.

Для обеих ролей задайте пароли.

Не выдавайте им:

```text
SUPERUSER
CREATEDB
CREATEROLE
REPLICATION
```

После создания проверьте свойства ролей через:

```sql
pg_roles
```

В итоговом запросе должны отображаться имя роли и наличие возможности `LOGIN`.

## Шаг 7. Настроить права приложения

Роль:

```text
helpdesk_app
```

должна иметь право подключаться к базе `helpdesk_lab`, использовать пространство имен `app`, читать существующие данные, добавлять новые записи и изменять существующие записи приложения.

Роль приложения не должна получать административные полномочия PostgreSQL.

Настройте разрешения SQL-командами `GRANT`.

После этого обязательно подключитесь под `helpdesk_app` и практически проверьте разрешенные операции.

Например, приложение должно суметь выполнить:

```sql
SELECT *
FROM app.tickets;
```

и добавить новое обращение.

## Шаг 8. Настроить пользователя только для чтения

Пользователь:

```text
helpdesk_readonly
```

должен иметь возможность подключаться к `helpdesk_lab` и читать таблицы пространства `app`.

Он не должен иметь возможность выполнять:

```sql
INSERT
UPDATE
DELETE
```

в таблицах приложения.

Проверьте это не только просмотром выданных привилегий, но и реальными запросами.

В файл `06_checks.sql` добавьте успешный запрос чтения.

В отчет добавьте также пример команды изменения данных, которая при подключении под `helpdesk_readonly` должна завершиться ошибкой доступа.

## Шаг 9. Исследовать специальные пространства имен

Получите через SQL сведения о специальных пространствах имен PostgreSQL.

Найдите среди них:

```text

information_schema
```

Если в текущем сеансе существует временное пространство имен, определите также его имя.

Через `information_schema` получите список пользовательских таблиц базы.

Через `pg_catalog` получите информацию об отношениях базы.

Не требуется выводить содержимое всех системных каталогов. Задача состоит в том, чтобы показать умение получить метаданные двумя разными способами.

## Шаг 10. Создать временную таблицу

Подключитесь под:

```text
helpdesk_app
```

и создайте временную таблицу:

```text
ticket_processing
```

В нее необходимо поместить идентификаторы и темы обращений со статусом `new`.

После этого получите содержимое временной таблицы запросом `SELECT`.

Закройте соединение с PostgreSQL, создайте новое соединение и попытайтесь снова обратиться к:

```text
ticket_processing
```

Зафиксируйте результат проверки.

В `05_temp_tables.sql` также подготовьте второй пример с:

```sql

```

Внутри одной транзакции временная таблица должна быть создана, заполнена и прочитана. После завершения транзакции объект больше не должен существовать.

## Шаг 11. Проверить локальное подключение

На Linux-сервере выполните локальное подключение к базе через `psql`.

Сначала выполните подключение обычным способом через локальный механизм PostgreSQL.

Затем отдельно выполните TCP/IP-подключение через:

```text
127.0.0.1
```

Пример общей формы команды:

```bash
psql -h 127.0.0.1 -p 5432 -U helpdesk_app -d helpdesk_lab
```

В обоих случаях выполните:

```sql
SELECT
    current_user,
    current_database();
```

Нужно понимать, что эти два подключения могут вести к одной базе, но использовать разные способы установления соединения.

## Шаг 12. Проверить удаленное подключение

Определите IP-адрес PostgreSQL-сервера командой Linux.

Проверьте, что PostgreSQL слушает TCP-порт:

```text
5432
```

Используйте:

```bash
ss
```

После этого подключитесь к серверу с другого компьютера через `psql` или DBeaver.

При удаленном подключении используйте:

```text
helpdesk_app
```

а не административную роль `postgres`.

После успешного подключения выполните:

```sql
SELECT current_user;
SELECT current_database();
```

а затем:

```sql
SELECT *
FROM app.tickets;
```

## Шаг 13. Проверить правила доступа

Получите путь к используемому файлу:

```text
pg_hba.conf
```

не вручную, а SQL-командой PostgreSQL.

Затем получите разобранные PostgreSQL правила через:

```sql
pg_hba_file_rules
```

Найдите правило, через которое разрешается подключение вашего удаленного клиента.

В рамках задания нельзя использовать небезопасное правило вида:

```conf
host    all    all    0.0.0.0/0    trust
```

Для сетевых подключений должна применяться парольная аутентификация.

После изменения `pg_hba.conf`, если оно потребуется, конфигурацию необходимо перечитать штатным способом.

Дамп нельзя считать готовым только потому, что команда завершилась без видимой ошибки. Необходимо убедиться, что файл действительно существует и имеет ненулевой размер.

## Шаг 18. Настроить PgBouncer

Создайте учебную конфигурацию, позволяющую подключаться к:

```text
helpdesk_lab
```

через PgBouncer.

PostgreSQL продолжает использовать:

```text
5432
```

а PgBouncer должен принимать клиентские соединения на:

```text
6432
```

На первом этапе используйте:

```ini
pool_mode = session
```

В конфигурации должны быть определены подключение к `helpdesk_lab`, адрес прослушивания, порт PgBouncer, тип аутентификации, файл пользователей и основные параметры пула.

Сохраните используемую конфигурацию в файл:

```text
pgbouncer.ini
```

в каталоге сдаваемой работы. Не включайте в работу реальные пароли.

# Подсказки по ключевым частям

Для создания объектов используйте квалифицированные имена. Вместо:

```sql
CREATE TABLE users ...
```

в этой работе лучше явно писать:

```sql
CREATE TABLE app.users ...
```

Это уменьшает зависимость от текущего `search_path`.

Для проверки текущего пользователя используйте:

```sql
SELECT current_user;
```

Для просмотра ролей подойдет:

```sql
SELECT
    rolname,
    rolcanlogin,
    rolsuper,
    rolcreatedb,
    rolcreaterole
FROM pg_roles;
```

Чтобы определить реальные пути текущего кластера, используйте команды `SHOW`, а не значения, скопированные из методички.

Для поиска пространств имен пригодится:

```sql
pg_catalog.pg_namespace
```

Для стандартного просмотра структуры базы пригодятся объекты:

```sql
information_schema.tables
information_schema.columns
```

Для проверки правил аутентификации используйте:

```sql
SHOW hba_file;
```

и:

```sql
SELECT *
FROM pg_hba_file_rules;
```

Для проверки сервера из Linux пригодятся:

```bash
pg_isready
```

и:

```bash
ss -lntp
```

Для резервного копирования custom-формата ориентируйтесь на:

```bash
pg_dump -Fc
```

а для его восстановления — на:

```bash
pg_restore
```

Если PgBouncer не запускается, сначала проверяйте не PostgreSQL, а состояние именно его службы:

```bash
systemctl status pgbouncer --no-pager
```

и журнал:

```bash
journalctl -u pgbouncer -n 50 --no-pager
```

# Советы по улучшению работы

Не выполняйте всю практику под суперпользователем `postgres`. Используйте его только там, где действительно требуются административные полномочия, а работу приложения проверяйте именно под `helpdesk_app`. Иначе невозможно доказать, что система прав настроена правильно.

Старайтесь делать SQL-скрипты воспроизводимыми. Если преподаватель получает только историю команд из терминала, повторить развертывание среды сложно. Значительно лучше, когда создание структуры, ролей, прав и тестовых данных разделено на несколько файлов с понятным порядком выполнения.

При проверке прав обязательно выполняйте отрицательные тесты. Недостаточно показать, что `helpdesk_readonly` способен выполнить `SELECT`. Нужно также доказать, что попытка `INSERT`, `UPDATE` или `DELETE` действительно блокируется PostgreSQL.

Не считайте наличие файла `.dump` подтверждением работоспособности резервной копии. Резервная копия считается проверенной только после успешного восстановления в отдельную базу и проверки данных.

При работе с PgBouncer сначала добейтесь стабильной работы в `pool_mode = session`. Только после этого можно дополнительно протестировать `transaction`, особенно если в приложении используются временные таблицы или другое состояние серверного сеанса.

В итоговом `README.md` кратко укажите порядок запуска файлов, используемые имена базы и ролей, порты `5432` и `6432`, команды проверки подключения и результат восстановления резервной копии. Пароли в `README.md`, SQL-файлах и скриншотах публиковать не нужно.
