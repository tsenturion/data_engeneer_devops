# Практическое задание: разработка и оптимизация базы PostgreSQL с интеграционными механизмами

## Цель

Создать учебную базу данных интернет-магазина и последовательно реализовать в ней возможности PostgreSQL, изученные в модулях 7–13: пользовательские типы данных, JSON и XML, ограничения целостности, схемы, представления, PL/pgSQL, индексы, секционирование, анализ планов выполнения, статистику, `dblink`, PL/Python, асинхронный обмен через Kafka, подключение через Spring/Hibernate и двухфазную фиксацию транзакций.

Работа должна представлять собой связанный проект, а не набор несвязанных SQL-команд.

Итоговые файлы рекомендуется разделить по этапам:

```text
01_types_and_tables.sql
02_views_and_queries.sql
03_plpgsql.sql
04_indexes.sql
05_partitioning.sql
06_performance.sql
07_dblink.sql
08_replication.sql
09_plpython.sql
10_kafka_producer.py
11_kafka_consumer.py
12_spring/
13_two_phase_commit.sql
```

## Шаг 3. Создайте основные таблицы

Создайте таблицы:

```text
app.customers
app.products
app.orders
app.order_items
```

В `customers` должны присутствовать идентификатор, ФИО, электронная почта, массив телефонных номеров, адрес составного типа, JSONB-профиль и дата регистрации.

В `products` должны находиться идентификатор, название, стоимость с использованием созданного домена, массив тегов, характеристики в `jsonb`, XML-документ, признак активности и дата создания.

В `orders` должны находиться идентификатор заказа, внешний ключ клиента, статус типа `order_status`, итоговая стоимость, диапазон времени доставки и дата создания.

В `order_items` должны находиться заказ, товар, количество и стоимость товара на момент заказа.

Используйте `IDENTITY` для автоматического формирования идентификаторов.

## Шаг 4. Добавьте ограничения целостности

Для таблиц настройте:


# Советы по улучшению работы

Не пытайтесь поместить весь проект в один SQL-файл. Разделение по модулям упрощает проверку и позволяет повторно выполнять отдельные этапы.

Добавляйте перед крупными блоками SQL комментарии:

```sql
-- Создание пользовательских типов

-- Создание индексов

-- Проверка плана выполнения

-- Демонстрация двухфазной транзакции
```

При анализе производительности не ограничивайтесь фразой «индекс ускорил запрос». Сохраняйте фактический результат `EXPLAIN (ANALYZE, BUFFERS)` и сравнивайте выбранные узлы плана.

Не создавайте индексы только ради количества. Каждый индекс должен соответствовать хотя бы одному запросу из проекта.

При работе с партициями сначала проверяйте, куда действительно попала строка. Для этого можно использовать системный столбец:

```sql
tableoid::regclass
```

При использовании `dblink`, Spring, Python и Kafka не помещайте реальные пароли в исходные файлы. Для Python и Java используйте переменные окружения или конфигурацию, которая не передается вместе с работой.

При экспериментах с `SET enable_*` изменяйте параметры только для текущего сеанса и возвращайте их исходное состояние.

`PREPARE TRANSACTION` используйте только на учебном сервере. После работы обязательно завершайте каждую подготовленную транзакцию через `COMMIT PREPARED` или `ROLLBACK PREPARED`.

Итоговая работа должна демонстрировать не только наличие SQL-кода, но и проверку результата: после создания объекта должен быть запрос, подтверждающий его работу; после создания индекса — план выполнения; после отправки сообщения — результат consumer; после транзакции — проверка итогового состояния базы.
