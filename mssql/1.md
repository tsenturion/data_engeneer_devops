# Модуль 1. Введение в разработку баз данных

## Введение в платформу SQL Server

Microsoft SQL Server — реляционная СУБД и полноценная платформа для хранения, обработки, защиты и эксплуатации данных. Работа с SQL Server не ограничивается командами `SELECT`, `INSERT`, `UPDATE` и `DELETE`: сервер управляет памятью, выполнением запросов, конкурентным доступом, журналированием, оптимизацией и надежностью данных.

В экземпляре SQL Server может находиться несколько баз данных. Каждая база имеет собственные объекты, файлы и настройки. Системная база `master` хранит сведения об экземпляре сервера, базах данных, учетных записях и части серверной конфигурации. Бизнес-данные приложения в `master` размещать не следует.

Список баз данных экземпляра:

```sql
SELECT
    name,
    database_id,
    state_desc
FROM sys.databases;
```

`sys.databases` — системное представление с информацией о базах данных экземпляра. Для учебной работы создается отдельная пользовательская база:

```sql
CREATE DATABASE TRAININGDB;
```

Переключение контекста на созданную базу:

```sql
USE TRAININGDB;
```

Проверка текущей базы:

```sql
SELECT DB_NAME() AS CURRENTDATABASE;
```

Ожидаемое имя текущей базы:

```
TrainingDB
```

Экземпляр SQL Server управляет серверными ресурсами, а база данных содержит конкретный набор объектов и данных. В одном экземпляре могут находиться, например, отдельные базы для CRM, бухгалтерии, склада и аналитики. Решение о разделении систем по базам зависит от требований к безопасности, нагрузке, обслуживанию и масштабированию.

Основные свойства учебной базы можно получить через `sys.databases`:

```sql
SELECT
    name,
    create_date,
    compatibility_level,
    recovery_model_desc
FROM sys.databases
WHERE name = 'TrainingDB';
```

`compatibility_level` задает уровень совместимости базы с возможностями конкретных версий SQL Server. `recovery_model_desc` показывает модель восстановления и связан с поведением журнала транзакций и возможностями восстановления после сбоев.

Разработчик базы данных проектирует структуру хранения, определяет способы обработки данных и учитывает будущую нагрузку. Корректный SQL-запрос сам по себе не гарантирует хорошую производительность: необходимо учитывать объем данных, частоту чтения и изменений, количество одновременных пользователей, дисковые операции и работу оптимизатора.

## Инструменты и задачи разработчика

DBeaver — клиентское приложение для подключения к SQL Server. Оно отправляет SQL-команды серверу и отображает возвращенный результат. Выполнение запроса происходит на стороне SQL Server, а не внутри DBeaver.

Проверка текущей базы через сервер:

```sql
SELECT DB_NAME();
```

Версия установленного SQL Server:

```sql
SELECT
    @@VERSION;
```

Имя экземпляра:

```sql
SELECT
    @@SERVERNAME AS ServerName;
```

Системные каталоги позволяют анализировать структуру базы средствами SQL. Список объектов текущей базы:

```sql
SELECT
    name,
    type_desc
FROM sys.objects;
```

В пустой пользовательской базе в основном отображаются системные объекты. После создания таблиц, представлений, процедур и других объектов они также будут доступны через системные представления.

При сопровождении базы важно уметь получать метаданные запросами, а не только через графический интерфейс. Это необходимо для диагностики, аудита структуры, автоматизации и анализа чужих баз данных.

Проверка текущего контекста базы и серверного времени:

```sql
SELECT
    DB_NAME() AS DATABASENAME,
    GETDATE() AS CURRENTTIME;
```

`DB_NAME()` возвращает имя текущей базы, а `GETDATE()` — текущее время SQL Server. Эти функции полезны для проверки контекста выполнения команд и диагностики подключения.

# Модуль 2. Проектирование и реализация таблиц

## Разработка таблиц

Таблица — основной объект реляционной базы данных для хранения строк и столбцов. Ее структура должна соответствовать предметной области, объему данных и предполагаемой нагрузке. Каждый столбец должен иметь понятное назначение, подходящий тип данных и хранить один логически однородный вид информации.

Пример таблицы клиентов:

```sql
CREATE TABLE Customers
(
    Customerid INT,
    Firstname NVARCHAR(50),
    Lastname NVARCHAR(50),
    Email NVARCHAR(100),
    Createddate DATETIME
);
```

Команда `CREATE TABLE` создает таблицу. Определение столбца состоит из имени и типа данных:

```
CustomerID INT
```

`CustomerID` хранит целые числа. Текстовый столбец переменной длины задается так:

```
FirstName NVARCHAR(50)
```

`NVARCHAR(50)` хранит Unicode-текст длиной до 50 символов.

Проверка созданных таблиц:

```sql
SELECT
    name,
    create_date
FROM sys.tables;
```

Подробная информация о структуре таблицы:

```sql
sp_help 'Customers';
```

`sp_help` показывает столбцы, типы данных и другие свойства объекта.

Не следует объединять несколько независимых значений в одно текстовое поле, например:

```
FullInformation NVARCHAR(500)
```

Если имя, телефон и адрес записаны в один столбец, поиск, фильтрация и изменение отдельных частей данных усложняются. Для каждого самостоятельного атрибута обычно используется отдельный столбец.

Пример таблицы товаров:

```sql
CREATE TABLE Products
(
    Productid INT,
    Productname NVARCHAR(100),
    Price DECIMAL(10, 2),
    Createddate DATETIME
);
```

Для цены используется точный числовой тип:

```
DECIMAL(10,2)
```

`DECIMAL(10,2)` допускает до 10 цифр всего, из них 2 — после десятичного разделителя. Пример корректного значения:

```
1250.50
```

Структуру таблиц и их столбцов можно получать через системные представления:

```sql
SELECT
    t.name AS tablename,
    c.name AS columnname
FROM sys.tables t
JOIN sys.columns c
    ON t.object_id = c.object_id;
```

Такой запрос полезен при аудите существующей базы и изучении чужого проекта.

## Типы данных

Тип данных определяет допустимые значения, формат хранения и объем используемой памяти. Неподходящий тип увеличивает размер базы, может снижать производительность и создавать ошибки обработки.

Основные целочисленные типы:

```
INT
BIGINT
SMALLINT
TINYINT
```

Они отличаются диапазоном значений и занимаемым объемом. Для очень больших счетчиков может понадобиться `BIGINT`, а для небольших диапазонов — `SMALLINT` или `TINYINT`.

Пример:

```sql
CREATE TABLE Statistics
(
    Viewcount BIGINT,
    Rating SMALLINT
);
```

Основные строковые типы:

```
CHAR
VARCHAR
NCHAR
NVARCHAR
```

`VARCHAR` хранит строки переменной длины без Unicode, `NVARCHAR` — Unicode-строки. `CHAR` и `NCHAR` используются для строк фиксированной длины.

Пример Unicode-строки:

```sql
CREATE TABLE Users
(
    Username NVARCHAR(100)
);
```

Она может содержать значения на разных языках:

```
Иван
John
Мария
```

Для фиксированного двухсимвольного кода подходит:

```
CountryCode CHAR(2)
```

Примеры значений:

```
RU
US
```

Типы даты и времени:

```
DATE
TIME
DATETIME
DATETIME2
```

Для новых решений часто используется `DATETIME2`, поскольку он поддерживает более широкий диапазон и большую точность по сравнению с `DATETIME`.

Пример:

```sql
CREATE TABLE Events
(
    Eventdate DATETIME2
);
```

Точные числовые типы для денежных и расчетных значений:

```
DECIMAL
NUMERIC
MONEY
```

В финансовых расчетах предпочтительны точные типы, например `DECIMAL`, а не типы с приблизительным представлением числа.

Логический тип SQL Server:

```
BIT
```

Пример:

```sql
CREATE TABLE Employees
(
    Isactive BIT
);
```

Обычно используются значения:

```
1
0
```

Для глобально уникальных идентификаторов применяется:

```
UNIQUEIDENTIFIER
```

Пример:

```sql
CREATE TABLE Sessions
(
    Sessionid UNIQUEIDENTIFIER
);
```

`UNIQUEIDENTIFIER` особенно полезен в распределенных системах, где идентификаторы создаются в разных узлах независимо друг от друга.

Выбор типа данных должен соответствовать реальному диапазону и назначению столбца. Использование `NVARCHAR(MAX)` или `BIGINT` без необходимости увеличивает потенциальный объем хранения и скрывает реальные ограничения данных.

## Использование схем

Схема — логический контейнер для объектов базы данных. По умолчанию многие объекты создаются в схеме `dbo`. Полное имя таблицы включает имя схемы:

```
dbo.Customers
```

Схемы помогают группировать объекты по функциональным областям и управлять доступом к ним.

Создание схемы `Sales`:

```sql
CREATE SCHEMA Sales;
```

Таблица внутри схемы:

```sql
CREATE TABLE Sales.Orders
(
    Orderid INT,
    Orderdate DATETIME2
);
```

Полное имя объекта:

```
Sales.Orders
```

Обращение к таблице:

```sql
SELECT *
FROM Sales.Orders;
```

Для другой предметной области можно создать отдельную схему:

```sql
CREATE SCHEMA Warehouse;
```

Пример объекта складской системы:

```sql
CREATE TABLE Warehouse.Products
(
    Productid INT,
    Productname NVARCHAR(100)
);
```

Использование схем делает структуру базы понятнее и позволяет выдавать права не на каждый объект отдельно, а на логические группы объектов.

## Операции над таблицами

Структура таблицы может изменяться после создания. Для этого используется команда:

```
ALTER TABLE
```

Добавление нового столбца:

```sql
ALTER TABLE Customers
ADD Phone NVARCHAR(20);
```

Проверка структуры:

```sql
sp_help 'Customers';
```

Изменение типа или размера существующего столбца:

```sql
ALTER TABLE Customers
ALTER COLUMN Email NVARCHAR(200);
```

Удаление столбца:

```sql
ALTER TABLE Customers
DROP COLUMN Phone;
```

Перед удалением необходимо убедиться, что столбец не используется приложением, запросами, индексами, ограничениями или другой логикой.

Полное удаление таблицы:

```sql
DROP TABLE Customers;
```

`DROP TABLE` удаляет объект вместе с данными, поэтому в рабочей среде такая операция должна выполняться контролируемо.

Изменения структуры базы в проектах обычно оформляются отдельными SQL-миграциями. Пример:

```sql
ALTER TABLE Customers
ADD Registrationdate DATETIME2;
```

Скрипты миграций хранятся вместе с кодом проекта и применяются последовательно на тестовых и рабочих средах. Это позволяет контролировать версии структуры базы и избегать расхождений между серверами.

# Модуль 3. Расширенное проектирование таблиц

## Секционирование данных

Секционирование применяется для крупных таблиц и индексов, когда данные удобно разделить на диапазоны. Для приложения таблица остается единым объектом, но SQL Server может работать только с нужными секциями. Это особенно полезно для временных данных: заказов, логов, операций и телеметрии.

Если таблица разделена по дате, запрос к одному временному диапазону может обращаться только к соответствующим секциям:

```sql
SELECT *
FROM ORDERSHISTORY
WHERE ORDERDATE >= '2026-01-01';
```

Исключение ненужных секций называется `partition elimination`. Секционирование не ускоряет любой запрос автоматически: оно эффективно, когда ключ секционирования совпадает с реальными условиями фильтрации и объем таблицы достаточно велик.

В SQL Server используются функция секционирования, схема секционирования и таблица или индекс, размещенные на этой схеме.

Функция секционирования задает границы диапазонов:

```sql
CREATE PARTITION FUNCTION SalesDatePartitionFunction (DATE)
AS RANGE RIGHT FOR VALUES
(
    '2024-01-01',
    '2025-01-01',
    '2026-01-01'
);
```

`RANGE RIGHT` означает, что граничное значение относится к правой секции. Например:

```
2025-01-01
```

дата `2025-01-01` попадет в секцию, начинающуюся с этой границы.

Схема секционирования определяет размещение секций:

```sql
CREATE PARTITION SCHEME SalesDatePartitionScheme
AS PARTITION SalesDatePartitionFunction
ALL TO ([PRIMARY]);
```

В примере все секции находятся в файловой группе `PRIMARY`. В производственных системах секции могут размещаться в разных файловых группах для раздельного хранения активных и архивных данных.

Таблица на схеме секционирования:

```sql
CREATE TABLE SalesHistory
(
    SaleID INT,
    SaleDate DATE,
    Amount DECIMAL(10,2)
)
ON SalesDatePartitionScheme(SaleDate);
```

Ключ секционирования:

```
SaleDate
```

По значению `SaleDate` SQL Server определяет секцию для каждой строки.

Добавление тестовых данных:

```sql
INSERT INTO SALESHISTORY
VALUES
(1, '2023-05-10', 1500.00),
(2, '2024-03-15', 2500.00),
(3, '2025-06-20', 3500.00),
(4, '2026-02-01', 4500.00);
```

Проверка номера секции:

```sql
SELECT
    $PARTITION.SalesDatePartitionFunction(SaleDate) AS PartitionNumber,
    *
FROM SalesHistory;
```

Для определения номера секции используется специальная функция:

```
$PARTITION
```

Ключ секционирования должен соответствовать характеру данных и запросов. Если большинство запросов фильтруют данные по дате, дата часто является хорошим кандидатом. Неудачный ключ приводит к неравномерному распределению или отсутствию выигрыша.

Типичный объект с постоянно растущими временными данными:

```sql
CREATE TABLE SERVERLOGS
(
    LOGID BIGINT,
    CREATEDDATE DATETIME2,
    MESSAGE NVARCHAR(500)
);
```

Удаление большого количества старых строк обычным `DELETE` может быть дорогостоящим:

```sql
DELETE FROM SERVERLOGS
WHERE CREATEDDATE < '2024-01-01';
```

SQL Server должен найти строки, изменить страницы и зафиксировать операции в журнале транзакций. Для секционированных таблиц большие диапазоны можно перемещать между совместимыми таблицами с помощью механизма `SWITCH`, использующего команду:

```
ALTER TABLE
```

Это позволяет организовывать архивирование без построчной обработки огромного массива данных.

Индексы также могут быть выровнены по той же схеме секционирования:

```sql
CREATE INDEX IX_SalesHistory_Date
ON SalesHistory(SaleDate)
ON SalesDatePartitionScheme(SaleDate);
```

Такой индекс разделяется по тому же ключу, что упрощает обслуживание отдельных секций.

Пример плохого кандидата на ключ секционирования:

```
CustomerName
```

Имя клиента редко подходит для диапазонного секционирования: распределение может быть неравномерным, а запросы обычно не строятся по нужным диапазонам.

Секционирование не создает несколько независимых таблиц. Для приложения объект остается одной таблицей:

```sql
SELECT *
FROM SALESHISTORY;
```

Информацию об индексах таблицы можно получить так:

```sql
SELECT
    OBJECT_NAME(object_id) AS tablename,
    name AS indexname,
    data_space_id
FROM sys.indexes
WHERE object_id = OBJECT_ID('SalesHistory');
```

Созданные функции секционирования:

```sql
SELECT *
FROM sys.partition_functions;
```

Созданные схемы секционирования:

```sql
SELECT *
FROM sys.partition_schemes;
```

Секционирование полезно прежде всего для управления большими объемами данных, архивирования и обслуживания диапазонов. Для небольших таблиц оно может быть избыточным.

## Сжатие данных

SQL Server хранит данные страницами по 8 КБ. Сжатие уменьшает физический объем хранения, не меняя логические значения, которые получает приложение. Выигрыш зависит от структуры данных и повторяемости значений.

Пример повторяющихся строковых значений:

```
Москва
Москва
Москва
Москва
```

Обычный запрос к таблице не меняется:

```sql
SELECT *
FROM Customers;
```

Для обычных таблиц и индексов основными режимами являются `ROW` и `PAGE`.

## ROW-сжатие

`ROW`-сжатие уменьшает физический размер отдельных значений внутри строки. Например, тип:

```
INT
```

имеет фиксированный логический тип, но небольшие фактические значения:

```
1
2
3
```

могут храниться компактнее после применения `ROW`-сжатия.

Тестовая таблица:

```sql
CREATE TABLE SALESDATA
(
    SALEID INT,
    QUANTITY INT,
    AMOUNT DECIMAL(10, 2),
    DESCRIPTION NVARCHAR(200)
);
```

Данные:

```sql
INSERT INTO SALESDATA
VALUES
(1, 5, 100.50, N 'Продажа товара'),
(2, 3, 250.00, N 'Продажа товара'),
(3, 8, 500.00, N 'Продажа товара');
```

Включение `ROW`-сжатия:

```sql
ALTER TABLE SalesData
REBUILD
WITH
(
    DATA_COMPRESSION = ROW
);
```

`REBUILD` перестраивает физическое представление объекта с выбранным режимом хранения.

Проверка уровня сжатия:

```sql
SELECT
    OBJECT_NAME(object_id) AS tablename,
    data_compression_desc
FROM sys.partitions
WHERE object_id = OBJECT_ID('SalesData');
```

Ожидаемое значение:

```
ROW
```

Тип столбца при этом не меняется:

```
Quantity INT
```

Меняется только физический формат хранения.

## PAGE-сжатие

`PAGE`-сжатие включает возможности `ROW`-сжатия и дополнительно использует повторяющиеся значения и словарь внутри страницы. Оно особенно полезно для данных с большим количеством повторов.

Пример таблицы логов:

```sql
CREATE TABLE APPLICATIONLOGS
(
    LOGID BIGINT,
    LEVEL NVARCHAR(20),
    MESSAGE NVARCHAR(500),
    CREATEDDATE DATETIME2
);
```

Повторяющиеся уровни сообщений:

```
INFO
INFO
INFO
ERROR
INFO
```

Повторяющийся текст:

```
Пользователь успешно вошел в систему
Пользователь успешно вошел в систему
Пользователь успешно вошел в систему
```

Включение `PAGE`-сжатия:

```sql
ALTER TABLE ApplicationLogs
REBUILD
WITH
(
    DATA_COMPRESSION = PAGE
);
```

`PAGE`-сжатие часто эффективно для архивных, исторических и аналитических данных, которые читаются значительно чаще, чем изменяются.

Сжатие уменьшает объем чтения с диска, но требует дополнительных ресурсов процессора на упаковку и распаковку данных. Поэтому решение принимается по результатам измерений, а не автоматически.

## Анализ эффективности сжатия

До перестроения крупного объекта можно оценить потенциальную экономию:

```sql
EXEC sp_estimate_data_compression_savings
    @schema_name = 'dbo',
    @object_name = 'SalesData',
    @index_id = NULL,
    @partition_number = NULL,
    @data_compression = 'PAGE';
```

`sp_estimate_data_compression_savings` оценивает текущий и предполагаемый размер объекта для выбранного режима сжатия. Если экономия мала, перестроение может не оправдывать дополнительную нагрузку.

## Сжатие индексов

Индексы также занимают значительный объем и могут сжиматься отдельно:

```sql
ALTER INDEX IX_IndexName
ON TableName
REBUILD
WITH
(
    DATA_COMPRESSION = PAGE
);
```

Для больших таблиц имеет смысл оценивать размер и полезность каждого крупного индекса отдельно.

## Сжатие и производительность запросов

Сжатие может ускорять чтение, если уменьшение числа страниц снижает нагрузку на дисковую подсистему. Например, объект может занимать:

```
100 ГБ
```

а после сжатия:

```
40 ГБ
```

В таком случае сервер читает меньше страниц, хотя тратит больше CPU на обработку сжатого формата.

## Сжатие и операционные данные

Для активно изменяемых таблиц агрессивное `PAGE`-сжатие может быть невыгодным из-за дополнительной процессорной нагрузки. Для исторических таблиц, архивов и отчетных данных оно часто эффективнее. Стратегия должна учитывать соотношение операций чтения и изменения.

## Проверка использования пространства

Размер объекта можно проверить стандартной процедурой:

```sql
EXEC sp_spaceused 'SalesData';
```

Количество зарезервированных и используемых страниц:

```sql
SELECT
    OBJECT_NAME(object_id) AS tablename,
    reserved_page_count,
    used_page_count
FROM sys.dm_db_partition_stats;
```

Эти данные позволяют сравнивать состояние объекта до и после применения сжатия.

## Практический подход при проектировании

Сжатие не исправляет ошибочную модель данных. Сначала выбираются корректные типы и структура таблиц. Например, без необходимости не следует заменять:

```
INT
```

на:

```
BIGINT
```

А даты не следует хранить как:

```
NVARCHAR(50)
```

если по смыслу требуется:

```
DATETIME2
```

Сжатие применяется после корректного проектирования и оценки фактической нагрузки.

## Хронологические таблицы

Хронологические таблицы, или system-versioned temporal tables, используются, когда необходимо хранить не только текущее состояние строки, но и историю ее изменений. Это позволяет определять, какое значение было актуально раньше, получать состояние данных на конкретную дату и анализировать изменения за заданный период.

SQL Server хранит текущую версию строки в основной таблице, а предыдущие версии — в связанной исторической таблице. Для приложения основная таблица остается обычной таблицей.

Например, существует таблица сотрудников:

```
Employees
```

Если должность сотрудника меняется, в обычной таблице останется только новое значение:

```
Руководитель группы
```

При использовании системного версионирования предыдущая версия также сохраняется:

```
Разработчик
```

Для определения периода действия версии SQL Server использует две временные колонки типа `DATETIME2`: начало и окончание действия строки.

Создание таблицы с системным версионированием:

```sql
CREATE TABLE EmployeesHistory
(
    EmployeeID INT PRIMARY KEY,
    FullName NVARCHAR(100),
    Position NVARCHAR(100),
    Salary DECIMAL(10,2),

    ValidFrom DATETIME2 GENERATED ALWAYS AS ROW START,
    ValidTo DATETIME2 GENERATED ALWAYS AS ROW END,

    PERIOD FOR SYSTEM_TIME (ValidFrom, ValidTo)
)
WITH
(
    SYSTEM_VERSIONING = ON
);
```

Специальные системные поля периода задаются так:

```sql
ValidFrom DATETIME2 GENERATED ALWAYS AS ROW START
```

```sql
ValidTo DATETIME2 GENERATED ALWAYS AS ROW END
```

SQL Server самостоятельно устанавливает значения этих колонок. Конструкция периода:

```sql
PERIOD FOR SYSTEM_TIME
```

указывает поля начала и окончания действия версии. Включение автоматического хранения истории задается параметром:

```sql
SYSTEM_VERSIONING = ON
```

После создания таблицы SQL Server автоматически связывает ее с исторической таблицей. Проверить тип таблиц можно через `sys.tables`:

```sql
SELECT
    name,
    temporal_type_desc
FROM sys.tables;
```

Добавление текущих данных выполняется обычным `INSERT`:

```sql
INSERT INTO EMPLOYEESHISTORY
(
    EMPLOYEEID,
    FULLNAME,
    POSITION,
    SALARY
)
VALUES
(
    1,
    N 'Иван Петров',
    N 'Разработчик',
    120000
);
```

Текущая версия строки читается обычным запросом:

```sql
SELECT *
FROM EMPLOYEESHISTORY;
```

SQL Server автоматически заполняет системные поля периода:

```
ValidFrom
ValidTo
```

Изменение текущей версии также выполняется обычным `UPDATE`:

```sql
UPDATE EMPLOYEESHISTORY
SET
    POSITION = N 'Руководитель группы',
    SALARY = 180000
WHERE EMPLOYEEID = 1;
```

При обновлении старая версия строки сохраняется в исторической таблице, а измененная версия становится текущей.

Все версии строк можно получить так:

```sql
SELECT *
FROM EmployeesHistory
FOR SYSTEM_TIME ALL;
```

Ключевая конструкция:

```sql
FOR SYSTEM_TIME ALL
```

возвращает текущие и исторические версии данных.

Состояние таблицы на определенный момент времени запрашивается через `AS OF`:

```sql
SELECT *
FROM EmployeesHistory
FOR SYSTEM_TIME AS OF '2026-01-01';
```

SQL Server выбирает версию строки, которая была действующей на указанную дату.

Для работы с временным диапазоном применяется:

```sql
FOR SYSTEM_TIME BETWEEN
```

Пример:

```sql
SELECT *
FROM EmployeesHistory
FOR SYSTEM_TIME BETWEEN
'2025-01-01'
AND
'2026-01-01';
```

Также поддерживаются конструкции:

```sql
FOR SYSTEM_TIME FROM
```

и:

```sql
FOR SYSTEM_TIME CONTAINED IN
```

Они используют разные правила включения версий в заданный временной диапазон.

Каждое изменение строки создает историческую запись, поэтому объем истории необходимо учитывать при проектировании. Для часто изменяемых таблиц заранее определяются срок хранения истории, правила очистки старых версий и стратегия архивирования.

Хронологические таблицы могут использоваться совместно с секционированием. Если история хранится несколько лет, данные можно разделять по времени и отдельно обслуживать старые диапазоны. Такой подход полезен для систем с большим объемом аудита, истории операций, кадровых изменений, цен или других данных, состояние которых важно восстанавливать на определенный момент.

До появления temporal tables историю часто реализовывали отдельными таблицами и DML-триггерами. Такой подход требует самостоятельно поддерживать логику сохранения предыдущих значений при изменении и удалении данных. Системное версионирование переносит сохранение исторических версий на SQL Server.

Параметры хронологических таблиц можно проверить системным запросом:

```sql
SELECT
    name,
    temporal_type_desc,
    history_table_id
FROM sys.tables
WHERE temporal_type <> 0;
```

В некоторых сценариях системное версионирование временно отключается:

```sql
ALTER TABLE EmployeesHistory
SET
(
    SYSTEM_VERSIONING = OFF
);
```

Повторное включение выполняется так:

```sql
ALTER TABLE EmployeesHistory
SET
(
    SYSTEM_VERSIONING = ON
);
```

Отключение требует осторожности: изменения, выполненные в этот период, могут не попасть в историю.

Хронологические таблицы применяются для аудита, анализа изменений и восстановления состояния данных в прошлом. Они не заменяют правильное проектирование таблиц, индексов и запросов. При больших объемах истории их следует сочетать с продуманной стратегией хранения, секционированием и сжатием.
