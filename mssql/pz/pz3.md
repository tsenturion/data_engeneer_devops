# Практическое задание

# Использование расширенного проектирования таблиц в MS SQL Server

## Цель

Разработать структуру хранения данных с учетом особенностей больших информационных систем, где объем данных постоянно увеличивается и требуется эффективная организация хранения.

В рамках работы необходимо создать таблицу, которая имитирует работу системы с большим количеством записей, выполнить настройку секционирования данных, изучить применение сжатия таблиц и реализовать механизм хранения истории изменений данных с использованием хронологических таблиц.

Задача работы — подготовить структуру базы данных, которая сможет сохранять производительность при росте объема информации и обеспечивать возможность анализа изменений данных за определенный период времени.

---

# Задание

Необходимо разработать базу данных для системы, где происходит постоянное накопление информации.

В качестве предметной области использовать один из вариантов:

- система учета заказов интернет-магазина;
- система банковских операций;
- система логирования действий пользователей;
- система управления датчиками и измерениями;
- система хранения документов;
- система учета обращений клиентов.

# 2. Создание таблицы с большим объемом данных

Создать основную таблицу, которая будет содержать информацию с историческим накоплением данных.

Например, таблица операций:

```sql
CREATE TABLE Storage.Transactions
(
    TransactionId BIGINT IDENTITY(1,1),
    UserId INT NOT NULL,
    Amount DECIMAL(12,2),
    TransactionDate DATE NOT NULL,
    Description NVARCHAR(500)
);
```

Таблица должна содержать поле даты, по которому будет выполняться разделение данных.

Например:

```sql
TransactionDate
```

Это поле будет использоваться для секционирования.

# 3. Реализация секционирования данных

Создать секционирование таблицы по временному признаку.

В качестве разделения использовать годы.

Например:

- данные за 2024 год;
- данные за 2025 год;
- данные за 2026 год;
- будущие данные.

Необходимо создать:

- функцию секционирования;
- схему секционирования;
- таблицу, использующую секционирование.

Пример создания функции:

```sql
CREATE PARTITION FUNCTION TransactionDateFunction (DATE)
AS RANGE RIGHT FOR VALUES
(
    '2025-01-01',
    '2026-01-01',
    '2027-01-01'
);
```

Создать схему:

```sql
CREATE PARTITION SCHEME TransactionDateScheme
AS PARTITION TransactionDateFunction
TO
(
    PRIMARY,
    PRIMARY,
    PRIMARY,
    PRIMARY
);
```

После этого создать таблицу с использованием созданной схемы.

Проверить распределение данных между секциями.

- ROW compression;
- PAGE compression.

Применить сжатие к таблице.

Пример:

```sql

```

После применения выполнить проверку размера таблицы.

Сравнить объем занимаемого пространства до и после сжатия.

# 7. Создание хронологической таблицы

Создать таблицу, где необходимо хранить историю изменения данных.

Например, таблица пользователей:

```sql
CREATE TABLE Storage.Customers
(
    CustomerId INT PRIMARY KEY,
    FullName NVARCHAR(200),
    Email NVARCHAR(200),
    Status NVARCHAR(50),

    ValidFrom DATETIME2 GENERATED ALWAYS AS ROW START,
    ValidTo DATETIME2 GENERATED ALWAYS AS ROW END,

    PERIOD FOR SYSTEM_TIME
(
    ValidFrom,
    ValidTo
)
)
WITH
(
    SYSTEM_VERSIONING = ON
);
```

SQL Server должен автоматически сохранять предыдущие версии строк.

---

# 8. Проверка истории изменений

Добавить запись:

```sql
INSERT INTO Storage.Customers
(
    Customerid,
    Fullname,
    Email,
    Status
)
VALUES
(
    1,
    'Иван Петров',
    'ivan@mail.ru',
    'Активен'
);
```

Изменить данные:

```sql
UPDATE Storage.Customers
SET Status = 'Заблокирован'
WHERE Customerid = 1;
```

Получить историю изменений:

```sql
SELECT *
FROM Storage.Customers
FOR SYSTEM_TIME ALL;
```

Проверить:

- текущую версию данных;
- предыдущие значения;
- время действия каждой версии.

# Подсказки по ключевым частям

При выборе данных для секционирования необходимо ориентироваться на реальные сценарии работы.

Чаще всего секционирование применяется для больших таблиц, где данные имеют естественное разделение по времени.

Например:

- логи системы;
- операции пользователей;
- платежи;
- события устройств;
- документы.

Для небольших таблиц секционирование обычно не дает преимуществ, так как усложняет структуру без заметного выигрыша.

При выборе поля секционирования важно использовать столбец, по которому часто выполняется фильтрация.

Например:

```sql
WHERE TransactionDate >= '2026-01-01'
```

Такой подход позволяет SQL Server быстрее работать с нужным диапазоном данных.

Сжатие данных необходимо применять осознанно. Оно уменьшает объем хранения, но требует дополнительных ресурсов процессора при работе с данными.

Чаще всего сжатие используется для:

- больших таблиц;
- архивных данных;
- таблиц, где много повторяющихся значений.

Для часто изменяемых таблиц необходимо учитывать нагрузку на систему.

Хронологические таблицы подходят для систем, где важно знать не только текущее состояние данных, но и историю изменений.

Примеры:

- изменение статуса заказа;
- изменение данных клиента;
- изменение стоимости товара;
- изменение настроек пользователя.

История изменений должна сохраняться автоматически, а не за счет ручного создания дополнительных таблиц и обработки каждого изменения отдельными запросами.

# Советы по улучшению работы

При проектировании больших баз данных важно учитывать не только создание таблиц, но и дальнейшее поведение системы при росте количества записей.

Хорошее решение должно учитывать, какие данные будут быстро увеличиваться, какие записи необходимо хранить долго, а какие можно переносить в архивное хранение.

Перед добавлением секционирования необходимо оценить размер таблицы. Для небольшой таблицы такая технология чаще всего будет избыточной.

При выборе стратегии хранения необходимо разделять активные и исторические данные. Например, последние месяцы операций могут использоваться ежедневно, а старые записи могут храниться для отчетности.

При использовании сжатия необходимо проверить реальные показатели, а не применять его автоматически ко всем объектам.

Хронологические таблицы рекомендуется использовать там, где требуется аудит изменений и возможность восстановить состояние данных на определенный момент времени.

Созданная структура должна быть подготовлена к дальнейшему развитию: добавлению индексов, оптимизации запросов, резервному копированию и анализу производительности.
