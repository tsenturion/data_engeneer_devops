# Практическое задание

# Создание индексов в MS SQL Server

## Цель

Спроектировать и реализовать набор индексов для таблиц MS SQL Server, сравнить поведение таблицы без кластеризованного индекса и таблицы с кластеризованным индексом, создать простые и составные некластеризованные индексы и проверить, как выбранная структура индексов влияет на выполнение запросов.

В рамках работы необходимо не просто создать несколько индексов, а определить, какие запросы они должны обслуживать, проверить планы выполнения и статистику ввода-вывода до и после индексирования, а затем сделать вывод о том, какие индексы действительно полезны.

Основной акцент работы — на проектировании индексов под реальную нагрузку. Наличие большого количества индексов само по себе не является признаком хорошо спроектированной базы данных.

# Задание

Для практической работы создать отдельную базу данных, содержащую данные системы обработки заказов. Основной таблицей должна стать таблица заказов или операций, объем которой позволит увидеть разницу между различными вариантами доступа к данным.

Минимальный рекомендуемый объем основной таблицы — 100 000 строк. При возможности допускается использовать 500 000–1 000 000 строк, чтобы различия в планах выполнения и количестве логических чтений проявлялись заметнее.

## 2. Создать таблицу-кучу

Создать таблицу заказов без первичного ключа и без кластеризованного индекса.

Таблица должна первоначально оставаться кучей.

В таблице предусмотреть минимум следующие данные:

```text
OrderId
CustomerId
OrderDate
Status
TotalAmount
ManagerId
RegionId
Comment
```

Типы данных необходимо подобрать самостоятельно с учетом назначения каждого столбца.

Пример основы таблицы:

```sql
CREATE TABLE Sales.Orders
(
    Orderid BIGINT NOT NULL,
    Customerid INT NOT NULL,
    Orderdate DATETIME2 NOT NULL,
    Status VARCHAR(30) NOT NULL,
    Totalamount DECIMAL(12, 2) NOT NULL,
    Managerid INT NULL,
    Regionid SMALLINT NOT NULL,
    Comment NVARCHAR(500) NULL
);
```

На этом этапе не создавать:

```text
PRIMARY KEY
CLUSTERED INDEX
NONCLUSTERED INDEX
```

После создания определить, действительно ли таблица является кучей.

Для проверки можно использовать системные представления:

```sql
SELECT
    i.name,
    i.index_id,
    i.type_desc
FROM sys.indexes AS i
WHERE i.object_id = OBJECT_ID('Sales.Orders');
```

Следует обратить внимание на значение `index_id`.

## 3. Заполнить таблицу тестовыми данными

Сгенерировать не менее 100 000 строк.

Данные должны содержать повторяющиеся значения для:

# Подсказки по ключевым частям

При выполнении работы необходимо разделять понятия структуры хранения и дополнительной структуры поиска. Если у таблицы отсутствует кластеризованный индекс, данные организованы как куча. После создания кластеризованного индекса страницы данных организуются по ключу кластеризованного индекса.

При анализе запросов не следует делать вывод только по времени выполнения. На небольшом объеме данных результаты могут зависеть от состояния кеша, текущей нагрузки на SQL Server и других факторов. Более информативным показателем для лабораторной работы часто будет количество логических чтений.

Для этого используется:

```sql
SET STATISTICS IO ON;
```

Например, в сообщениях можно увидеть:

```text
logical reads 850
```

После создания подходящего индекса для того же запроса значение может значительно уменьшиться.

При исследовании планов необходимо различать `Scan` и `Seek`.

`Index Seek` или `Clustered Index Seek` обычно означает, что SQL Server смог использовать структуру индекса для поиска требуемого диапазона ключей.

`Scan` означает просмотр значительной части структуры. Сам по себе `Scan` не всегда является ошибкой. Если запрос возвращает большую долю таблицы, последовательное чтение может быть дешевле множества точечных обращений через индекс.

Не следует считать правилом:

```text
Seek = всегда хорошо
Scan = всегда плохо
```

Решение необходимо оценивать в контексте количества строк, логических чтений, селективности условия и всей стоимости плана.

При проектировании составных индексов порядок столбцов имеет значение.

Индекс:

```sql
(CustomerId, OrderDate)
```

не эквивалентен индексу:

```sql
(OrderDate, CustomerId)
```

Первый вариант может быть удобен для запросов, начинающих фильтрацию по `CustomerId`, а второй — для другой структуры нагрузки.

При выборе ключевых столбцов необходимо учитывать их типы данных и размер. Очень широкие ключи увеличивают размер индекса, поскольку значения ключа необходимо хранить внутри индексной структуры.

Особенно внимательно следует относиться к столбцам вроде:

```sql
NVARCHAR(500)
```

или другим длинным строковым значениям.

Не следует создавать индекс по каждому столбцу таблицы. При каждой операции `INSERT`, `UPDATE` и `DELETE` SQL Server должен поддерживать соответствующие индексные структуры.

Поэтому при разработке высоконагруженной базы необходимо искать баланс между стоимостью чтения и стоимостью изменения данных.

# Советы по улучшению работы

Не оценивайте индекс только по тому, создался он без ошибки или нет. Главная проверка начинается после `CREATE INDEX`. Необходимо выяснить, использует ли его оптимизатор и действительно ли он сокращает объем работы SQL Server.

Не создавайте индекс только потому, что столбец присутствует в `WHERE`. Если условие возвращает половину таблицы, использование некластеризованного индекса может оказаться дороже обычного сканирования.

При работе с составными индексами анализируйте реальные шаблоны запросов. Индекс должен проектироваться под конкретную нагрузку, а не под отдельную таблицу в отрыве от запросов.

Сравнивайте результаты через логические чтения:

```sql
SET STATISTICS IO ON;
```

Если до создания индекса SQL Server выполнил несколько тысяч логических чтений, а после создания подходящего индекса — несколько десятков, это гораздо более показательный результат, чем небольшое отличие времени выполнения на локальном компьютере.

Обращайте внимание на `Key Lookup`. Его наличие не означает автоматически, что индекс спроектирован неправильно. Один или несколько обращений могут быть дешевыми. Если же `Key Lookup` выполняется тысячи раз, стоимость такого плана может стать значительной.

Не оставляйте экспериментальные индексы после завершения анализа. После выполнения работы структура должна содержать только те индексы, необходимость которых можно объяснить через реальные запросы.

Для высоконагруженной базы особенно важно учитывать не только `SELECT`. Чем больше индексов имеет таблица, тем больше структур требуется поддерживать при изменении строк. Поэтому индекс, ускоряющий редко выполняемый запрос, но заметно увеличивающий стоимость миллионов операций записи, может оказаться неправильным архитектурным решением.

Итогом работы должен стать не максимальный набор индексов, а минимально достаточная индексная структура, для каждого элемента которой можно ответить на три вопроса: какой запрос этот индекс обслуживает, насколько он уменьшает стоимость чтения и какую дополнительную стоимость создает для операций изменения данных.
