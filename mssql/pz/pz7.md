# Практическое задание

# Использование колоночных индексов в MS SQL Server

## Цель

Исследовать устройство и практическое применение колоночных индексов SQL Server, создать кластеризованный и некластеризованный Columnstore-индекс, сравнить их с традиционными строковыми индексами и определить, для каких типов нагрузки колоночное хранение дает наибольший эффект.

В рамках работы необходимо создать таблицу с большим объемом данных, выполнить аналитические запросы до и после создания Columnstore-индекса, изучить планы выполнения, сравнить количество логических чтений, время выполнения и объем занимаемого пространства.

Дополнительно необходимо исследовать внутреннее состояние Columnstore через группы строк, сегменты и delta store, выполнить операции добавления и изменения данных и провести обслуживание колоночного индекса.

Главная задача работы — определить, когда Columnstore является рациональным архитектурным решением, а когда традиционный Rowstore остается предпочтительным.

# Задание

Необходимо создать базу данных, моделирующую хранилище большого количества операций.

Рекомендуемая предметная область — аналитическая система продаж.

Основная таблица должна содержать не менее 500 000 строк. Для более показательного эксперимента рекомендуется использовать от 1 до 3 миллионов строк.

В таблице должны присутствовать:

- идентификаторы;
- даты;
- числовые показатели;
- категориальные значения;
- данные, подходящие для группировки;
- данные, подходящие для агрегирования.


Второй запрос — продажи по регионам:

```sql
SELECT
    REGIONID,
    COUNT(*) AS SALESCOUNT,
    SUM(TOTALAMOUNT) AS TOTALSALES,
    AVG(TOTALAMOUNT) AS AVERAGESALE
FROM ANALYTICS.SALESROWSTORE
GROUP BY REGIONID;
```

Третий запрос — продажи по годам:

```sql
SELECT
    YEAR(SALEDATE) AS SALEYEAR,
    COUNT(*) AS SALESCOUNT,
    SUM(TOTALAMOUNT) AS TOTALSALES
FROM ANALYTICS.SALESROWSTORE
GROUP BY YEAR(SALEDATE)
ORDER BY SALEYEAR;
```

Четвертый запрос:

```sql
SELECT
    CATEGORYID,
    REGIONID,
    SUM(QUANTITY) AS TOTALQUANTITY,
    SUM(TOTALAMOUNT) AS TOTALSALES
FROM ANALYTICS.SALESROWSTORE
WHERE
    SALEDATE >= '2025-01-01'
    AND SALEDATE < '2026-01-01'
GROUP BY
    CATEGORYID,
    REGIONID;
```

Пятый запрос:

```sql
SELECT
    TOP(20)
        PRODUCTID,
    SUM(QUANTITY) AS TOTALQUANTITY,
    SUM(TOTALAMOUNT) AS TOTALSALES
FROM ANALYTICS.SALESROWSTORE
GROUP BY PRODUCTID
ORDER BY TOTALSALES DESC;
```

Для каждого запроса сохранить фактический план выполнения.

# Подсказки по ключевым частям

Columnstore необходимо рассматривать не просто как еще один вид индекса. Это другой способ организации и обработки больших объемов информации.

В традиционной Rowstore-структуре значения одной строки располагаются совместно. Такой формат хорошо соответствует операциям, где необходимо быстро получить конкретную строку или небольшой набор строк.

Например:

```sql
SELECT *
FROM Analytics.Salesrowstore
WHERE Saleid = 250000;
```

В подобных операциях классический B-tree индекс может быть чрезвычайно эффективным.

Columnstore ориентирован на другой тип нагрузки. Значения организуются по столбцам, что особенно удобно, когда запрос обрабатывает миллионы строк, но использует лишь несколько колонок.

Например:

```sql
SELECT
    REGIONID,
    SUM(TOTALAMOUNT)
FROM ANALYTICS.SALESCOLUMNSTORE
GROUP BY REGIONID;
```

Для такого запроса нет необходимости логически работать со всеми столбцами большой таблицы.

Именно поэтому Columnstore особенно характерен для:

```text
аналитических систем;
хранилищ данных;
отчетности;
больших таблиц фактов;
агрегационных запросов;
исторических данных.
```

При этом не следует делать вывод, что Columnstore всегда быстрее обычных индексов.

Запрос вида:

```sql
SELECT *
FROM Analytics.Salesrowstore
WHERE Saleid = 100;
```

имеет совершенно другую природу нагрузки.

Для точечного поиска хорошо спроектированный Rowstore-индекс часто будет более естественным решением.

---

Важным элементом Columnstore является Row Group. Не нужно представлять колоночный индекс как одну непрерывную структуру. SQL Server организует данные в группы строк, после чего внутри них формирует колоночные сегменты.

Поэтому при диагностике необходимо использовать:

```sql
sys.column_store_row_groups
```

и анализировать не только сам факт существования Columnstore, но и состояние его групп строк.

---

Необходимо обратить внимание на значение:

```text
deleted_rows
```

После удаления данных строки могут логически считаться удаленными, но физическая организация Columnstore имеет собственный жизненный цикл.

Если доля удаленных строк становится значительной, это может влиять на эффективность хранения и обработки.

---

При загрузке данных также имеет значение размер порции.

Большие пакетные загрузки обычно лучше соответствуют природе аналитических систем, чем постоянный поток единичных изменений.

Это не означает, что Columnstore не поддерживает изменения данных. Необходимо понимать различия между возможностью выполнить операцию и оптимальностью такой модели нагрузки.

---

Некластеризованный Columnstore особенно интересен для систем смешанного типа.

Основная таблица может оставаться традиционной:

```text
Rowstore
```

и использовать классические индексы для транзакционных операций.

Одновременно:

```text
Nonclustered Columnstore Index
```

может использоваться для аналитики.

Такой вариант необходимо рассмотреть в практической работе как возможную архитектуру системы, в которой одновременно существуют OLTP- и аналитические запросы.

---

При оценке производительности не используйте только время выполнения.

Обязательно анализируйте:

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
```

и планы выполнения.

Первый запуск запроса и повторный запуск могут существенно отличаться из-за состояния кеша.

Поэтому необходимо сравнивать несколько показателей одновременно.

---

Columnstore также тесно связан со сжатием данных.

Хорошо повторяющиеся значения часто позволяют получить значительное уменьшение объема хранения.

Например, столбец:

```text
RegionId
```

может содержать миллионы значений, но фактически иметь всего несколько различных вариантов.

Аналогичная ситуация может возникать для:

```text
Status
CategoryId
ManagerId
```

Такая структура хорошо подходит для колоночного представления.

---

При сравнении Rowstore и Columnstore не изменяйте одновременно слишком много факторов.

Если для Rowstore создать десять оптимизированных индексов, а Columnstore оставить без дополнительных структур, сравнение перестанет отражать именно различие моделей хранения.

Лучше сначала сравнить базовые варианты, а затем отдельно исследовать гибридную архитектуру.

# Советы по улучшению работы

Не оценивайте Columnstore на таблице из нескольких тысяч строк. На небольшом объеме данных эффект может быть практически незаметен, а стоимость дополнительных механизмов может исказить результат. Для этой работы необходим достаточно большой набор данных.

Не измеряйте только продолжительность выполнения запроса. Сравнивайте планы, логические чтения, CPU Time и количество обработанных строк.

Не делайте вывод, что Columnstore должен заменить все обычные индексы. Это архитектура, ориентированная прежде всего на определенный профиль нагрузки.

При проектировании аналитической системы обращайте внимание на то, сколько столбцов реально требуется запросу. Запрос:

```sql
SELECT SUM(TOTALAMOUNT)
FROM ANALYTICS.SALESCOLUMNSTORE;
```

хорошо соответствует природе колоночного хранения.

Запрос:

```sql
SELECT *
FROM Analytics.Salescolumnstore;
```

использует значительно больше данных и имеет другой профиль нагрузки.

Не забывайте анализировать Row Group. Недостаточно увидеть надпись `COLUMNSTORE` в списке индексов. Эксплуатация таких структур требует понимания того, насколько качественно сформированы сжатые группы строк и сколько в них логически удаленных записей.

Не выполняйте `REBUILD` после каждого изменения данных. Обслуживание индекса само является ресурсоемкой операцией. Необходимо сначала исследовать состояние структуры и только затем принимать решение.

Для больших хранилищ желательно рассматривать способ загрузки данных как часть архитектуры. Пакетная загрузка больших объемов и постоянные единичные изменения создают разный профиль эксплуатации Columnstore.

При смешанной нагрузке обязательно исследуйте вариант:

```text
Rowstore + Nonclustered Columnstore
```

Он позволяет сохранить классические B-tree индексы для транзакционных операций и одновременно предоставить аналитическим запросам колоночную структуру.

В итоговом решении необходимо отвечать не на вопрос «Columnstore быстрее или медленнее», а на более точный вопрос: какой тип хранения эффективнее для конкретного характера нагрузки, объема данных и набора запросов.

Итоговая работа считается выполненной качественно, если выбор между Rowstore, Clustered Columnstore и гибридной архитектурой сделан на основании измерений, планов выполнения, структуры Row Group и характера операций, а не только на основании общего представления о том, что колоночные индексы предназначены для больших таблиц.
