# Практическое задание

# Реагирование на изменение данных через триггеры в MS SQL Server

## Цель

Спроектировать и реализовать DML-триггеры в MS SQL Server для автоматической реакции на операции `INSERT`, `UPDATE` и `DELETE`, организовать аудит изменений, проверить работу логики при массовом изменении строк и исследовать расширенные возможности триггеров.

В ходе практической работы необходимо создать базу данных с несколькими связанными таблицами, реализовать `AFTER`- и `INSTEAD OF`-триггеры, использовать специальные таблицы `inserted` и `deleted`, выполнять проверку изменяемых данных, создавать историю изменений и исследовать влияние триггеров на транзакции и производительность.

Особое внимание необходимо уделить тому, что триггер SQL Server должен корректно работать не только с одной строкой, но и с множеством строк, изменяемых одной командой.

Основной результат работы — научиться применять триггеры только для задач, где автоматическая реакция на изменение данных действительно оправдана, и избегать скрытой логики, усложняющей сопровождение базы данных.

Необходимо создать отдельную базу данных для системы управления складом и заказами.

# 11. Создание первого AFTER INSERT-триггера

Создать триггер, который после добавления нового товара автоматически создает строку его остатка со значением `0`.

```sql
CREATE TRIGGER Sales.trg_Products_AfterInsert
ON Sales.Products
AFTER INSERT
AS
BEGIN
    SET NOCOUNT ON;

    INSERT INTO Sales.Stock
    (
        ProductId,
        Quantity
    )
    SELECT
        i.ProductId,
        0
    FROM inserted AS i;
END;
GO
```

Убедиться, что строка остатка была создана автоматически.

# 13. Создание AFTER UPDATE-триггера для истории цен

Создать триггер, который сохраняет изменение цены товара.

```sql
CREATE TRIGGER Sales.trg_Products_PriceHistory
ON Sales.Products
AFTER UPDATE
AS
BEGIN
    SET NOCOUNT ON;

    INSERT INTO Audit.ProductPriceHistory
    (
        ProductId,
        OldPrice,
        NewPrice,
        ChangedBy
    )
    SELECT
        d.ProductId,
        d.Price,
        i.Price,
        SUSER_SNAME()
    FROM inserted AS i
    INNER JOIN deleted AS d
        ON d.ProductId = i.ProductId
    WHERE i.Price <> d.Price;
END;
GO
```

Изменить цену:

```sql

SET Price = 40000
WHERE Productid = 1;
```

Проверить:

```sql

FROM Audit.Productpricehistory
ORDER BY Historyid DESC;
```

# 26. Реализация пересчета для нескольких заказов

# 36. Получение списка всех DML-триггеров

Использовать:

```sql
SELECT
    OBJECT_SCHEMA_NAME(t.parent_id) AS schemaname,
    OBJECT_NAME(t.parent_id) AS tablename,
    t.name AS triggername,
    t.is_disabled,
    t.create_date,
    t.modify_date
FROM sys.triggers AS t
WHERE t.parent_class_desc = 'OBJECT_OR_COLUMN'
ORDER BY
    schemaname,
    tablename,
    triggername;
```

# Подсказки по ключевым частям

DML-триггер — это объект базы данных, автоматически выполняемый в ответ на изменение данных.

В рамках работы рассматриваются события:

```sql
INSERT
UPDATE
DELETE
```

Для обычного вызова триггера не используется:

```sql
EXEC
```

Он вызывается самой DML-операцией.

Например:

```sql
UPDATE Sales.Products
SET Price = 50000
WHERE Productid = 1;
```

может автоматически вызвать один или несколько триггеров таблицы `Products`.

Это делает триггер удобным механизмом автоматической реакции, но одновременно означает, что его логика менее очевидна человеку, который смотрит только на исходный `UPDATE`.

Поэтому триггеры следует применять осознанно.

Одно из самых важных правил SQL Server — триггер должен проектироваться для набора строк.

Нельзя считать, что:

```sql
SELECT @ProductId = ProductId
FROM inserted;
```

безопасно решает задачу для любого `INSERT`.

Если одна команда добавляет:

```sql
INSERT ...
VALUES
(...),
(...),
(...);
```

`inserted` содержит несколько строк.

Если триггер берет одну строку в переменную, остальные данные могут быть проигнорированы.

Правильный стиль — наборная обработка:

```sql
INSERT INTO Audit.SomeHistory
(
    ...
)
SELECT
    ...
FROM inserted;
```

При `INSERT` специальная таблица:

```text
inserted
```

содержит новые строки.

При `DELETE`:

```text
deleted
```

содержит удаленные строки.

При `UPDATE` участвуют обе:

```text
deleted — состояние до изменения;
inserted — состояние после изменения.
```

Именно поэтому аудит изменений удобно строить через соединение:

```sql
FROM inserted AS i
INNER JOIN deleted AS d
    ON ...
```

Необходимо отличать `AFTER` и `INSTEAD OF`.

`AFTER` выполняется после успешного выполнения соответствующей операции и проверки ограничений.

`INSTEAD OF` выполняется вместо исходной операции.

Например, запрос:

```sql
DELETE FROM Sales.Customers
WHERE Customerid = 10;
```

при наличии `INSTEAD OF DELETE` может вообще не удалять строку, а выполнить:

```sql
UPDATE Sales.Customers
SET Isactive = 0
WHERE Customerid = 10;
```

Так можно реализовать мягкое удаление.

При этом триггер не должен подменять ограничения там, где достаточно декларативных механизмов SQL Server.

Например:

```text
цена не должна быть отрицательной
```

лучше выражается через:

```sql
CHECK (Price >= 0)
```

а не через триггер.

Связь между заказом и клиентом лучше контролировать:

```sql
FOREIGN KEY
```

Уникальность Email лучше контролировать:

```sql
UNIQUE
```

Триггер следует использовать там, где правило зависит от сложного состояния, требует аудита или автоматической реакции на событие.

Например:

```text
записать старое и новое значение цены;
пересчитать агрегированное поле;
зафиксировать изменение статуса;
выполнить мягкое удаление;
проверить сложное межтабличное правило.
```

Необходимо понимать транзакционную природу триггера.

Если внутри триггера возникает ошибка:

```sql
THROW
```

исходная операция обычно также не может завершиться успешно.

Например, если `UPDATE` пытается установить запрещенную цену, триггер может остановить операцию, и новая цена не будет сохранена.

Это делает триггеры сильным механизмом контроля, но ошибка в триггере способна заблокировать обычные операции приложения.

При аудите пользователя необходимо понимать разницу между пользователем SQL Server и пользователем приложения.

Если приложение подключается под одним техническим логином:

```text
application_login
```

тогда:

```sql
SUSER_SNAME()
```

будет одинаковым для всех операторов приложения.

В таких системах можно передавать прикладной идентификатор через:

```sql
SESSION_CONTEXT
```

и сохранять его в журнале.

Необходимо учитывать, что такая информация надежна настолько, насколько надежно приложение устанавливает контекст.

При проектировании триггера избегайте:

```text
курсоров;
циклов по inserted;
отдельного UPDATE для каждой строки;
отдельного INSERT истории для каждой строки.
```

Старайтесь решать задачу одним или несколькими наборными запросами.

Не следует создавать длинные цепочки триггеров, в которых один триггер изменяет таблицу, второй вызывает третий, третий изменяет первую таблицу. Такие системы сложно анализировать и тестировать.

Если вложенное поведение действительно необходимо, исследуйте:

```sql
TRIGGER_NESTLEVEL()
```

и конфигурацию рекурсивных триггеров.

Не полагайтесь на неопределенный порядок нескольких триггеров одного события. Если логика зависит от жесткой последовательности, лучше пересмотреть архитектуру. `sp_settriggerorder` может задать первый и последний триггер, но не превращает набор независимых триггеров в удобный механизм управления сложным workflow.

Не создавайте триггер для задачи, которую прозрачнее решить в хранимой процедуре.

Если изменение данных происходит только через одну контролируемую процедуру, иногда бизнес-логика внутри процедуры будет понятнее.

Если же правило должно выполняться независимо от того, кто изменяет данные:

```text
приложение;
DBeaver;
другая процедура;
ETL;
администратор;
```

триггер может быть оправдан.

# Советы по улучшению работы

Не используйте триггер там, где достаточно `CHECK`, `FOREIGN KEY`, `UNIQUE`, `DEFAULT` или другого декларативного механизма SQL Server. Такие ограничения обычно проще, прозрачнее и надежнее.

Не пишите триггеры для одной строки. Это одна из наиболее частых ошибок.

Плохо:

```sql
DECLARE @ProductId INT;

SELECT @ProductId = ProductId
FROM inserted;
```

если операция потенциально может затронуть несколько строк.

Предпочтительно:

```sql
INSERT INTO Audit.Sometable
(
    Productid
)
SELECT Productid
FROM Inserted;
```

Тестируйте каждый триггер минимум в трех сценариях: изменение одной строки, изменение нескольких строк и операция, которая фактически не затрагивает ни одной строки.

Не скрывайте критичную бизнес-логику в десятках триггеров без документации. При сопровождении системы необходимо понимать, какие дополнительные действия происходят после `INSERT`, `UPDATE` или `DELETE`.

Для аудита сохраняйте как минимум:

```text
что изменилось;
старое значение;
новое значение;
когда произошло изменение;
кто инициировал изменение.
```

Если аудит необходим для строгих регуляторных требований, обычной пользовательской таблицы истории и DML-триггера может быть недостаточно. В таком случае необходимо отдельно рассматривать специализированные средства аудита SQL Server и архитектурные требования конкретной системы.

Не используйте триггер для отправки длительных сетевых запросов, запуска тяжелой внешней логики или других продолжительных действий. Пока работает триггер, исходная операция остается частью той же транзакционной работы и может удерживать блокировки.

Не делайте сложные отчеты внутри триггера. Триггер должен выполнять минимально необходимую реакцию на изменение данных.

Если нужно записать историю 100 000 измененных строк, триггер должен выполнять наборный `INSERT ... SELECT`, а не 100 000 отдельных операций через цикл.

При работе с несколькими триггерами одной таблицы не проектируйте систему, зависящую от случайного порядка их выполнения.

При использовании `INSTEAD OF` внимательно проверяйте, что исходное действие действительно реализовано внутри триггера. Если `INSTEAD OF INSERT` не выполнит собственный `INSERT`, новая строка не появится.

При тестировании ошибок обязательно проверяйте состояние данных после `THROW`. Недостаточно увидеть сообщение об ошибке — необходимо убедиться, что исходное изменение не было частично сохранено.

При работе с историей избегайте записи изменений, которых фактически не было. Например:

```sql
SET Price = Price
```

не должно автоматически интерпретироваться как реальное изменение цены только потому, что столбец присутствовал в `SET`.

Для сложных проверок сравнивайте значения из:

```text
inserted
deleted
```

Итоговая работа считается качественно выполненной, если триггеры корректно работают с массовыми операциями, не используют ошибочную построчную логику, поддерживают согласованность данных, не дублируют возможности обычных ограничений и имеют понятное, обоснованное назначение.
