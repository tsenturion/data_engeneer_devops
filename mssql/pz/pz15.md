# Практическое задание

# Работа с пространственными данными SQL Server

## Цель

Освоить хранение, создание, обработку и поиск пространственных данных в MS SQL Server, изучить различия между типами `geometry` и `geography`, научиться создавать точки, линии и полигоны, выполнять пространственные операции и использовать пространственные индексы.

В рамках практической работы необходимо реализовать два независимых сценария.

Первый сценарий моделирует план здания или территории в условной декартовой системе координат и использует тип:

```sql
geometry
```

Второй сценарий моделирует расположение реальных объектов по GPS-координатам и использует:

```sql
geography
```

Дополнительно необходимо реализовать передачу координат из прикладной программы в SQL Server и получение пространственных данных обратно в приложение.

Основной результат работы — научиться выбирать пространственный тип в зависимости от задачи, выполнять пространственные запросы и понимать, когда обычные числовые столбцы `Latitude` и `Longitude` уже недостаточны.

# 13. Проверка пересечения объектов

Создать линию предполагаемой прокладки кабеля:

```sql
DECLARE @Cable geometry =
    geometry::STGeomFromText
    (
        'LINESTRING
        (
            -20 40,
            250 40
        )',
        0
    );

SELECT
    RoomName,
    Shape.STIntersects(@Cable) AS IntersectsCable
FROM Map.Rooms;
```

`STIntersects()` возвращает `1`, если пространственные объекты пересекаются, и `0`, если пересечения нет. При разных SRID метод возвращает `NULL`.

# 18. Создание geometry spatial index

Пространственные индексы SQL Server создаются только для столбцов `geometry` или `geography`. Для spatial index таблица должна иметь кластеризованный первичный ключ.

Создать индекс:

```sql
CREATE SPATIAL INDEX SIX_Rooms_Shape
ON Map.Rooms(Shape)
USING GEOMETRY_AUTO_GRID
WITH
(
    BOUNDING_BOX =
    (
        -100,
        -100,
        500,
        500
    )
);
GO
```

Проверить:

```sql
SELECT
    name,
    type_desc
FROM sys.indexes
WHERE object_id =
    OBJECT_ID('Map.Rooms');
```

# 22. Первое знакомство с geography

SQL Server `geography` представляет объекты в геодезической, то есть округлой земной системе координат, и подходит для GPS-координат.

Создать географическую точку:

```sql
DECLARE @Location geography;

SET @Location =
    geography::Point
    (
        55.7539,
        37.6208,
        4326
    );

SELECT
    @Location.STAsText() AS Location,
    @Location.Lat AS Latitude,
    @Location.Long AS Longitude,
    @Location.STSrid AS Srid;
```

---

# 23. Важное различие порядка координат

Для:

```sql
geography::Point
```

порядок аргументов:

```text
Latitude
Longitude
SRID
```

Например:

```sql
geography::Point
(
    55.7539,
    37.6208,
    4326
);
```

Для WKT используется обратный порядок координат:

```text
X Y
Longitude Latitude
```

Поэтому эквивалент:

```sql
geography::STGeomFromText
(
    'POINT(37.6208 55.7539)',
    4326
);
```

Microsoft отдельно указывает, что порядок координат `geography::Point(Lat, Long, SRID)` обратен порядку в WKT.

# 27. Вычисление расстояния между филиалами

Получить две точки:

```sql
DECLARE @Branch1 geography;
DECLARE @Branch2 geography;

SELECT
    @Branch1 = Location
FROM Geo.Branches
WHERE BranchId = 1;

SELECT
    @Branch2 = Location
FROM Geo.Branches
WHERE BranchId = 2;

SELECT
    @Branch1.STDistance(@Branch2)
        AS Distance;
```

Для `geography` единица измерения результата определяется SRID. `STDistance()` возвращает приблизительное геодезическое расстояние между объектами и возвращает `NULL`, если SRID объектов различаются.

Для используемого в работе WGS84 результат удобно интерпретировать как расстояние в метрах.

# Подсказки по ключевым частям

Главное различие между двумя пространственными типами заключается не в синтаксисе, а в модели пространства.

`geometry` рассматривает координаты как точки на плоскости.

Например:

```sql
geometry::Point
(
    100,
    200,
    0
)
```

может обозначать положение оборудования на плане здания.

Здесь:

```text
100
200
```

не являются широтой и долготой.

Они могут означать:

```text
метры;
миллиметры;
пиксели;
условные единицы чертежа.
```

`geography` предназначен для координат на поверхности Земли.

Например:

```sql
geography::Point
(
    55.7539,
    37.6208,
    4326
)
```

представляет точку с широтой и долготой.

Не следует использовать `geometry` с GPS-координатами только потому, что они технически помещаются в два числа. При вычислении больших расстояний плоская модель не учитывает форму Земли.

Особенно важно не перепутать порядок координат.

При использовании:

```sql
geography::Point
```

порядок:

```text
Latitude
Longitude
```

При WKT:

```text
POINT(X Y)
```

для GPS это:

```text
POINT(Longitude Latitude)
```

Например:

```sql
geography::Point
(
    55.7539,
    37.6208,
    4326
)
```

и:

```sql
geography::STGeomFromText
(
    'POINT(37.6208 55.7539)',
    4326
)
```

представляют одну и ту же точку. Такое различие официально отмечено в документации SQL Server.

SRID необходимо рассматривать как часть пространственных данных.

Он сообщает, в какой системе пространственных координат следует интерпретировать объект.

Если два объекта имеют разные:

```text
STSrid
```

нельзя ожидать корректного пространственного сравнения.

Например:

```sql
A.STDistance(B)
```

вернет `NULL`, если SRID не совпадают.

Для GPS-сценария в этой работе используется:

```text
4326
```

WGS84.

При работе с `geography` расстояние нельзя вычислять вручную как простую разницу:

```text
Latitude1 - Latitude2
Longitude1 - Longitude2
```

Такой расчет не является реальным расстоянием по поверхности Земли.

Используйте:

```sql
STDistance()
```

SQL Server сам учитывает используемую географическую модель.

Пространственные запросы хорошо подходят для задач вида:

```text
найти ближайший филиал;
найти клиента в зоне доставки;
найти датчики внутри территории;
проверить пересечение маршрута с зоной;
определить помещение для оборудования;
найти объекты в радиусе пяти километров.
```

Пространственный тип не отменяет обычные реляционные столбцы.

Для филиала все равно необходимо хранить:

```text
BranchId
BranchName
Address
```

а spatial-столбец отвечает именно за географическую часть данных.

Не следует вместо:

```sql
Location geography
```

хранить только:

```text
Latitude FLOAT
Longitude FLOAT
```

если системе регулярно необходимо выполнять:

```text
расстояния;
пересечения;
буферные зоны;
поиск внутри полигона;
пространственную индексацию.
```

Отдельные `Latitude` и `Longitude` допустимы как дополнительные данные или как формат обмена с приложением, но SQL Server не сможет применить к двум независимым числам полный набор spatial-операций без предварительного создания пространственного объекта.

Пространственный индекс также не является обычным B-tree индексом.

SQL Server использует специальную пространственную индексацию, основанную на разбиении пространства. Поэтому запрос должен быть сформулирован таким образом, чтобы оптимизатор мог использовать spatial index.

Для `geography` поддерживаются в том числе определенные формы:

```sql
Location.STIntersects(@Area) = 1
```

и:

```sql
Location.STDistance(@Point) <= 5000
```

при выполнении требований пространственного индекса.

Не следует ожидать, что spatial index обязательно ускорит запрос на таблице из десяти строк. Эффект необходимо проверять на достаточно большом наборе пространственных объектов.

Для `geometry` при создании spatial index необходимо особенно внимательно определить:

```sql
BOUNDING_BOX
```

Если данные фактически находятся в координатах:

```text
0–1000
```

разумно использовать область, охватывающую эти значения.

Не следует случайно задавать:

```text
0–10
```

для данных, большая часть которых находится значительно дальше.

Для `geography` `BOUNDING_BOX` не задается. SQL Server использует географическую модель пространства.

При работе с приложением не обязательно передавать сложный CLR-объект пространственного типа через драйвер.

Практичный вариант — передать обычные параметры:

```text
latitude
longitude
```

и сформировать пространственное значение непосредственно в параметризованном SQL:

```sql
geography::Point(?, ?, 4326)
```

Такой подход особенно удобен для Python-приложений.

Для обмена между системами также подходят стандартизированные представления:

```text
WKT
WKB
```

WKT удобно читать человеку:

```text
POINT(37.6208 55.7539)
```

WKB предназначен для бинарного представления.

Пространственные данные следует применять там, где пространственные отношения действительно являются частью бизнес-логики. Если приложению требуется только один раз вывести широту и долготу на экран и никогда не выполняются пространственные запросы, полноценная spatial-модель может оказаться избыточной.

# Советы по улучшению работы

Не смешивайте `geometry` и `geography` в одной логической задаче без необходимости. Сначала определите, плоская у вас система координат или географическая.

Для планировки здания используйте:

```sql
geometry
```

Для GPS и реальных расстояний:

```sql
geography
```

Не путайте широту и долготу. Эта ошибка особенно легко появляется при переходе между:

```sql
geography::Point()
```

и WKT.

При создании точки через:

```sql
geography::Point
```

используйте:

```text
Latitude, Longitude
```

При WKT:

```text
Longitude Latitude
```

Перед выполнением пространственных операций проверяйте SRID.

Не исправляйте несовпадение SRID простым присваиванием другого номера без понимания системы координат. Изменение идентификатора само по себе не является полноценным преобразованием координат между системами.

Не храните пространственные данные исключительно как текст:

```text
"55.75, 37.62"
```

если база должна выполнять пространственные операции.

Не пытайтесь вручную реализовывать географическое расстояние обычной формулой SQL, если задача уже корректно решается:

```sql
STDistance()
```

Не создавайте spatial index до понимания рабочей нагрузки. Как и любой индекс, он занимает пространство и требует обслуживания.

Не оценивайте индекс по таблице из пяти точек. Используйте десятки тысяч объектов и реальные пространственные предикаты.

Для поиска объектов рядом с пользователем используйте пространственное условие:

```sql
Location.STDistance(@UserLocation) <= @Radius
```

а не загрузку всех строк в приложение с последующим расчетом расстояния циклом Python.

Это позволяет выполнять отбор ближе к данным и дает SQL Server возможность использовать пространственную индексацию.

При интеграции с приложением всегда используйте параметризованные запросы. Не формируйте координаты конкатенацией пользовательской строки непосредственно в SQL.

Итоговая работа считается качественно выполненной, если проведено практическое сравнение `geometry` и `geography`, реализованы точки, линии и полигоны, выполнены пространственные отношения и расчеты расстояний, протестирован spatial index и координаты успешно используются не только внутри SQL Server, но и из прикладного кода.
