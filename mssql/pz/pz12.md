# Практическое задание

# Использование таблиц в оперативной памяти в MS SQL Server

## Цель

Спроектировать и реализовать объекты In-Memory OLTP в MS SQL Server, создать таблицы, оптимизированные для размещения в оперативной памяти, исследовать варианты их устойчивости, сравнить HASH- и NONCLUSTERED-индексы и реализовать хранимые процедуры с нативной компиляцией.

В рамках практической работы необходимо подготовить базу данных для использования In-Memory OLTP, создать обычную дисковую таблицу и аналогичную memory-optimized таблицу, выполнить операции `INSERT`, `SELECT`, `UPDATE` и `DELETE`, исследовать использование оперативной памяти, проверить особенности `SCHEMA_AND_DATA` и `SCHEMA_ONLY`, создать HASH-индексы и проанализировать значение `BUCKET_COUNT`.

Вторая часть работы посвящена процедурам, компилируемым в машинный код. Необходимо реализовать обычную интерпретируемую процедуру и процедуру с `NATIVE_COMPILATION`, выполнить одинаковую нагрузку и сравнить полученные показатели.

Основной результат работы — определить, в каких сценариях In-Memory OLTP может быть полезен для высоконагруженной транзакционной базы данных и почему перенос любой таблицы в оперативную память сам по себе не гарантирует ускорения системы.

# Задание

Необходимо создать отдельную лабораторную базу данных.

Предметная область — система регистрации большого количества оперативных событий. Это могут быть события приложения, операции пользователей, сеансы, телеметрия или очередь обработки.

# 1. Проверка поддержки In-Memory OLTP

До создания объектов проверить экземпляр SQL Server.

Выполнить:

```sql
SELECT
    SERVERPROPERTY('ProductVersion') AS PRODUCTVERSION,
    SERVERPROPERTY('Edition') AS EDITION,
    SERVERPROPERTY('IsXTPSupported') AS ISXTPSUPPORTED;
```

Значение:

```text
IsXTPSupported = 1
```

означает, что экземпляр SQL Server поддерживает In-Memory OLTP. Свойство `IsXTPSupported` официально предназначено для такой проверки.

Если возвращается:

```text
0
```

необходимо зафиксировать результат и проверить конфигурацию используемого SQL Server.

# 10. Создание memory-optimized таблицы

Создать аналогичную структуру в оперативной памяти:

```sql
CREATE TABLE Operations.EventsMemory
(
    EventId BIGINT IDENTITY(1,1) NOT NULL,

    CustomerId INT NOT NULL,

    EventType TINYINT NOT NULL,

    Amount DECIMAL(12,2) NOT NULL,

    Status TINYINT NOT NULL,

    CreatedAt DATETIME2(3) NOT NULL,

    Payload NVARCHAR(200) NULL,

    CONSTRAINT PK_EventsMemory
        PRIMARY KEY NONCLUSTERED HASH (EventId)
        WITH
        (
            BUCKET_COUNT = 131072
        ),

    INDEX IX_EventsMemory_CustomerId
        NONCLUSTERED HASH (CustomerId)
        WITH
        (
            BUCKET_COUNT = 65536
        ),

    INDEX IX_EventsMemory_CreatedAt
        NONCLUSTERED (CreatedAt)
)
WITH
(
    MEMORY_OPTIMIZED = ON,
    DURABILITY = SCHEMA_AND_DATA
);
GO
```

Параметр:

```sql
MEMORY_OPTIMIZED = ON
```

указывает, что таблица относится к In-Memory OLTP.

Параметр:

```sql
DURABILITY = SCHEMA_AND_DATA
```

означает, что сохраняются и схема, и данные таблицы. При восстановлении базы после перезапуска данные долговечной memory-optimized таблицы восстанавливаются из устойчивого хранения.

# 17. Исследование BUCKET_COUNT

Получить статистику HASH-индексов:

```sql
SELECT
    OBJECT_NAME(h.object_id) AS tablename,
    i.name AS indexname,
    h.total_bucket_count,
    h.empty_bucket_count,
    CONVERT(
        DECIMAL(10, 2),
        h.empty_bucket_count * 100.0
        / NULLIF(h.total_bucket_count, 0)
    ) AS emptybucketpercent,
    h.avg_chain_length,
    h.max_chain_length
FROM sys.dm_db_xtp_hash_index_stats AS h
INNER JOIN sys.indexes AS i
    ON
        i.object_id = h.object_id
        AND i.index_id = h.index_id
WHERE
    h.object_id
    = OBJECT_ID('Operations.EventsMemory');
```

Зафиксировать:

```text
total_bucket_count
empty_bucket_count
EmptyBucketPercent
avg_chain_length
max_chain_length
```

`BUCKET_COUNT` является обязательным параметром HASH-индекса. Его недостаточное значение увеличивает длину цепочек, а слишком большое значение расходует дополнительную память. Microsoft рекомендует выбирать количество корзин с учетом ожидаемого количества различных значений ключа; `sys.dm_db_xtp_hash_index_stats` предназначено для анализа этого решения.

# 23. Сравнение SCHEMA_AND_DATA и SCHEMA_ONLY

Получить информацию:

```sql
SELECT
    name,
    is_memory_optimized,
    durability_desc
FROM sys.tables
WHERE
    name IN
    (
        'EventsMemory',
        'SessionCache'
    );
```

Сравнить:

```text
EventsMemory      SCHEMA_AND_DATA
SessionCache      SCHEMA_ONLY
```

`SCHEMA_ONLY` сохраняет определение таблицы, но данные такой таблицы не предназначены для восстановления после перезапуска или перехода базы через failover. `SCHEMA_AND_DATA` сохраняет и структуру, и данные.

Перезапускать общий или производственный экземпляр SQL Server ради этого эксперимента не требуется.

Если используется полностью изолированная лабораторная машина и преподаватель разрешил перезапуск экземпляра, можно отдельно проверить фактическое поведение после перезапуска.

# 27. Создание обычной интерпретируемой процедуры

Создать обычную процедуру:

```sql
CREATE PROCEDURE App.usp_InsertEventsInterpreted
    @RowsCount INT
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @Counter INT = 1;

    WHILE @Counter <= @RowsCount
    BEGIN
        INSERT INTO Operations.EventQueueInterpreted
        (
            WorkerId,
            EventType,
            CreatedAt,
            Payload
        )
```

# Подсказки по ключевым частям

Memory-optimized таблица не означает, что SQL Server полностью перестает использовать диск. Для долговечной таблицы с:

```sql
DURABILITY = SCHEMA_AND_DATA
```

основное рабочее представление данных находится в памяти, но устойчивое хранение необходимо для восстановления состояния после перезапуска.

Поэтому утверждение:

```text
In-Memory = данные вообще никогда не записываются на диск
```

некорректно.

Для:

```sql
DURABILITY = SCHEMA_ONLY
```

ситуация другая. Сохраняется структура объекта, но сами данные рассматриваются как недолговечные.

Такая таблица подходит для информации, которую допустимо восстановить или заново сформировать.

HASH-индекс следует выбирать прежде всего для запросов точного равенства:

```sql
WHERE EventId = 100
```

или:

```sql
WHERE CustomerId = 500
```

Если требуется:

```sql
WHERE CreatedAt
    BETWEEN @DateFrom AND @DateTo
```

обычный memory-optimized `NONCLUSTERED` индекс обычно лучше соответствует задаче.

Особое значение имеет:

```sql
BUCKET_COUNT
```

HASH-индекс заранее создает определенное количество корзин. При слишком маленьком значении большое количество ключей попадает в одни и те же корзины, образуя длинные цепочки.

При чрезмерном значении резервируется дополнительная память.

Поэтому `BUCKET_COUNT` нельзя бездумно устанавливать:

```text
1000000000
```

для любой таблицы.

Оценивать необходимо количество различных значений и ожидаемый рост.

Для проверки используются:

```sql
sys.dm_db_xtp_hash_index_stats
```

и показатели:

```text
total_bucket_count
empty_bucket_count
avg_chain_length
max_chain_length
```

При выборе между HASH и NONCLUSTERED необходимо учитывать не только количество строк, но и форму запросов.

Высоконагруженная система может иметь таблицу из миллионов строк, но если основная операция — поиск диапазона дат, HASH-индекс не является естественным выбором только потому, что таблица большая.

Нативная процедура:

```sql
WITH NATIVE_COMPILATION
```

не является обычной процедурой с дополнительным флагом «ускорить».

Она компилируется в нативный код и имеет специальные требования к используемому T-SQL и объектам. Microsoft описывает native procedure как средство для производительно-критичных OLTP-операций, особенно при частом выполнении и наличии нескольких действий или процедурной логики.

Необходимо помнить, что native procedure не может обращаться к обычным дисковым таблицам. Если одна процедура должна работать одновременно с большим количеством традиционных disk-based объектов, простое добавление:

```sql
NATIVE_COMPILATION
```

не является решением.

Memory-optimized таблицы при этом можно использовать и без native procedures:

```sql
SELECT ...
FROM Operations.EventsMemory;
```

Это обычный допустимый сценарий.

В этом случае T-SQL остается интерпретируемым, но сама таблица использует In-Memory OLTP.

При тестировании производительности нельзя делать вывод по одной операции:

```sql
INSERT одной строки
```

Преимущество технологии становится более понятным на частых конкурентных OLTP-операциях и больших сериях коротких транзакций.

Локальный тест с одним подключением DBeaver не полностью воспроизводит высоконагруженную рабочую систему.

Поэтому вывод:

```text
у меня INSERT занял 20 мс вместо 25 мс,
значит In-Memory быстрее на 20%
```

будет недостаточно обоснованным.

Нужно выполнить несколько запусков, использовать одинаковые данные и сравнивать сопоставимые операции.

Также необходимо учитывать стоимость памяти.

Обычная дисковая таблица может быть намного больше объема доступной RAM, а для In-Memory OLTP планирование памяти становится важной частью архитектуры.

Используйте:

```sql
sys.dm_db_xtp_table_memory_stats
```

для контроля реального потребления памяти объектами In-Memory OLTP.

# Советы по улучшению работы

Не переносите таблицу в In-Memory OLTP только потому, что она большая. Размер таблицы сам по себе не определяет, что memory-optimized хранение будет лучшим решением.

В первую очередь необходимо искать таблицы с высокой конкурентной OLTP-нагрузкой, большим количеством коротких операций и проблемами традиционной блокировочной архитектуры.

Не используйте HASH для всех индексов. HASH хорошо соответствует точному поиску, но плохо заменяет диапазонный индекс.

Не выбирайте `BUCKET_COUNT` случайным образом. После загрузки данных обязательно проверяйте:

```sql
sys.dm_db_xtp_hash_index_stats
```

Если средние и максимальные цепочки становятся большими, индекс требует анализа.

Не используйте `SCHEMA_ONLY` для данных, потеря которых приведет к нарушению бизнес-процесса.

Например, постоянные финансовые операции или заказы нельзя превращать в недолговечные данные только ради производительности.

При сравнении обычной и нативной процедуры используйте одинаковые таблицы, одинаковые объемы данных и одинаковую бизнес-логику. Иначе результаты невозможно корректно сравнить.

Не делайте вывод по одному запуску. Выполняйте тест несколько раз.

Не очищайте кеши SQL Server между каждым экспериментом без понимания того, что именно вы измеряете. In-Memory OLTP по своей природе не исследуется теми же методами кеширования страниц, что традиционные disk-based таблицы.

Не следует ожидать, что фактический выигрыш будет одинаковым на каждом компьютере. Производительность зависит от объема RAM, процессора, количества параллельных соединений, размера данных, структуры индексов и характера запросов.

Нативная процедура особенно интересна там, где операция выполняется очень часто. Для редкого административного запроса сложность отдельной native procedure может быть неоправданной.

Не пытайтесь перенести весь SQL-код приложения в нативные процедуры. Поддерживается не весь набор возможностей обычного T-SQL, а сами native procedures ориентированы прежде всего на производительно-критичные OLTP-сценарии.

Для высоконагруженной системы рассматривайте In-Memory OLTP как отдельный архитектурный инструмент, а не как универсальную кнопку ускорения.

Итоговая работа считается качественно выполненной, если выбор между disk-based и memory-optimized хранением подтвержден измерениями, правильно выбраны `SCHEMA_ONLY` или `SCHEMA_AND_DATA`, HASH-индексы спроектированы с учетом кардинальности ключей, потребление памяти проверено через DMV, а преимущество или отсутствие преимущества `NATIVE_COMPILATION` подтверждено собственным тестом.
