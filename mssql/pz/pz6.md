# Практическое задание

# Разработка оптимальной стратегии индексирования в MS SQL Server

## Цель

Разработать и обосновать стратегию индексирования для базы данных MS SQL Server на основании реальной нагрузки, планов выполнения запросов, статистики использования индексов и данных Query Store.

В ходе практической работы необходимо перейти от подхода «создадим индекс для конкретного запроса» к полноценному анализу рабочей нагрузки. Необходимо определить наиболее важные запросы системы, найти проблемные операции, подобрать минимально достаточный набор индексов, сравнить несколько вариантов индексирования, проверить влияние индексов на операции чтения и изменения данных и удалить структуры, которые не дают практической пользы.

Дополнительно необходимо использовать средства SQL Server для анализа и сопровождения индексной стратегии: фактические планы выполнения, системные представления, Database Engine Tuning Advisor и Query Store.

Основной результат работы — не максимальное количество созданных индексов, а аргументированная стратегия, в которой для каждого индекса понятно, какую нагрузку он обслуживает и какую стоимость его поддержание создает для системы.

# Задание

Необходимо подготовить базу данных, имитирующую работу системы с постоянным потоком операций.

Можно продолжить работу с базой данных из предыдущего практического задания либо создать отдельную базу.

Рекомендуемая предметная область — система обработки заказов интернет-магазина или корпоративной системы продаж.

Основная таблица должна содержать не менее 100 000 строк. Для более показательного анализа рекомендуется использовать от 300 000 до 1 000 000 строк.

В базе должны присутствовать запросы разного характера: точечный поиск, диапазонная выборка, соединения таблиц, сортировка, агрегирование, выборка по нескольким условиям и операции изменения данных.

| Индекс                  | Ключевые столбцы      | INCLUDE                 | Для каких запросов |

| IX_Orders_Customer_Date | CustomerId, OrderDate | Status, TotalAmount     | Q2, Q3, Q7         |

# 10. Проанализировать использование индексов

Использовать динамическое системное представление:

```sql
SELECT
    OBJECT_NAME(s.object_id) AS tablename,
    i.name AS indexname,
    s.user_seeks,
    s.user_scans,
    s.user_lookups,
    s.user_updates
FROM sys.dm_db_index_usage_stats AS s
INNER JOIN sys.indexes AS i
    ON
        i.object_id = s.object_id
        AND i.index_id = s.index_id
WHERE
    s.database_id = DB_ID()
    AND s.object_id = OBJECT_ID('Sales.Orders')
ORDER BY i.name;
```

Перед анализом несколько раз выполнить рабочие запросы.

Проанализировать показатели:

```text
user_seeks
user_scans
user_lookups
user_updates
```

Найти индексы, которые активно используются для чтения.

Отдельно обратить внимание на индексы, у которых много `user_updates`, но практически отсутствуют `user_seeks` и `user_scans`.

Необходимо учитывать, что статистика из `sys.dm_db_index_usage_stats` не является постоянной и может сбрасываться после перезапуска SQL Server или других событий.

# 13. Исследовать физическую статистику индексов

Использовать:

```sql
SELECT
    OBJECT_NAME(ips.object_id) AS tablename,
    i.name AS indexname,
    ips.index_type_desc,
    ips.avg_fragmentation_in_percent,
    ips.page_count
FROM
    sys.dm_db_index_physical_stats(
        DB_ID(),
        OBJECT_ID('Sales.Orders'),
        NULL,
        NULL,
        'LIMITED'
    ) AS ips
INNER JOIN sys.indexes AS i
    ON
        i.object_id = ips.object_id
        AND i.index_id = ips.index_id
ORDER BY ips.avg_fragmentation_in_percent DESC;
```

Зафиксировать:

```text
avg_fragmentation_in_percent
page_count
```

Необходимо учитывать не только процент фрагментации, но и размер индекса. Высокий процент фрагментации у индекса, состоящего из нескольких страниц, сам по себе не является серьезной причиной для обслуживания.

# 18. Найти запросы с несколькими планами

Используя Query Store, найти запросы, для которых SQL Server сохранял более одного плана.

Например:

```sql

    q.query_id,
    COUNT(DISTINCT p.plan_id) AS planscount
FROM sys.query_store_query AS q
INNER JOIN sys.query_store_plan AS p
    ON q.query_id = p.query_id
GROUP BY q.query_id
HAVING COUNT(DISTINCT p.plan_id) > 1
ORDER BY planscount DESC;
```

# 20. Проверить рекомендации отсутствующих индексов

Получить информацию из динамических представлений отсутствующих индексов.

Например:

```sql
SELECT TOP (20)
    migs.user_seeks,
    migs.user_scans,
    migs.avg_total_user_cost,
    migs.avg_user_impact,
    mid.statement,
    mid.equality_columns,
    mid.inequality_columns,
    mid.included_columns
FROM sys.dm_db_missing_index_group_stats AS migs
INNER JOIN sys.dm_db_missing_index_groups AS mig
    ON migs.group_handle = mig.index_group_handle
INNER JOIN sys.dm_db_missing_index_details AS mid
    ON mig.index_handle = mid.index_handle
WHERE mid.database_id = DB_ID()
ORDER BY
    migs.avg_user_impact DESC;
```

Проанализировать рекомендации.

Не создавать каждый предложенный индекс.

Проверить, не перекрывается ли предлагаемая структура уже существующими индексами.

Сравнить рекомендации:

```text
плана выполнения;
DMV отсутствующих индексов;
Database Engine Tuning Advisor;
собственного анализа;
Query Store.
```

На основании всех источников определить итоговую индексную стратегию.

# Подсказки по ключевым частям

Стратегия индексирования должна начинаться не с команды `CREATE INDEX`, а с анализа рабочей нагрузки. Индекс существует для обслуживания запросов, поэтому сначала необходимо определить, какие запросы являются действительно важными.

В высоконагруженной базе нельзя оптимизировать каждый запрос независимо. Индекс, который ускоряет один запрос, становится дополнительной структурой для всех операций `INSERT`, `UPDATE` и `DELETE`.

Например, если таблица имеет десять некластеризованных индексов, вставка новой строки потенциально требует изменения не только основной структуры таблицы, но и каждого из соответствующих индексов.

Именно поэтому количество индексов не должно быть максимальным. Оно должно быть минимально достаточным.

При анализе плана выполнения обязательно сравнивайте предполагаемое и фактическое количество строк. Большая разница между ними может говорить о проблемах со статистикой или особенностях распределения данных.

Не рассматривайте процент стоимости оператора в графическом плане как абсолютную характеристику производительности. Эта стоимость является оценкой оптимизатора внутри конкретного плана.

Обязательно анализируйте:

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
```

Особенно важны логические чтения.

Если запрос выполняется за:

```text
30 мс
```

до оптимизации и:

```text
20 мс
```

после нее, разница на локальном компьютере может быть нестабильной.

Если при этом количество логических чтений сократилось с:

```text
15 000
```

до:

```text
40
```

изменение значительно более показательно.

При анализе `Key Lookup` необходимо учитывать количество выполнений. Один `Key Lookup` практически не является проблемой. Десятки тысяч обращений могут существенно увеличить стоимость запроса.

`INCLUDE` следует использовать для покрытия запросов, но нельзя без необходимости помещать туда все столбцы таблицы. Широкий индекс занимает больше места и дороже обслуживается.

Database Engine Tuning Advisor необходимо воспринимать как источник рекомендаций, а не как систему, автоматически принимающую архитектурные решения.

Аналогично необходимо относиться к рекомендациям отсутствующих индексов. SQL Server может предложить несколько очень похожих индексов для разных запросов. Задача администратора или разработчика базы данных — объединить требования и построить более рациональную структуру.

Query Store необходимо использовать для анализа поведения запросов во времени. Это особенно важно при поиске регрессий, когда запрос раньше выполнялся быстро, а после изменения данных, статистики, индексов или плана начал выполняться значительно хуже.

# Советы по улучшению работы

Не начинайте оптимизацию с автоматического создания всех индексов, которые появляются в рекомендациях плана выполнения. Один запрос может предложить индекс, полезный именно для него, но невыгодный для системы в целом.

При анализе высоконагруженной системы учитывайте частоту выполнения запросов. Оптимизация запроса, выполняющегося один раз в сутки, с 500 мс до 50 мс может иметь меньшую практическую ценность, чем уменьшение времени запроса с 20 до 10 мс, если второй запрос выполняется несколько миллионов раз в сутки.

Старайтесь объединять требования нескольких запросов. Вместо нескольких похожих индексов иногда можно разработать один составной индекс, который эффективно обслуживает целую группу операций.

Не рассматривайте индекс в изоляции от остальных структур. После создания нового индекса необходимо проверить, не сделал ли он другой индекс избыточным.

При работе с Query Store анализируйте динамику. Важен не только самый медленный запрос прямо сейчас, но и запросы, производительность которых ухудшилась относительно предыдущих периодов.

Не выполняйте `REBUILD` всех индексов по расписанию только по факту существования таблиц. Обслуживание индексов само создает нагрузку на процессор, память, дисковую подсистему и журнал транзакций. Решение должно основываться на состоянии конкретной структуры и характеристиках нагрузки.

При анализе рекомендаций отсутствующих индексов обращайте внимание на сходство предлагаемых ключей. Если система предлагает:

```text
(CustomerId)

(CustomerId, OrderDate)

(CustomerId, OrderDate) INCLUDE (Status)

(CustomerId, OrderDate) INCLUDE (Status, TotalAmount)
```

не следует автоматически создавать четыре индекса. Необходимо определить, можно ли обслужить рабочую нагрузку одной или двумя структурами.

В итоговой работе каждый индекс должен иметь конкретное обоснование. Недостаточно написать «индекс ускоряет запрос». Необходимо показать, какой запрос он обслуживает, как изменился план выполнения, насколько уменьшились логические чтения, требуется ли `Key Lookup`, сколько места занимает индекс и какую нагрузку он добавляет операциям изменения данных.

Итоговая стратегия считается успешной, если после оптимизации критичные запросы используют рациональные планы выполнения, количество логических чтений сокращено, отсутствуют очевидно дублирующие индексы, а сама индексная структура остается достаточно компактной для рабочей нагрузки.
