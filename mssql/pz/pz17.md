# Практическое задание

# Совместный доступ к данным в MS SQL Server

## Цель

Исследовать механизм совместного доступа к данным в MS SQL Server, научиться управлять явными транзакциями, наблюдать блокировки между параллельными соединениями, определять источник блокировки, анализировать типы и режимы блокировок и исследовать влияние уровней изоляции на параллельную работу пользователей.

В ходе практической работы необходимо создать отдельную тестовую базу данных, работать одновременно минимум в двух независимых соединениях DBeaver, моделировать конкурентное чтение и изменение одних и тех же данных, исследовать `COMMIT` и `ROLLBACK`, наблюдать ожидания блокировок через системные представления SQL Server, воспроизвести грязное чтение, неповторяемое чтение и фантомные строки, проверить уровни `READ UNCOMMITTED`, `READ COMMITTED`, `REPEATABLE READ`, `SERIALIZABLE` и `SNAPSHOT`, исследовать блокировку обновления и создать контролируемую взаимоблокировку.

Особое внимание необходимо уделить тому, что блокировка сама по себе не является ошибкой. Это один из основных механизмов, с помощью которого SQL Server обеспечивает согласованность данных при параллельной работе множества транзакций.

Основной результат работы — научиться отвечать на практические вопросы:

```text
Какая транзакция удерживает ресурс?

Какая сессия ожидает?

Что именно заблокировано?

Какой режим блокировки используется?

Как долго существует транзакция?

Какой запрос стал причиной блокировки?

Почему операция ожидает?

Как выбранный уровень изоляции влияет на параллельность?
```

# Задание

Для выполнения работы необходимо использовать минимум три независимых SQL-редактора или подключения.

Условно они будут называться:

```text
Сессия A — первая рабочая транзакция.

Сессия B — конкурентная транзакция.

Сессия Monitor — диагностика блокировок.
```

В DBeaver важно убедиться, что это действительно отдельные физические соединения SQL Server, а не несколько редакторов, использующих одно соединение.

# 2. Создание таблицы счетов

```sql
CREATE TABLE Bank.Accounts
(
    AccountId INT
        CONSTRAINT PK_Accounts
        PRIMARY KEY CLUSTERED,

    CustomerName NVARCHAR(200) NOT NULL,

    Balance DECIMAL(14,2) NOT NULL,

    Status VARCHAR(20) NOT NULL
        CONSTRAINT DF_Accounts_Status
        DEFAULT 'Active',

    ModifiedAt DATETIME2 NOT NULL
        CONSTRAINT DF_Accounts_ModifiedAt
        DEFAULT SYSDATETIME(),

    CONSTRAINT CK_Accounts_Balance
        CHECK (Balance >= 0),

    CONSTRAINT CK_Accounts_Status
        CHECK
        (
            Status IN
            (
                'Active',
                'Blocked',
                'Closed'
            )
        )
);
GO
```

# 3. Создание таблицы операций

```sql
CREATE TABLE Bank.Transactions
(
    TransactionId BIGINT IDENTITY(1,1)
        CONSTRAINT PK_Transactions
        PRIMARY KEY CLUSTERED,

    AccountId INT NOT NULL,

    OperationType VARCHAR(20) NOT NULL,

    Amount DECIMAL(14,2) NOT NULL,

    CreatedAt DATETIME2 NOT NULL
        CONSTRAINT DF_Transactions_CreatedAt
        DEFAULT SYSDATETIME(),

    CONSTRAINT FK_Transactions_Accounts
        FOREIGN KEY (AccountId)
        REFERENCES Bank.Accounts(AccountId),

    CONSTRAINT CK_Transactions_OperationType
        CHECK
        (
            OperationType IN
            (
                'Deposit',
                'Withdrawal'
            )
        ),

    CONSTRAINT CK_Transactions_Amount
        CHECK (Amount > 0)
);
GO
```

# Подсказки по ключевым частям

Транзакция — это логическая единица работы. Если несколько изменений должны либо завершиться совместно, либо совместно отмениться, их необходимо рассматривать как одну транзакцию.

Простейший шаблон:

```sql
BEGIN TRANSACTION;

-- Изменения.

COMMIT TRANSACTION;
```

Если операция должна быть отменена:

```sql
ROLLBACK TRANSACTION;
```

Пока транзакция не завершена, она может продолжать удерживать блокировки.

Именно поэтому забытая открытая транзакция является одной из классических причин длительных блокировок.

Важно различать:

```text
активный запрос;

активную транзакцию.
```

Сессия может находиться в состоянии:

```text
sleeping
```

но при этом иметь:

```text
open_transaction_count > 0
```

и удерживать блокировки.

Для диагностики блокировок одним из основных источников является:

```sql
sys.dm_tran_locks
```

Он показывает не SQL-код, а блокировки и запросы блокировок.

Важные поля:

```text
request_session_id

resource_type

request_mode

request_status
```

Например:

```text
GRANT
```

означает, что блокировка предоставлена.

```text
WAIT
```

означает ожидание.

Основные режимы, которые необходимо понимать в рамках работы:

```text
S — Shared.

X — Exclusive.

U — Update.

IS — Intent Shared.

IX — Intent Exclusive.
```

Shared lock используется при блокировочном чтении.

Exclusive lock требуется для изменения ресурса.

Update lock помогает управлять ситуацией, когда транзакция сначала читает строку с намерением позже ее изменить.

Intent locks показывают намерение блокировать ресурсы более низкого уровня и позволяют SQL Server эффективнее управлять иерархией:

```text
таблица;
страница;
ключ или строка.
```

Не следует воспринимать большое количество блокировок как автоматическую проблему.

В SQL Server блокировки создаются постоянно и являются штатной частью конкурентной работы.

Проблемой становится ситуация, когда блокировка приводит к неприемлемому времени ожидания или формирует длинную blocking chain.

Необходимо отличать:

```text
blocking

deadlock.
```

Blocking:

```text
A удерживает ресурс.

B ожидает ресурс A.
```

Если A завершится, B продолжит работу.

Deadlock:

```text
A удерживает ресурс 1 и ожидает ресурс 2.

B удерживает ресурс 2 и ожидает ресурс 1.
```

Ни одна транзакция не может продолжить работу.

SQL Server обнаруживает такой цикл и выбирает одну транзакцию жертвой.

Ошибка:

```text
1205
```

не означает повреждение базы данных.

Приложение обычно должно быть готово безопасно повторить транзакцию, если операция допускает повтор.

Одним из наиболее простых способов предотвращения deadlock является единый порядок доступа к ресурсам.

Если все операции всегда изменяют:

```text
Account 1,
потом Account 2,
```

риск цикла ниже, чем если разные части приложения используют противоположный порядок.

Уровень изоляции определяет баланс между:

```text
согласованностью;

параллельностью;

блокировками;

видимостью изменений.
```

`READ UNCOMMITTED` допускает грязные чтения.

Это означает, что запрос может увидеть данные, которые позже вообще будут отменены:

```sql
ROLLBACK;
```

Поэтому:

```sql
WITH (NOLOCK)
```

нельзя рассматривать как универсальное средство повышения производительности.

Запрос действительно может меньше ждать блокирующих транзакций, но ценой становится ослабление гарантий чтения.

Для финансовых расчетов, отчетов остатков и других задач, требующих согласованности, это может быть недопустимо.

`READ COMMITTED` является стандартным уровнем во многих конфигурациях SQL Server.

В классическом блокировочном варианте запрос не должен читать незакоммиченные изменения другой транзакции.

`REPEATABLE READ` защищает уже прочитанные строки от изменения другими транзакциями до завершения текущей транзакции.

`SERIALIZABLE` усиливает защиту диапазонов и препятствует появлению фантомных строк, подходящих под ранее выполненное условие.

Это повышает согласованность, но потенциально снижает параллельность.

`SNAPSHOT` использует версии строк и позволяет транзакции работать с согласованным состоянием данных без обычной shared-lock модели для чтения.

`READ_COMMITTED_SNAPSHOT` меняет реализацию `READ COMMITTED`: чтения могут использовать версии строк вместо ожидания writers.

Однако row versioning не означает исчезновение всех блокировок.

Операции изменения:

```text
UPDATE;
INSERT;
DELETE;
```

по-прежнему должны координировать конкурентный доступ.

Также сохраняются schema locks и другие категории блокировок.

Важный диагностический запрос:

```sql
SELECT
    session_id,
    blocking_session_id,
    wait_type,
    wait_resource
FROM sys.dm_exec_requests;
```

Он позволяет быстро определить непосредственного блокировщика.

Однако реальная blocking chain может содержать несколько уровней.

Например:

```text
Session 70 блокирует 71.

Session 71 блокирует 72.

Session 72 блокирует 73.
```

В таком случае исправление сессии 72 не устранит корневую причину. Необходимо найти head blocker.

`LOCK_TIMEOUT` позволяет ограничить время ожидания блокировки на уровне сессии.

Например:

```sql
SET LOCK_TIMEOUT 3000;
```

задает три секунды.

Это не освобождает чужую блокировку. Оно только определяет, сколько текущая сессия готова ее ждать.

`NOWAIT` предназначен для сценария, когда запрос не должен ждать занятый ресурс.

`READPAST` может пропускать заблокированные строки. Такое поведение иногда полезно в реализации конкурентных очередей, но опасно для задач, где требуется полный набор данных.

Lock hints:

```text
NOLOCK;
UPDLOCK;
HOLDLOCK;
ROWLOCK;
READPAST;
NOWAIT.
```

не следует использовать автоматически.

Каждый hint изменяет стандартное поведение оптимизатора или механизма блокировок и должен иметь измеримую причину.

При высокой конкурентной нагрузке продолжительность транзакции часто важнее количества строк SQL-кода.

Плохая транзакция может выглядеть так:

```text
BEGIN TRANSACTION;

изменить данные;

вызвать внешний сервис;

ждать пользователя;

выполнить сложный отчет;

изменить еще данные;

COMMIT.
```

Все это время ресурсы могут оставаться заблокированными.

В высоконагруженной системе транзакции обычно стараются делать:

```text
короткими;

предсказуемыми;

с минимальным набором необходимых ресурсов.
```

При анализе блокировок необходимо искать не только заблокированный запрос, но и причину того, почему блокирующая транзакция еще не завершилась.

Иногда проблема заключается не в самом `UPDATE`, а в том, что после него приложение несколько минут не отправляет:

```sql
COMMIT
```

или:

```sql
ROLLBACK.
```

# Советы по улучшению работы

Не исправляйте блокировки автоматическим добавлением:

```sql
WITH (NOLOCK)
```

во все запросы.

Это не устранение причины блокировки, а изменение гарантий чтения.

Сначала необходимо определить head blocker, продолжительность транзакции и причину удержания ресурса.

Не используйте:

```text
KILL session_id
```

как первый способ борьбы с блокировкой. Завершение сессии может инициировать длительный rollback большой транзакции и само по себе не объясняет первопричину.

Для учебной базы `KILL` можно исследовать отдельно, но в данной работе достаточно диагностировать и завершать собственные транзакции штатно.

Старайтесь сохранять одинаковый порядок обращения к ресурсам во всех транзакциях. Это один из наиболее эффективных способов уменьшения числа deadlock.

Не размещайте внутри длительной транзакции пользовательский ввод, сетевые запросы и другие операции с непредсказуемым временем завершения.

Не делайте транзакцию шире, чем необходимо для обеспечения атомарности.

Не полагайтесь только на `sys.dm_exec_requests`. Блокирующая сессия может находиться в состоянии `sleeping` и не иметь текущего request, но при этом удерживать открытую транзакцию.

Поэтому при расследовании блокировок полезно совместно анализировать:

```sql
sys.dm_exec_requests

sys.dm_exec_sessions

sys.dm_tran_locks

sys.dm_tran_active_transactions
```

При выборе уровня изоляции не используйте правило:

```text
чем выше уровень, тем лучше.
```

Более строгая изоляция дает больше гарантий, но обычно снижает степень конкурентности.

Не используйте `SERIALIZABLE` для всех операций без необходимости.

Не включайте `READ_COMMITTED_SNAPSHOT` в реальной базе только ради эксперимента без оценки всей нагрузки. Это изменение поведения базы данных и использование row versioning должно быть архитектурным решением.

В рамках данной практики такие изменения выполняются только на отдельной лабораторной базе.

Не считайте snapshot isolation способом избавиться от всех блокировок. Writers по-прежнему конфликтуют с writers, а некоторые типы блокировок вообще не относятся к обычному чтению строк.

При разработке прикладной системы учитывайте ошибку deadlock `1205`. Даже хорошо спроектированная система при высокой параллельности может столкнуться с deadlock, поэтому короткие идемпотентные транзакции нередко реализуют с ограниченным механизмом retry.

Итоговая работа считается качественно выполненной, если блокировка не просто создана, а полностью диагностирована: определены обе сессии, режимы блокировок, ожидаемый ресурс, открытая транзакция и причина ожидания; исследованы различия уровней изоляции; создан и устранен deadlock; показано влияние row versioning на совместный доступ.
