# Практическое задание

# Проектирование и реализация пользовательских функций в MS SQL Server

## Цель

Спроектировать и реализовать пользовательские функции в MS SQL Server для повторного использования вычислений и запросов, исследовать различия между скалярными и табличными функциями, проверить особенности их использования внутри SQL-запросов и определить случаи, когда вместо пользовательской функции целесообразнее применять представление, вычисляемый столбец, `CASE`, `APPLY`, хранимую процедуру или встроенные средства SQL Server.

В рамках практической работы необходимо создать базу данных для системы продаж, реализовать несколько скалярных функций, inline table-valued functions и multi-statement table-valued functions, использовать функции в `SELECT`, `WHERE`, `JOIN` и `APPLY`, исследовать планы выполнения и сравнить пользовательские функции с альтернативными механизмами решения тех же задач.

Основной результат работы — научиться выбирать тип функции исходя не только из удобства повторного использования кода, но и из характера данных, требований к производительности и возможностей оптимизатора SQL Server.

(
    @Quantity INT,
    @UnitPrice DECIMAL(12,2)
)
RETURNS DECIMAL(18,2)
AS

# 27. Создание multi-statement table-valued function

Создать функцию, которая возвращает сводную информацию о заказах клиента.

Например:

```sql
CREATE FUNCTION App.ufn_GetCustomerOrderSummary
(
    @CustomerId INT
)
RETURNS @Result TABLE
(
    Status VARCHAR(30),
    OrdersCount INT,
    TotalAmount DECIMAL(18,2)
)
AS
BEGIN

    INSERT INTO @Result
    (
        Status,
        OrdersCount,
        TotalAmount
    )
    SELECT
        o.Status,
        COUNT(DISTINCT o.OrderId),
        SUM
        (
            oi.Quantity
            * oi.UnitPrice
            * (1 - oi.DiscountPercent / 100.0)
        )
    FROM Sales.Orders AS o
    INNER JOIN Sales.OrderItems AS oi
        ON oi.OrderId = o.OrderId
    WHERE o.CustomerId = @CustomerId
    GROUP BY o.Status;

    RETURN;
END;
GO
```

Проверить:

```sql
SELECT *
FROM App.ufn_GetCustomerOrderSummary(1);
```

# Подсказки по ключевым частям

Скалярная функция возвращает одно значение.

Например:

```sql
SELECT App.ufn_CalculateLineAmount(
    5,
    1000
);
```

Результатом будет одно значение.

Скалярные функции удобны для инкапсуляции повторяемой логики вычислений, но не следует автоматически переносить в функцию каждое выражение.

Если выражение используется один раз:

```sql
Quantity * UnitPrice
```

создание отдельной функции может только усложнить код.

Если же одна и та же прикладная формула используется в большом количестве запросов и ее необходимо централизовать, пользовательская функция может быть оправдана.

При этом необходимо анализировать планы выполнения. Современные версии SQL Server способны встраивать некоторые скалярные пользовательские функции в запрос, но эта оптимизация применяется не ко всем функциям и не при любых условиях.

Поэтому нельзя рассуждать так:

```text
SQL Server всегда встроит скалярную функцию.
```

Проверяется конкретный фактический план.

Inline table-valued function работает иначе.

Она имеет форму:

```sql
CREATE FUNCTION ...
RETURNS TABLE
AS
RETURN
(
    SELECT ...
);
```

Такая функция особенно удобна, когда необходимо получить параметризованный набор строк.

Например:

```sql
SELECT *
FROM App.ufn_GetCustomerOrders(15);
```

В отличие от представления, функция может принять:

```text
CustomerId
```

и сформировать набор данных именно для указанного клиента.

Результат табличной функции можно использовать как источник данных:

```sql
FROM App.ufn_GetCustomerOrders(15)
```

Также его можно соединять с другими объектами.

Особенно полезен оператор:

```sql
APPLY
```

когда параметры функции зависят от строки внешнего запроса.

Например:

```sql
FROM Sales.Customers AS c
CROSS APPLY
    App.ufn_GetCustomerOrders(c.CustomerId) AS o
```

Здесь для каждой строки внешнего источника передается свой `CustomerId`.

`CROSS APPLY` не возвращает строку внешней таблицы, если внутренняя функция ничего не вернула.

`OUTER APPLY` сохраняет такую строку аналогично логике внешнего соединения.

Multi-statement table-valued function использует возвращаемую табличную переменную:

```sql
RETURNS @Result TABLE
```

и внутри выполняет:

```sql
INSERT INTO @Result
```

Такой вариант позволяет реализовать более сложную пошаговую логику.

Однако его не следует выбирать автоматически.

Если результат можно выразить одним запросом:

```sql
SELECT ...
FROM ...
WHERE ...
```

inline TVF обычно проще и предоставляет оптимизатору более прозрачное представление логики запроса.

Поэтому один из важных экспериментов работы — сравнение:

```text
inline TVF
```

и:

```text
multi-statement TVF.
```

Необходимо смотреть не только время, но и фактический план и оценки количества строк.

Функция не является эквивалентом хранимой процедуры.

Хранимая процедура может использоваться для выполнения серверной операции и может содержать значительно более широкий набор действий.

Функция предназначена прежде всего для вычисления и возврата результата, пригодного для использования внутри выражений или запросов.

Например, функцию можно использовать:

```sql
SELECT *
FROM App.ufn_GetCustomerOrders(1);
```

или:

```sql
SELECT
    App.ufn_CalculateFinalAmount(
        Quantity,
        Unitprice,
        Discountpercent
    )
FROM Sales.Orderitems;
```

Процедура вызывается иначе:

```sql
EXEC App.usp_GetCustomerOrders
    @CustomerId = 1;
```

и не является обычным табличным выражением в предложении `FROM`.

Пользовательская функция также не предназначена для произвольного изменения данных основной базы. Попытка выполнить внутри обычной T-SQL функции операции, изменяющие состояние пользовательских таблиц, должна стать частью практического эксперимента.

Необходимо отдельно понимать отличие пользовательской функции от встроенной функции.

SQL Server уже предоставляет большое количество функций:

```sql
SUM()
AVG()
COUNT()
ROUND()
LEN()
UPPER()
LOWER()
COALESCE()
DATEADD()
DATEDIFF()
SYSDATETIME()
```

Не следует создавать:

```text
ufn_GetCurrentDate
```

только для того, чтобы внутри вызвать:

```sql
SYSDATETIME()
```

без дополнительной прикладной логики.

Также необходимо рассматривать `CASE` как альтернативу простым скалярным функциям.

Если классификация нужна только одному запросу:

```sql
CASE
    WHEN Price < 5000 THEN 'Budget'
    WHEN Price <= 20000 THEN 'Middle'
    ELSE 'Premium'
END
```

она может быть понятнее непосредственно внутри запроса.

Если же классификация является единым бизнес-правилом и используется во множестве мест, отдельная функция может уменьшить дублирование.

Для вычислений, непосредственно являющихся характеристикой строки таблицы, необходимо рассмотреть вычисляемые столбцы.

Например:

```sql
TotalAmount AS (Quantity * UnitPrice)
```

может быть более естественным решением, чем постоянный вызов функции для получения того же значения.

Для непараметризованного набора данных можно использовать представление.

Для параметризованного табличного выражения более естественным вариантом может быть inline TVF.

Для серверной операции, которая изменяет данные, использует транзакцию, возвращает несколько результирующих наборов или выполняет сложную последовательность действий, чаще следует рассматривать хранимую процедуру.

Поэтому правильный вопрос при проектировании звучит не так:

```text
Как написать функцию?
```

а так:

```text
Действительно ли здесь функция является лучшим механизмом?
```

# Советы по улучшению работы

Не создавайте пользовательскую функцию только для сокращения одной строки SQL-кода. Отдельный объект базы данных оправдан тогда, когда логика действительно повторяется, имеет самостоятельный смысл и ее централизованное хранение улучшает сопровождение системы.

Если задача решается выражением:

```sql
Quantity * UnitPrice
```

и используется только в одном месте, отдельная функция может оказаться лишней.

Если формула сложная, используется десятками отчетов и должна изменяться централизованно, функция становится значительно более оправданной.

При работе с наборами строк в первую очередь рассматривайте inline table-valued function. Она особенно полезна для параметризованных выборок и хорошо сочетается с реляционной моделью запросов SQL Server.

Не выбирайте multi-statement TVF только потому, что внутри нее удобнее писать последовательный код. Если логика выражается одним `SELECT`, сначала попробуйте inline TVF и сравните планы.

Не воспринимайте скалярную функцию как бесплатный вызов. Если функция используется в запросе, обрабатывающем сотни тысяч или миллионы строк, обязательно исследуйте фактический план.

Современный SQL Server может оптимизировать часть скалярных функций через механизм scalar UDF inlining, но решение зависит от конкретной функции и конфигурации. Проверять необходимо фактическое поведение, а не предполагать его.

Не скрывайте за функцией выражение, которое мешает эффективно использовать индекс, не проведя измерения.

Например, запрос:

```sql
WHERE App.ufn_GetSomeValue(ColumnName) = ...
```

может иметь другой профиль оптимизации, чем условие непосредственно по индексируемому столбцу.

При работе с производительностью всегда сравнивайте:

```text
Logical Reads
CPU Time
Elapsed Time
Estimated Rows
Actual Rows
операторы фактического плана
```

Не делайте вывод по одному времени выполнения.

Первый и второй запуск одного запроса могут отличаться из-за кеширования данных и планов.

Используйте пользовательские функции там, где они действительно повышают выразительность модели.

Используйте представление, когда нужен повторяемый непараметризованный набор данных.

Используйте inline TVF, когда нужен параметризованный табличный результат.

Используйте вычисляемый столбец, когда вычисляемое значение является естественной характеристикой строки таблицы.

Используйте `CASE`, когда условная логика проста и локальна для конкретного запроса.

Используйте встроенную функцию SQL Server, если она уже решает поставленную задачу.

Используйте хранимую процедуру, когда требуется выполнить операцию, изменить данные, использовать транзакционную логику или предоставить отдельный серверный интерфейс выполнения.

Итоговая работа считается качественно выполненной, если функции не просто созданы и вызваны, а проведено сравнение разных типов функций, исследованы фактические планы выполнения и для каждой существенной задачи выбран механизм, соответствующий характеру операции и требованиям к производительности.
