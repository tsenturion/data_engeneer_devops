# Практическое задание

# Хранение и запрос двоичных и текстовых документов в SQL Server

## Цель

Спроектировать и реализовать систему хранения неструктурированных данных в MS SQL Server, исследовать различные способы хранения текстовых и бинарных документов, настроить FILESTREAM для размещения содержимого файлов вне обычных страниц базы данных и реализовать полнотекстовый поиск по документам.

В рамках практической работы необходимо создать библиотеку документов, в которой будут храниться метаданные файлов, обычный текст, бинарное содержимое и FILESTREAM-данные. Необходимо загрузить документы с файловой системы, получить их обратно из SQL Server, проверить размер и свойства бинарных данных, настроить полнотекстовый каталог и полнотекстовый индекс, выполнить поиск через `CONTAINS`, `FREETEXT`, `CONTAINSTABLE` и `FREETEXTTABLE`, исследовать ранжирование результатов и работу различных типов запросов.

Отдельное внимание необходимо уделить тому, что SQL Server может хранить бинарное значение двумя принципиально разными способами. Обычный `VARBINARY(MAX)` хранит значение как часть данных SQL Server, а `VARBINARY(MAX) FILESTREAM` позволяет хранить BLOB-содержимое в файловой системе NTFS под контролем SQL Server. FILESTREAM-данные при этом остаются частью транзакционной модели базы данных.

Практическая работа должна показать полный цикл:

```text
файл на файловой системе

загрузка содержимого

VARBINARY(MAX) или FILESTREAM

метаданные документа

полнотекстовая индексация

полнотекстовый запрос

получение найденного документа
```

# 1. Проверка платформы SQL Server

Перед началом работы определить операционную систему сервера SQL Server.

Выполнить:

```sql
SELECT
    host_platform,
    host_distribution,
    host_release
FROM sys.dm_os_host_info;
```

Если результат:

```text
Windows
```

можно выполнять все этапы работы, включая FILESTREAM.

Если SQL Server работает на Linux, этапы с FILESTREAM необходимо пропустить и выполнить вариант с обычным `VARBINARY(MAX)`.

В SQL Server 2025 на Linux FILESTREAM и FileTable не поддерживаются.

# 2. Проверка полнотекстового поиска

Проверить, установлен ли компонент Full-Text Search:

```sql
SELECT
    FULLTEXTSERVICEPROPERTY
    (
        'IsFullTextInstalled'
    ) AS IsFullTextInstalled;
```

Ожидаемый результат:

```text
1
```

Если возвращается:

```text

```

компонент Full-Text Search не установлен.

В этом случае его необходимо добавить средствами установки SQL Server.

Полнотекстовый поиск является дополнительным компонентом SQL Server Database Engine.

# 4. Уровни доступа FILESTREAM

Для лабораторной работы необходимо понимать уровни:

```text
0 — FILESTREAM отключен.

1 — разрешен доступ через T-SQL.

2 — T-SQL и Win32 streaming access.

3 — T-SQL, Win32 streaming access и удаленный доступ.
```

Текущая документация SQL Server определяет именно эти уровни `filestream access level`.

Для базовой лабораторной работы достаточно уровня:

```text
1
```

Если дополнительно исследуется файловый доступ, требуется соответствующая настройка Windows и более высокий уровень.

---

# 5. Включение FILESTREAM на Windows

FILESTREAM сначала необходимо разрешить средствами SQL Server Configuration Manager.

В свойствах экземпляра SQL Server включить:

```text
Enable FILESTREAM for Transact-SQL access
```

Если будет исследоваться потоковый файловый доступ:

```text
Enable FILESTREAM for file I/O streaming access
```

После этого в SQL Server выполнить:

```sql
EXEC sp_configure
    'filestream access level',
    2;

RECONFIGURE;
```

Для применения системной настройки FILESTREAM может потребоваться перезапуск службы SQL Server.

# 8. Создание таблицы для обычного текстового хранения

Создать таблицу:

```sql
CREATE TABLE Documents.TextDocuments
(
    DocumentId BIGINT IDENTITY(1,1)
        CONSTRAINT PK_TextDocuments
        PRIMARY KEY CLUSTERED,

    Title NVARCHAR(300) NOT NULL,

    Category NVARCHAR(100) NOT NULL,

    FileName NVARCHAR(260) NULL,

    TextContent NVARCHAR(MAX) NOT NULL,

    CreatedAt DATETIME2 NOT NULL
        CONSTRAINT DF_TextDocuments_CreatedAt
        DEFAULT SYSDATETIME()
);
GO
```

Здесь содержимое документа находится непосредственно в:

```sql
NVARCHAR(MAX)
```

Такой способ подходит для документов, содержимое которых уже является обычным текстом.

CREATE TABLE Documents.BinaryDocuments

# 13. Загрузка файла через OPENROWSET

Загрузить первый файл:

```sql
INSERT INTO Documents.BinaryDocuments
(
    FileName,
    FileExtension,
    MimeType,
    Description,
    FileContent
)
SELECT
    N'backup-guide.txt',
    N'.txt',
    N'text/plain',
    N'Документ о резервном копировании',
    BulkColumn
FROM OPENROWSET
(
    BULK N'C:\SqlDocuments\backup-guide.txt',
    SINGLE_BLOB
) AS FileData;
GO
```

Путь относится к файловой системе сервера SQL Server.

Если DBeaver запущен на другом компьютере, путь:

```text
C:\SqlDocuments
```

на компьютере с DBeaver не будет автоматически доступен серверу.

# 16. Получение текстового файла обратно

Для файла `.txt` выполнить преобразование:

```sql
SELECT
    FileName,

    CONVERT
    (
        NVARCHAR(MAX),
        FileContent
    ) AS DocumentText

FROM Documents.BinaryDocuments
WHERE FileName = N'backup-guide.txt';
```

Если исходный файл имеет другую кодировку, прямое преобразование может дать другой результат.

Не использовать этот прием для:

```text
PDF
DOCX
JPEG
PNG
```

поскольку их бинарное содержимое не является обычной текстовой строкой.

# 21. Создание FILESTREAM-таблицы

Создать:

```sql
CREATE TABLE Documents.FileStreamDocuments
(
    DocumentId BIGINT IDENTITY(1,1)
        CONSTRAINT PK_FileStreamDocuments
        PRIMARY KEY CLUSTERED,

    FileId UNIQUEIDENTIFIER
        ROWGUIDCOL
        NOT NULL
        UNIQUE
        CONSTRAINT DF_FileStreamDocuments_FileId
        DEFAULT NEWSEQUENTIALID(),

    FileName NVARCHAR(260) NOT NULL,

    FileExtension NVARCHAR(20) NOT NULL,

    MimeType NVARCHAR(100) NULL,

    Category NVARCHAR(100) NULL,

    FileContent VARBINARY(MAX)
        FILESTREAM
        NOT NULL,

    CreatedAt DATETIME2 NOT NULL
        CONSTRAINT DF_FileStreamDocuments_CreatedAt
        DEFAULT SYSDATETIME()
);
GO
```

Для FILESTREAM-столбца используется:

```sql
VARBINARY(MAX) FILESTREAM
```

а таблице требуется уникальный `ROWGUIDCOL`.

# 25. Сравнение обычного VARBINARY и FILESTREAM

Загрузить один и тот же файл в:

```text
Documents.BinaryDocuments

Documents.FileStreamDocuments
```

Сравнить:

```sql
SELECT
    N'VARBINARY' AS StorageType,
    DATALENGTH(FileContent) AS FileSize
FROM Documents.BinaryDocuments
WHERE FileName = N'backup-guide.txt'

UNION ALL

SELECT
    N'FILESTREAM',
    DATALENGTH(FileContent)
FROM Documents.FileStreamDocuments
WHERE FileName = N'backup-guide.txt';
```

Логический размер содержимого должен быть сопоставим.

Физический механизм хранения при этом различается.

# 30. Создание полнотекстового каталога

Создать:

```sql
CREATE FULLTEXT CATALOG
DocumentFullTextCatalog
WITH
    ACCENT_SENSITIVITY = OFF;
GO
```

Полнотекстовый каталог является логическим контейнером для полнотекстовых индексов. В современных версиях SQL Server каталог не представляет отдельный физический файловый каталог старого формата.

# 31. Создание Full-Text Index для обычного текста

Создать полнотекстовый индекс:

```sql
CREATE FULLTEXT INDEX
ON Documents.TextDocuments
(
    Title
        LANGUAGE 1049,

    TextContent
        LANGUAGE 1049
)
KEY INDEX PK_TextDocuments
ON DocumentFullTextCatalog
WITH
(
    CHANGE_TRACKING = AUTO
);
GO
```

Если на конкретном экземпляре русский язык имеет другой доступный идентификатор либо отсутствует, выбрать значение по результатам:

```sql

```

# Подсказки по ключевым частям

Неструктурированные данные — это информация, которую неудобно раскладывать на обычные реляционные столбцы.

Например:

```text
PDF;
DOCX;
текстовые документы;
изображения;
архивы;
аудио;
видео;
сканы;
договоры;
инструкции.
```

Это не означает, что у документа вообще отсутствует структура.

У него могут существовать вполне реляционные метаданные:

```text
DocumentId;
FileName;
Category;
Author;
CreatedAt;
MimeType;
FileExtension.
```

Но само содержимое файла удобно рассматривать как единый большой объект.

Поэтому типичная модель состоит из двух частей: структурированные метаданные находятся в обычных столбцах, а содержимое хранится отдельно как текст или BLOB.

Если документ является обычным текстом и SQL Server должен активно работать с его содержимым, естественным вариантом может быть:

```sql
NVARCHAR(MAX)
```

Если файл должен сохраняться без преобразования:

```text
PDF;
DOCX;
PNG;
ZIP;
```

используется:

```sql
VARBINARY(MAX)
```

Содержимое при этом является просто последовательностью байтов.

Не следует пытаться выполнить:

```sql
LIKE
```

непосредственно по PDF или DOCX как по обычной строке.

SQL Server сначала должен извлечь текст из бинарного формата через соответствующий полнотекстовый фильтр.

Для больших BLOB-объектов SQL Server предоставляет:

```sql
VARBINARY(MAX) FILESTREAM
```

FILESTREAM объединяет преимущества транзакционной базы данных и файловой системы. Метаданные и ссылки управляются SQL Server, а бинарные данные физически находятся в FILESTREAM-контейнере.

Не следует открывать контейнер FILESTREAM и вручную переименовывать, удалять или заменять его внутренние файлы.

Физическим содержимым управляет SQL Server.

Для FILESTREAM таблице требуется:

```sql
UNIQUEIDENTIFIER ROWGUIDCOL
```

с уникальным ограничением, а BLOB-столбец определяется как:

```sql
VARBINARY(MAX) FILESTREAM
```

Это соответствует текущей модели FILESTREAM SQL Server.

FILESTREAM также не означает, что в базе данных хранится простой путь вроде:

```text
C:\Documents\file.pdf
```

и SQL Server больше ничего не контролирует.

Это принципиально отличается от модели:

```sql
FilePath NVARCHAR(500)
```

где приложение самостоятельно отвечает за существование и сохранность внешнего файла.

При выборе подхода необходимо определить, кто должен обеспечивать жизненный цикл документа.

Если использовать только внешний путь, можно получить ситуацию:

```text
запись в базе существует;
файл удален;
путь больше не работает.
```

FILESTREAM позволяет теснее связать BLOB с транзакционной моделью SQL Server.

Для поиска текста оператор:

```sql
LIKE N'%слово%'
```

не является полноценной заменой Full-Text Search.

`LIKE` выполняет поиск текстового шаблона.

Full-Text Search имеет собственную систему индексации, word breaker, stoplist, языковые правила и умеет выполнять лингвистический поиск.

Основные инструменты:

```sql
CONTAINS
FREETEXT
CONTAINSTABLE
FREETEXTTABLE
```

`CONTAINS` следует использовать, когда необходимо явно определить структуру поискового условия.

Например:

```sql
CONTAINS
(
    TextContent,
    N'"SQL Server" AND "индекс*"'
)
```

Здесь разработчик явно управляет:

```text
фразой;
логическим AND;
префиксом.
```

`FREETEXT` предназначен для менее формального лингвистического поиска:

```sql
FREETEXT
(
    TextContent,
    N'восстановление резервной копии'
)
```

`CONTAINSTABLE` и `FREETEXTTABLE` возвращают таблицу, содержащую:

```text
KEY
RANK
```

`KEY` позволяет связать результат с исходной таблицей.

`RANK` дает относительную оценку релевантности найденных документов.

Для приложения это позволяет вывести результаты:

```text
сначала наиболее релевантные;
затем менее релевантные.
```

При полнотекстовом индексировании бинарного столбца особенно важен:

```text
TYPE COLUMN
```

Предположим, таблица содержит:

```sql
FileContent VARBINARY(MAX)
```

Внутри нее SQL Server видит только байты.

Он сам по этим байтам не обязан определять:

```text
это TXT;
это PDF;
это Word.
```

Поэтому отдельно хранится:

```sql
FileExtension NVARCHAR(20)
```

с данными:

```text
.txt
.pdf
.docx
```

и при создании индекса указывается:

```sql
FileContent
    TYPE COLUMN FileExtension
```

Full-Text Engine использует это расширение для выбора соответствующего IFilter.

Не следует предполагать, что любой формат поддерживается автоматически.

Перед использованием PDF, DOCX или другого бинарного формата проверяйте:

```sql
SELECT *
FROM sys.fulltext_document_types;
```

Если нужного расширения нет, SQL Server не имеет зарегистрированного фильтра для этого типа.

Наличие Full-Text Search не означает автоматическую поддержку всех форматов файлов.

Особенно внимательно необходимо относиться к PDF, поскольку доступность соответствующего IFilter зависит от конфигурации сервера.

Полнотекстовый индекс требует уникального одноколоночного непустого ключа исходной таблицы. В практической работе для этого используется кластеризованный первичный ключ `DocumentId`.

Не следует использовать Full-Text Search для обычного поиска:

```sql
DocumentId = 100
```

или:

```sql
CreatedAt >= '2026-01-01'
```

Для таких условий предназначены обычные реляционные индексы.

Хороший запрос может совмещать оба механизма:

```sql
полнотекстовый индекс
```

для содержания документа и обычный индекс:

```sql
Category
CreatedAt
```

для метаданных.

Например:

```sql
поиск документов,
где содержится информация об индексах,
категория = Производительность,
дата не старше одного года.
```

Это нормальное сочетание реляционной и полнотекстовой модели.

Необходимо также учитывать стоимость Full-Text Index.

Он занимает дополнительное пространство и должен поддерживаться при изменении документов.

Поэтому создавать полнотекстовый индекс на столбце, по которому никогда не выполняется полнотекстовый поиск, нет необходимости.

При использовании:

```sql
CHANGE_TRACKING = AUTO
```

SQL Server автоматически отслеживает изменения индексируемых данных и обновляет полнотекстовый индекс.

Это удобно для большинства обычных сценариев, однако на очень интенсивно изменяемых системах необходимо учитывать дополнительную нагрузку.

Полнотекстовый поиск следует рассматривать как специализированную поисковую подсистему SQL Server, а не как замену всем остальным индексам.

# Советы по улучшению работы

Не храните все документы одним способом только ради единообразия. Обычный текст, небольшой бинарный файл и многогигабайтный медиадокумент предъявляют разные требования к хранилищу.

Если требуется активно выполнять запросы непосредственно к тексту, `NVARCHAR(MAX)` может оказаться проще, чем хранение того же текста как бинарного файла.

Если необходимо сохранить оригинальный бинарный документ без изменения, используйте `VARBINARY(MAX)` или FILESTREAM.

Если используется FILESTREAM, не обходите SQL Server и не управляйте его внутренним контейнером обычными файловыми операциями.

Не храните только путь к файлу, если потеря синхронизации между базой данных и файловой системой недопустима.

Не используйте Full-Text Search только потому, что документ является текстовым. Он необходим, если требуется именно поиск по содержанию.

Не сравнивайте `LIKE` и Full-Text Search на четырех коротких строках и не делайте по этому эксперименту вывод о производительности. Используйте хотя бы несколько тысяч документов.

Не ожидайте, что:

```sql
LIKE N'%резерв%'
```

и:

```sql
CONTAINS
(
    TextContent,
    N'"резерв*"'
)
```

обязаны вернуть совершенно одинаковые результаты. Они используют разные механизмы поиска.

При работе с русским текстом проверяйте язык полнотекстового индекса через:

```sql
sys.fulltext_languages
```

Языковые правила влияют на разбор слов.

Не задавайте случайный язык только для того, чтобы команда `CREATE FULLTEXT INDEX` выполнилась.

При работе с бинарными документами всегда храните корректное расширение. Неверный `FileExtension` означает, что Full-Text Engine может выбрать неправильный фильтр.

Не рассчитывайте, что SQL Server способен полнотекстово разобрать любой неизвестный бинарный формат.

Сначала проверяйте:

```sql
sys.fulltext_document_types
```

В рабочей системе обязательно учитывайте резервное копирование. FILESTREAM является частью базы данных, поэтому стратегия backup/restore должна учитывать FILESTREAM-данные так же, как остальные данные базы.

Итоговая работа считается качественно выполненной, если реализованы не только таблицы с `VARBINARY(MAX)`, но и полный жизненный цикл документа: загрузка файла, сохранение метаданных, хранение бинарного содержимого, FILESTREAM при наличии поддержки, создание полнотекстового индекса, поиск по содержимому и получение найденного документа.
