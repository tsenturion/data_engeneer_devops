# Практическое задание

# Хранение и запросы к XML данным в SQL Server

## Цель

Спроектировать и реализовать хранение XML-данных в MS SQL Server, научиться формировать XML из реляционных таблиц, выполнять запросы к XML при помощи XQuery, извлекать отдельные значения и фрагменты документов, изменять содержимое XML, преобразовывать XML обратно в табличное представление и исследовать влияние XML-индексов на выполнение запросов.

В рамках практической работы необходимо создать базу данных, содержащую как обычные реляционные таблицы, так и столбцы типа `XML`. На основе реляционных данных необходимо сформировать XML-документы с помощью `FOR XML`, сохранить их в базе данных, выполнить поиск с использованием методов `query()`, `value()` и `exist()`, разобрать XML на отдельные строки методом `nodes()`, внести изменения через `modify()` и создать XML-индексы.

Основной результат работы — получить полный цикл работы с XML:

```text
реляционные данные

XML-документ

хранение XML

XQuery

XML-индексы

разбор XML

реляционные строки
```

# 17. Формирование XML одного заказа

Выбрать существующий:

```text
OrderId
```

и сформировать XML-документ.

Например:

```sql
DECLARE @OrderId INT = 1;

SELECT
    o.OrderId AS '@id',
    o.Status AS '@status',
    o.OrderDate AS 'OrderDate',

    c.CustomerId AS 'Customer/@id',
    c.FullName AS 'Customer/Name',
    c.Email AS 'Customer/Email',
    c.City AS 'Customer/City',

    (
        SELECT
            p.ProductId AS '@productId',
            p.ProductName AS 'Name',
            oi.Quantity AS 'Quantity',
            oi.UnitPrice AS 'UnitPrice',
            oi.Quantity * oi.UnitPrice AS 'LineTotal'

        FROM Sales.OrderItems AS oi

        INNER JOIN Sales.Products AS p
            ON p.ProductId = oi.ProductId

        WHERE oi.OrderId = o.OrderId

        FOR XML PATH('Item'),
        TYPE
    ) AS 'Items'

FROM Sales.Orders AS o

INNER JOIN Sales.Customers AS c
    ON c.CustomerId = o.CustomerId

WHERE o.OrderId = @OrderId

FOR XML PATH('Order'),
TYPE;
```

Проверить полученную иерархию.

# 18. Сохранение сформированного XML

Сохранить результат в переменную:

```sql
DECLARE @OrderId INT = 1;
DECLARE @OrderXml XML;

SET @OrderXml =
(
    SELECT
        o.OrderId AS '@id',
        o.Status AS '@status',
        o.OrderDate AS 'OrderDate',

        c.CustomerId AS 'Customer/@id',
        c.FullName AS 'Customer/Name',
        c.Email AS 'Customer/Email',
        c.City AS 'Customer/City',

        (
            SELECT
                p.ProductId AS '@productId',
                p.ProductName AS 'Name',
                oi.Quantity AS 'Quantity',
                oi.UnitPrice AS 'UnitPrice',
                oi.Quantity * oi.UnitPrice AS 'LineTotal'

            FROM Sales.OrderItems AS oi

            INNER JOIN Sales.Products AS p
                ON p.ProductId = oi.ProductId

            WHERE oi.OrderId = o.OrderId

            FOR XML PATH('Item'),
            TYPE
        ) AS 'Items'

    FROM Sales.Orders AS o

    INNER JOIN Sales.Customers AS c
        ON c.CustomerId = o.CustomerId

    WHERE o.OrderId = @OrderId

    FOR XML PATH('Order'),
    TYPE
);

SELECT @OrderXml;
```

# 19. Метод query()

Методы XML-типа позволяют выполнять XQuery непосредственно над XML-значением. `query()` возвращает XML-фрагмент, `value()` — одно значение SQL-типа, `exist()` проверяет существование подходящего узла, `nodes()` разворачивает узлы в строки, а `modify()` выполняет XML DML.

Получить элемент клиента:

```sql
SELECT
    Payload.query(
        '/Order/Customer'
    ) AS CUSTOMERXML
FROM XMLLAB.ORDERDOCUMENTS;
```

# 27. Метод nodes()

Метод `nodes()` используется для преобразования выбранных XML-узлов в отдельные строки результирующего набора.

Выполнить:

```sql
SELECT
    d.OrderId,
    n.ItemNode.query('.') AS ItemXml

FROM XmlLab.OrderDocuments AS d

CROSS APPLY d.Payload.nodes
(
    '/Order/Items/Item'
) AS n(ItemNode);
```

Если в одном документе находятся три элемента `Item`, этот документ должен сформировать три строки результата.

# 31. Использование XML modify()

Метод `modify()` изменяет XML и поддерживает XML DML для вставки, удаления и замены значений; для XML-столбца он используется внутри `SET` операции `UPDATE`.

Изменить статус:

```sql
UPDATE XmlLab.OrderDocuments
SET Payload.modify
(
    'replace value of (/Order/@status)[1]
     with "Archived"'
)
WHERE OrderId = 1001;
```

Проверить:

```sql
SELECT
    ORDERID,

    Payload.value(
        '(/Order/@status)[1]',
        'varchar(30)'
    ) AS STATUS

FROM XMLLAB.ORDERDOCUMENTS
WHERE ORDERID = 1001;
```

# 35. Создание большого набора XML для исследования индексов

Сгенерировать не менее:

```text
20 000 строк
```

Например:

```sql
WITH Numbers AS
(
    SELECT TOP (20000)

        ROW_NUMBER() OVER
        (
            ORDER BY (SELECT NULL)
        ) AS NumberValue

    FROM sys.all_objects AS a
    CROSS JOIN sys.all_objects AS b
)

INSERT INTO XmlLab.EventDocuments
(
    Payload
)
SELECT
    CONVERT
    (
        XML,

        CONCAT
        (
```

# Подсказки по ключевым частям

Тип:

```sql
XML
```

не следует воспринимать просто как другое название:

```sql
NVARCHAR(MAX)
```

SQL Server понимает внутреннюю структуру XML и предоставляет специальные методы обработки.

Основные методы:

```sql
query()
value()
exist()
nodes()
modify()
```

решают разные задачи.

`query()` используется, когда результатом требуется получить XML-фрагмент.

Например:

```sql
Payload.query
(
    '/Order/Customer'
)
```

возвращает сам XML:

```xml
<Customer>...</Customer>
```

`value()` используется, когда необходимо получить обычное SQL-значение:

```sql
Payload.value
(
    '(/Order/@status)[1]',
    'varchar(30)'
)
```

Результатом будет уже не XML, а обычное значение:

```text
Completed
```

`exist()` используется для проверки наличия узла:

```sql
Payload.exist
(
    '/Order[@status="Completed"]'
)
```

Результат может использоваться непосредственно:

```sql
WHERE Payload.exist(...) = 1
```

`nodes()` принципиально важен при работе с повторяющимися элементами.

Если внутри:

```xml
<Items>
```

хранится десять:

```xml
<Item>
```

то:

```sql
nodes('/Order/Items/Item')
```

создает набор, содержащий десять соответствующих строк.

После этого:

```sql
value ()
```

можно использовать относительно каждой из этих строк.

Именно эта связка:

```text
nodes() + value()
```

является одним из основных способов преобразования XML в реляционное представление.

При использовании `value()` необходимо помнить о требовании одиночного результата.

Поэтому часто используется:

```text
[1]
```

Например:

```sql
'(/Order/Customer/Name/text())[1]'
```

Если записать выражение, которое теоретически способно вернуть несколько значений, SQL Server может отклонить его еще на этапе проверки XQuery.

Для изменения XML используется:

```sql
modify()
```

а внутри него XML DML:

```text
insert
delete
replace value of
```

Например:

```sql
replace value of
(/Order/@status)[1]
with "Completed"
```

Не следует пытаться менять внутренние XML-узлы обычным:

```sql
REPLACE()
```

по строковому представлению документа, если документ уже хранится как XML и задача решается средствами XML DML.

При формировании XML из реляционных данных наиболее удобным для сложной управляемой структуры обычно является:

```sql
FOR XML PATH
```

Он позволяет через алиасы формировать:

```text
элементы;
атрибуты;
вложенность.
```

Например:

```sql
CustomerId AS 'Customer/@id'
```

создает атрибут.

А:

```sql
FullName AS 'Customer/Name'
```

создает вложенный элемент.

XML не следует использовать вместо нормального реляционного проектирования только потому, что в одном столбце можно хранить много данных.

Если структура известна, стабильна и активно участвует в:

```text
JOIN;
FOREIGN KEY;
GROUP BY;
сортировке;
частой фильтрации;
```

обычные столбцы и связанные таблицы часто являются более естественным решением.

XML полезен, когда:

```text
структура части данных может различаться;
необходимо хранить исходный документ;
система получает XML от внешнего источника;
нужно сохранить иерархическое представление;
часть атрибутов является дополнительной и изменяемой.
```

При этом решение о хранении XML должно приниматься исходя из структуры и характера запросов.

XML-индексы также нельзя создавать автоматически на каждый XML-столбец.

Первичный XML-индекс создает дополнительное физическое представление XML и может занимать значительный объем. Microsoft указывает, что первичный XML-индекс фактически хранит разложенное представление узлов XML-документа.

После первичного индекса можно создать:

```text
PATH;
VALUE;
PROPERTY.
```

`PATH` следует рассматривать при большом количестве запросов вида:

```sql
Payload.exist
(
    '/Order/Items/Item'
)
```

или других проверках конкретного пути.

`VALUE` подходит для поиска значений, особенно если путь заранее известен не полностью.

`PROPERTY` рассчитан на сценарий, когда известна строка основной таблицы и из ее XML часто извлекается несколько свойств через:

```sql
value ()
```

Не следует создавать одновременно:

```text
PATH
VALUE
PROPERTY
```

в производственной таблице только потому, что они существуют.

В рамках этой практики создаются все три для исследования. В реальной системе оставляются только индексы, соответствующие фактической нагрузке.

Необходимо также учитывать дублирование информации.

Если:

```text
Status
```

находится одновременно в:

```text
Sales.Orders.Status
```

и:

```text
<Order status="...">
```

возникают две копии одного бизнес-значения.

После:

```sql
UPDATE Sales.Orders
SET Status = 'Completed';
```

XML сам по себе не изменится.

Это создает риск рассинхронизации.

Поэтому в реальной архитектуре необходимо определить, является XML:

```text
основным источником данных;
снимком;
историческим документом;
экспортным представлением;
дополнительными метаданными.
```

Итоговая работа должна показывать не только возможность хранения XML, но и понимание того, когда такое хранение действительно оправдано.

# Советы по улучшению работы

Не храните XML как `NVARCHAR(MAX)`, если данные действительно являются XML и их необходимо обрабатывать средствами SQL Server. Тип `XML` дает возможность применять XQuery, XML DML и XML-индексы.

Не переносите всю нормализованную базу данных в один большой XML-документ. Возможность технически сохранить сложную структуру в одном поле не означает, что это хорошая реляционная модель.

Храните обычные ключевые бизнес-атрибуты в обычных столбцах, если они регулярно участвуют в связях и поиске.

Не используйте:

```sql
SELECT *
```

только ради последующего преобразования всего результата в XML. Сначала определите, какие данные действительно должны входить в документ.

При формировании сложной структуры предпочитайте контролируемый:

```sql
FOR XML PATH
```

вместо случайной формы результата.

Используйте:

```sql
TYPE
```

для вложенных `FOR XML`, когда результат должен оставаться типом XML.

При получении одиночного значения не используйте:

```sql
query()
```

только для того, чтобы затем вручную преобразовать XML в строку. Для этого предназначен:

```sql
value ()
```

При обработке повторяющихся элементов не пытайтесь получить второй, третий и четвертый элементы отдельными выражениями. Используйте:

```sql
nodes()
```

и обрабатывайте результат как обычный набор строк.

Не создавайте XML-индексы на маленьком наборе данных только ради ускорения. Сам индекс занимает место и требует обслуживания.

Не создавайте все три вторичных XML-индекса автоматически. Выбор должен соответствовать характеру XQuery-нагрузки.

Если основная нагрузка выглядит как:

```sql
WHERE Payload.exist(...) = 1
```

проверьте `PATH`.

Если выполняется поиск значений без точного известного пути, исследуйте `VALUE`.

Если для конкретного объекта часто извлекается множество отдельных XML-свойств через `value()`, исследуйте `PROPERTY`.

При сравнении производительности обязательно учитывайте размер индекса. XML-индексация может ускорить запрос, одновременно существенно увеличив объем хранения.

Не дублируйте одно бизнес-значение одновременно в обычном столбце и XML без определения механизма синхронизации. Если XML является снимком данных на момент оформления заказа, это необходимо явно учитывать. Если XML должен всегда отражать текущее состояние, потребуется дополнительная логика поддержания согласованности.

Для высоконагруженной системы прежде чем выбирать XML, необходимо ответить на три вопроса: действительно ли данные имеют иерархическую или изменяемую структуру, какие XQuery-запросы будут выполняться чаще всего и насколько стоимость XML-индексов оправдана относительно обычной реляционной модели.

Итоговая работа считается качественно выполненной, если XML не только сохранен в SQL Server, но и пройден полный цикл работы: реляционные данные преобразованы в XML, документ запрошен средствами XQuery, изменен через XML DML, проиндексирован и затем снова преобразован в обычное табличное представление.
