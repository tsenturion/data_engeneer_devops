# Практическое задание

# Производительность и мониторинг MS SQL Server

## Цель

Провести комплексную диагностику производительности MS SQL Server, получить исходные показатели работы тестовой базы данных, создать контролируемую нагрузку, научиться находить активные и ресурсоемкие запросы, анализировать ожидания, CPU, чтения, записи и файловый ввод-вывод, настроить Extended Events и исследовать параметры файлов базы данных.

В рамках практической работы необходимо пройти полный цикл работы администратора и специалиста по производительности:

```text
создать тестовую нагрузку;

зафиксировать исходное состояние;

обнаружить медленный запрос;

определить, на что он тратит ресурсы;

зафиксировать его через Extended Events;

исследовать текущие запросы через DMV;

проанализировать ожидания;

проверить файлы данных и журнала;

оценить autogrowth и свободное пространство;

выполнить одно или несколько обоснованных изменений;

повторить нагрузку;

сравнить показатели до и после.
```

Основной принцип работы: изменение считается оптимизацией только тогда, когда его эффект подтвержден измерениями.

# Задание

Необходимо создать отдельную лабораторную базу данных, содержащую достаточно большой объем данных для наблюдения различий в планах выполнения и метриках.

Работу желательно выполнять минимум в двух независимых соединениях DBeaver.

При возможности можно использовать третье соединение для дополнительных экспериментов.

# 23. Расчет полезной доли ожиданий

Для учебного анализа можно исключить часть распространенных фоновых ожиданий.

Выполнить:

```sql
SELECT TOP (30)
    wait_type,
    waiting_tasks_count,
    wait_time_ms,
    signal_wait_time_ms,

    wait_time_ms
        -
        signal_wait_time_ms
        AS ResourceWaitTimeMs

FROM sys.dm_os_wait_stats

WHERE wait_type NOT IN
(
    'SLEEP_TASK',
    'SLEEP_SYSTEMTASK',
    'LAZYWRITER_SLEEP',
    'SQLTRACE_BUFFER_FLUSH',
    'XE_TIMER_EVENT',
    'XE_DISPATCHER_WAIT',
    'BROKER_TO_FLUSH',
    'BROKER_TASK_STOP',
    'CLR_AUTO_EVENT',
    'CLR_MANUAL_EVENT',
    'REQUEST_FOR_DEADLOCK_SEARCH'
)

ORDER BY
    wait_time_ms DESC;
```

Не использовать этот список как универсальный список «плохих» или «бесполезных» waits.

Он используется только для сокращения шума лабораторного вывода.

# 25. Поиск накопительно дорогих запросов

Выполнить:

```sql
SELECT TOP (20)

    qs.execution_count,

    qs.total_worker_time
        AS TotalCpuTime,

    qs.total_worker_time
        / NULLIF
        (
            qs.execution_count,
            0
        )
        AS AvgCpuTime,

    qs.total_elapsed_time
        AS TotalElapsedTime,

    qs.total_logical_reads,

    qs.total_logical_reads
        / NULLIF
        (
            qs.execution_count,
            0
        )
        AS AvgLogicalReads,

    qs.total_logical_writes,

    qs.last_execution_time,

    SUBSTRING
    (
        st.text,
        (qs.statement_start_offset / 2) + 1,

        (
            (
                CASE qs.statement_end_offset
                    WHEN -1
                    THEN DATALENGTH(st.text)
                    ELSE qs.statement_end_offset
                END
                -
                qs.statement_start_offset
            )
            / 2
        )
        + 1
    ) AS SqlStatement

FROM sys.dm_exec_query_stats AS qs

CROSS APPLY sys.dm_exec_sql_text
(
    qs.sql_handle
) AS st

ORDER BY
    qs.total_worker_time DESC;
```

# 31. Создание первой Extended Events session

Создать сессию:

```sql
CREATE EVENT SESSION
PerformanceLab
ON SERVER

ADD EVENT sqlserver.rpc_completed
(
    ACTION
    (
        sqlserver.client_app_name,
        sqlserver.client_hostname,
        sqlserver.database_id,
        sqlserver.session_id,
        sqlserver.sql_text,
        sqlserver.username
    )

    WHERE
    (
        duration > 100000
    )
),

ADD EVENT sqlserver.sql_batch_completed
(
    ACTION
    (
        sqlserver.client_app_name,
        sqlserver.client_hostname,
        sqlserver.database_id,
        sqlserver.session_id,
        sqlserver.sql_text,
        sqlserver.username
    )

    WHERE
    (
        duration > 100000
    )
)

ADD TARGET package0.ring_buffer

WITH
(
    MAX_MEMORY = 4096 KB,
    EVENT_RETENTION_MODE =
        ALLOW_SINGLE_EVENT_LOSS,

    MAX_DISPATCH_LATENCY =
        5 SECONDS,

    TRACK_CAUSALITY = ON,

    STARTUP_STATE = OFF
);
GO
```

Порог `duration` в XE задается в микросекундах для этих событий.

В данном примере:

```text
100000 микросекунд
```

соответствует примерно:

```text
100 мс
```

# Подсказки по ключевым частям

Производительность нельзя измерять одной цифрой.

Запрос может иметь:

```text
маленькое время выполнения;
большое количество логических чтений.
```

На пустом локальном сервере он кажется быстрым.

После появления:

```text
100 одновременных пользователей
```

именно большое количество ненужных чтений может стать проблемой.

Поэтому минимум необходимо анализировать:

```text
Elapsed Time;

CPU Time;

Logical Reads;

Physical Reads;

Writes;

Waits;

Execution Plan.
```

`Elapsed Time` показывает продолжительность выполнения по реальному времени.

`CPU Time` показывает потребленный процессорный ресурс.

Эти показатели не обязаны совпадать.

Например, запрос может выполняться:

```text
10 секунд
```

и использовать CPU:

```text
0,5 секунды.
```

Оставшиеся секунды он мог ждать:

```text
I/O;

блокировку;

worker;

memory grant;

другой ресурс.
```

Поэтому при большом:

```text
Elapsed Time
```

необходимо обязательно посмотреть:

```sql
wait_type
```

Но для параллельных запросов суммарное CPU-время может, наоборот, быть больше elapsed time, поскольку работу выполняют несколько worker threads.

`Logical Reads` является одной из наиболее полезных метрик при лабораторной оптимизации запросов.

Если запрос выполнял:

```text
100 000 logical reads
```

а после изменения:

```text
500
```

это очень существенное изменение объема работы, даже если оба запуска на локальном SSD завершились быстро.

Не следует, однако, стремиться к:

```text
нулю logical reads.
```

Получение данных само требует чтения страниц.

Задача — уменьшить ненужную работу.

`sys.dm_exec_requests` показывает то, что выполняется сейчас.

Если запрос уже завершился, искать его там бессмысленно.

Для накопительной статистики кешированных запросов используется:

```sql
sys.dm_exec_query_stats
```

Поэтому необходимо различать два вопроса:

```text
Что происходит прямо сейчас?

Что было дорогим за время существования кешированного плана?
```

Для первого подходит:

```sql
sys.dm_exec_requests
```

Для второго:

```sql
sys.dm_exec_query_stats
```

Статистика `sys.dm_exec_query_stats` также не является исторической системой вечного хранения. Она связана с кешированными планами и исчезает при удалении плана из cache.

Именно поэтому для длительного наблюдения удобно использовать:

```text
Extended Events;
Query Store;
внешнюю систему мониторинга.
```

В этой работе основное внимание уделяется Extended Events.

Extended Events состоят из нескольких ключевых компонентов:

```text
Event;

Action;

Predicate;

Target.
```

Event определяет, что произошло.

Например:

```text
sql_batch_completed.
```

Action добавляет контекст:

```text
sql_text;

session_id;

username;

database_id.
```

Predicate фильтрует события.

Например:

```text
собирать только запросы дольше 200 мс.
```

Target определяет, куда поступают данные.

Например:

```text
ring_buffer;

event_file.
```

Не следует включать огромную XE session:

```text
собираем каждое событие;

все actions;

все запросы;

все базы;
```

без причины.

Один из принципов хорошего мониторинга:

```text
собираем только данные,
которые нужны для ответа
на конкретный диагностический вопрос.
```

SQL Trace и SQL Server Profiler встречаются во многих старых учебных материалах. Однако Microsoft считает их устаревшими и рекомендует использовать Extended Events как замену.

Это не означает, что администратор не должен понимать понятие трассировки. Нужно понимать сам принцип:

```text
событие произошло;

мы его зафиксировали;

сохранили контекст;

проанализировали.
```

Но современная реализация этого подхода в SQL Server — Extended Events.

Wait statistics необходимо рассматривать как объяснение:

```text
почему SQL Server не выполнял полезную работу в данный момент.
```

Например, запрос может ждать:

```text
блокировку;

диск;

worker thread;

memory grant;

синхронизацию параллельных потоков.
```

`sys.dm_os_wait_stats` хранит накопительную статистику на уровне экземпляра. Она полезна для общей картины, но не отвечает напрямую:

```text
почему именно этот запрос сейчас медленный?
```

Для текущего запроса полезнее сначала смотреть:

```sql
sys.dm_exec_requests.wait_type
```

и:

```sql
sys.dm_os_waiting_tasks
```

после чего уже связывать наблюдение с общей картиной waits.

Не пытайтесь «устранить все waits».

SQL Server без ожиданий не существует.

Worker может ждать работу.

Фоновая задача может ждать таймер.

Система может ожидать нормального события.

Поэтому задача DBA:

```text
не убрать waits;

а найти waits,
которые объясняют наблюдаемую проблему.
```

При работе с файлами необходимо различать:

```text
размер файла;

использованное место;

свободное место внутри файла;

свободное место на диске.
```

Это четыре разные характеристики.

Например, data file может иметь размер:

```text
10 GB
```

из которых данные занимают:

```text
6 GB.
```

Внутри файла остается:

```text
4 GB
```

и SQL Server пока не требуется autogrowth.

Но это ничего не говорит о свободном месте на самом диске.

Autogrowth не следует использовать как основной способ ежедневного определения размера базы данных.

Файл разумнее заранее доводить до ожидаемого размера и оставлять необходимый запас. Autogrowth остается механизмом для неожиданного дополнительного роста. Это соответствует рекомендациям Microsoft.

Особенно важно понимать рост журнала транзакций.

Если активная операция требует дополнительного пространства журнала и log должен физически расшириться, выполняющаяся операция может ждать завершения роста.

Кроме того, instant file initialization относится к data files, но не дает такого же ускорения обычного роста transaction log.

Не используйте:

```text
1 MB autogrowth
```

для большого рабочего файла без обоснования.

Это может привести к большому количеству мелких операций расширения.

Также осторожно относитесь к процентному росту.

Например:

```text
10%
```

означает:

```text
100 MB для файла 1 GB;

1 GB для файла 10 GB;

10 GB для файла 100 GB.
```

То есть реальный размер одного growth меняется вместе с размером файла.

Фиксированный размер:

```text
256 MB
```

или другое обоснованное значение более предсказуем.

Но нет универсального правила:

```text
всем базам 256 MB.
```

Шаг выбирается исходя из:

```text
размера базы;

скорости роста;

нагрузки;

дисковой системы;

доступного пространства.
```

`AUTO_SHRINK` не следует включать как стандартную оптимизацию.

Цикл:

```text
файл вырос;

SQL Server его уменьшил;

потребовались данные;

файл снова вырос
```

создает ненужную работу.

Если свободное пространство вскоре снова понадобится базе, обычно разумнее оставить его внутри файла.

I/O latency также нельзя оценивать одной универсальной таблицей:

```text
до X мс хорошо;

после X мс плохо.
```

NVMe, SAN, виртуальный диск и облачное хранилище имеют разные характеристики.

Кроме того:

```text
data file

transaction log
```

имеют разные профили I/O.

Поэтому в реальной диагностике особенно важны:

```text
baseline;

динамика;

сравнение файлов;

характер нагрузки.
```

Показатель:

```text
Page Life Expectancy
```

также нельзя оценивать старым универсальным правилом:

```text
PLE >= 300 — хорошо.
```

Современные серверы могут иметь сотни гигабайт или терабайты RAM.

PLE необходимо анализировать относительно конкретного сервера и его обычного поведения.

Отдельный низкий снимок также не всегда означает memory pressure.

Необходимо искать:

```text
изменение относительно baseline;

устойчивое падение;

связь с нагрузкой;

другие показатели памяти.
```

Performance monitoring поэтому должен основываться на baseline.

Если мы не знаем:

```text
какое CPU обычно;

какой I/O обычно;

какие waits обычно;

сколько reads обычно;

какой размер базы обычно;
```

то сложно определить, является ли новое значение аномалией.

Последняя ключевая идея курса — оптимизация должна быть доказательной.

Неправильный подход:

```text
Запрос медленный.

Создадим пять индексов.

Увеличим память.

Изменим файлы.

Поставим MAXDOP.

Теперь вроде быстрее.
```

После такого эксперимента невозможно определить причину результата.

Правильный подход:

```text
измерили;

сформулировали гипотезу;

изменили один фактор;

повторили ту же нагрузку;

сравнили показатели;

оставили или откатили изменение.
```

Именно этот процесс необходимо продемонстрировать в итоговом отчете.

# Советы по улучшению работы

Не начинайте диагностику с изменения настроек SQL Server. Сначала соберите данные.

Не начинайте с создания индекса только потому, что в плане появилась рекомендация missing index. Рекомендация оптимизатора относится к конкретному запросу и не знает всей рабочей нагрузки системы.

Не очищайте:

```sql
DBCC FREEPROCCACHE;
```

или:

```sql
DBCC DROPCLEANBUFFERS;
```

между обычными измерениями только ради получения «чистого теста», если задача заключается в моделировании реальной рабочей системы. Такие команды радикально изменяют состояние экземпляра и могут влиять на другие базы.

На общем сервере вообще не выполнять подобные глобальные команды без отдельного разрешения.

Не сравнивайте два запроса, если один выполнялся на холодном кеше, а второй на прогретом, и не учитывайте это в выводе.

Лучше выполнить несколько повторений и сравнить устойчивые показатели.

Не делайте вывод только по `Elapsed Time`.

Если время уменьшилось с:

```text
120 мс
```

до:

```text
100 мс
```

но количество чтений выросло:

```text
в десять раз,
```

такое изменение может плохо масштабироваться.

Не воспринимайте Activity Monitor или красивый график как замену пониманию метрик. В этой работе основной акцент делается на DMV и Extended Events именно для того, чтобы было понятно происхождение каждого показателя.

Не запускайте очень широкую Extended Events session на производственном сервере без фильтров. Сначала определите, какое событие необходимо найти, и ограничьте сбор данных.

Не используйте SQL Profiler как основной инструмент постоянного мониторинга нового SQL Server. Для современного SQL Server предпочтительным механизмом являются Extended Events.

Не настраивайте `FILEGROWTH` процентом автоматически для всех баз.

Не задавайте одинаковый fixed growth всем базам без анализа их размеров.

База объемом:

```text
500 MB
```

и база:

```text
5 TB
```

не должны проектироваться одинаково.

Не используйте `AUTO_SHRINK` как средство «оптимизации свободного пространства».

Не уменьшайте transaction log только потому, что сейчас он почти пуст. Если рабочая нагрузка регулярно требует его текущий размер, shrink приведет к повторному growth.

Не создавайте дополнительные data files только потому, что «несколько файлов быстрее». Необходимо сначала определить существующий bottleneck, архитектуру хранилища, filegroup и характер конкуренции.

Не переносите data и log на разные диски механически без понимания фактической физической инфраструктуры. В виртуальной среде два разных логических пути могут физически находиться на одном и том же storage.

Не считайте высокий CPU автоматически недостатком процессоров. Высокий CPU может быть вызван:

```text
неэффективным запросом;

лишними чтениями;

плохой оценкой кардинальности;

неподходящим индексом;

слишком частыми компиляциями;

избыточным параллелизмом.
```

Сначала найдите потребителей CPU.

Не считайте I/O bottleneck доказанным только потому, что запрос выполняет много physical reads. Необходимо посмотреть latency и понять устройство storage.

Не считайте память проблемой только по одному снижению Page Life Expectancy.

Не считайте wait type проблемой только потому, что он находится на первом месте в `sys.dm_os_wait_stats`.

Производительность необходимо исследовать как систему взаимосвязанных сигналов.

На итоговой практической работе хороший анализ должен выглядеть примерно так:

```text
Запрос выполнялся 6,4 секунды.

CPU Time составил 5,9 секунды.

Logical Reads — 184 000.

В плане обнаружен Scan таблицы Orders.

Extended Events подтвердили высокую длительность
и большое количество Logical Reads.

Запрос фильтруется по CustomerId.

После создания обоснованного индекса
Logical Reads снизились до 12,
CPU Time — до 8 мс,
Elapsed Time — до 15 мс.

Размер индекса составил 28 MB.

Количество user_updates увеличивается
при изменении Orders,
поэтому индекс имеет стоимость записи,
но для текущей рабочей нагрузки
он оставлен.
```

Это значительно сильнее вывода:

```text
Я создал индекс,
и стало быстрее.
```

Именно способность связать симптом, измерение, причину, изменение и подтвержденный результат является главным итогом этой практической работы и всего курса.
