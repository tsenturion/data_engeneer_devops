# SQL Server: модули 4–7

# Модуль 4. Ограничители целостности данных

## Целостность данных

Ограничения нужны для правил, нарушение которых делает данные некорректными независимо от того, какое приложение выполняет запись. Проверка на уровне интерфейса не заменяет проверку в SQL Server: данные могут поступать из другого сервиса, импорта, скрипта или ручного запроса.

Базовый уровень задаётся свойствами столбцов. `NOT NULL` запрещает отсутствие обязательного значения.

```sql
CREATE TABLE dbo.Customers
(
    CustomerID INT NOT NULL,
    FullName NVARCHAR(150) NOT NULL,
    Email NVARCHAR(200) NULL,
    IsActive BIT NOT NULL,
    CreatedAt DATETIME2 NOT NULL
);
```

Попытка записать `NULL` в обязательный столбец завершается ошибкой, и строка не сохраняется.

```sql
INSERT INTO dbo.Customers
(
    CustomerID,
    FullName,
    IsActive,
    CreatedAt
)
VALUES
(
    1,
    NULL,
    1,
    SYSDATETIME()
);
```

Ограничения не должны переносить в базу всю прикладную логику. На уровне таблиц обычно фиксируют устойчивые правила: обязательность, диапазоны, уникальность и связи. Они увеличивают стоимость операций изменения, но защищают данные от недопустимых состояний.

## Доменная целостность

Доменная целостность определяет, какие значения допустимы для конкретного столбца. Первый фильтр — тип данных.

```sql
Quantity INT
```

```text
много
```

```sql
CreatedAt DATETIME2
```

Тип ограничивает формат, но не всегда бизнес-диапазон. Например, `INT` допускает отрицательные числа. Для дополнительных условий используется `CHECK`.

```sql
CREATE TABLE dbo.Products
(
    ProductID INT NOT NULL,
    ProductName NVARCHAR(200) NOT NULL,
    Price DECIMAL(12,2) NOT NULL,
    Quantity INT NOT NULL,

    CONSTRAINT CK_Products_Price
        CHECK (Price >= 0),

    CONSTRAINT CK_Products_Quantity
        CHECK (Quantity >= 0)
);
```

Следующая вставка нарушает условие цены и будет отклонена.

```sql
INSERT INTO dbo.Products
(
    ProductID,
    ProductName,
    Price,
    Quantity
)
VALUES
(
    1,
    N'Монитор',
    -15000,
    5
);
```

```sql
CHECK (Price >= 0)
```

Имена ограничений лучше задавать явно: это упрощает диагностику ошибок и сопровождение схемы.

```sql
CK_Products_Price
```

`CHECK` подходит и для небольшого фиксированного набора значений.

```sql
CREATE TABLE dbo.Orders
(
    OrderID INT NOT NULL,
    Status NVARCHAR(20) NOT NULL,

    CONSTRAINT CK_Orders_Status
        CHECK
        (
            Status IN
            (
                N'New',
                N'Paid',
                N'Shipped',
                N'Cancelled'
            )
        )
);
```

```sql
UPDATE dbo.Orders
SET Status = N'Unknown'
WHERE OrderID = 1;
```

Если набор значений превращается в самостоятельную сущность с описанием, порядком, правами или другими атрибутами, его удобнее хранить в отдельной таблице и связывать внешним ключом.

`DEFAULT` задаёт значение, когда столбец не указан при вставке.

```sql
ALTER TABLE dbo.Customers
ADD CONSTRAINT DF_Customers_IsActive
DEFAULT (1) FOR IsActive;
```

```sql
INSERT INTO dbo.Customers
(
    CustomerID,
    FullName,
    CreatedAt
)
VALUES
(
    2,
    N'Анна Петрова',
    SYSDATETIME()
);
```

```text
IsActive = 1
```

`DEFAULT` и `NOT NULL` решают разные задачи. Первое подставляет стандартное значение, второе запрещает `NULL`. Явно переданный `NULL` не заменяется значением по умолчанию.

```sql
NULL
```

Типичная комбинация для обязательного поля со стандартным значением:

```sql
IsActive BIT NOT NULL
    CONSTRAINT DF_Customers_IsActive DEFAULT (1)
```

Доменная целостность обычно строится сочетанием типа данных, `NULL`/`NOT NULL`, `CHECK` и `DEFAULT`.

## Сущностная и ссылочная целостность

Сущностная целостность требует однозначно идентифицировать строку. Для основного идентификатора используется `PRIMARY KEY`.

```sql
CREATE TABLE dbo.Customers
(
    CustomerID INT NOT NULL,
    FullName NVARCHAR(150) NOT NULL,

    CONSTRAINT PK_Customers
        PRIMARY KEY (CustomerID)
);
```

Дубликат ключа сохранить нельзя.

```sql
INSERT INTO dbo.Customers
VALUES
(1, N'Иван Петров');

INSERT INTO dbo.Customers
VALUES
(1, N'Анна Соколова');
```

Дополнительные значения, которые тоже должны быть уникальны, защищаются через `UNIQUE`.

```sql
ALTER TABLE dbo.Customers
ADD Email NVARCHAR(200) NULL;
```

```sql
ALTER TABLE dbo.Customers
ADD CONSTRAINT UQ_Customers_Email
UNIQUE (Email);
```

Ссылочная целостность контролируется `FOREIGN KEY`: значение внешнего ключа должно соответствовать существующей строке родительской таблицы.

```sql
CREATE TABLE dbo.Orders
(
    OrderID INT NOT NULL,
    CustomerID INT NOT NULL,
    OrderDate DATETIME2 NOT NULL,

    CONSTRAINT PK_Orders
        PRIMARY KEY (OrderID),

    CONSTRAINT FK_Orders_Customers
        FOREIGN KEY (CustomerID)
        REFERENCES dbo.Customers(CustomerID)
);
```

Ссылка на отсутствующего клиента будет отклонена.

```sql
INSERT INTO dbo.Orders
(
    OrderID,
    CustomerID,
    OrderDate
)
VALUES
(
    100,
    500,
    SYSDATETIME()
);
```

По умолчанию нельзя удалить родительскую строку, если на неё продолжают ссылаться дочерние записи.

```sql
DELETE FROM dbo.Customers
WHERE CustomerID = 1;
```

Каскадные действия меняют это поведение. `ON DELETE CASCADE` автоматически удаляет связанные строки, поэтому его применение должно быть осознанным: в крупной системе одна операция может затронуть большой объём данных.

```sql
CONSTRAINT FK_Orders_Customers
FOREIGN KEY (CustomerID)
REFERENCES dbo.Customers(CustomerID)
ON DELETE CASCADE
```

Для изменения ключа существует аналогичный механизм.

```sql
ON UPDATE CASCADE
```

Первичные идентификаторы обычно проектируют стабильными, поэтому каскадное обновление используется значительно реже.

Существующие ограничения можно анализировать через системный каталог.

```sql
SELECT
    name,
    definition
FROM sys.check_constraints;
```

```sql
SELECT
    name,
    OBJECT_NAME(parent_object_id) AS ChildTable,
    OBJECT_NAME(referenced_object_id) AS ParentTable
FROM sys.foreign_keys;
```

```sql
SELECT
    name,
    type_desc
FROM sys.key_constraints;
```

Добавление ограничения в таблицу с уже накопленными данными требует проверки существующих строк. Если они нарушают новое правило, сначала необходимо исправить данные.

```sql
CREATE TABLE dbo.Payments
(
    PaymentID INT,
    Amount DECIMAL(12,2)
);
```

```sql
INSERT INTO dbo.Payments
VALUES
(1, -1000);
```

```sql
ALTER TABLE dbo.Payments
ADD CONSTRAINT CK_Payments_Amount
CHECK (Amount >= 0);
```

На больших таблицах такая проверка может быть ресурсоёмкой. Поэтому критичные ограничения лучше закладывать при проектировании схемы.

Итоговое распределение ответственности простое: тип данных контролирует формат, `NOT NULL` — обязательность, `DEFAULT` — стандартное значение, `CHECK` — условие, `PRIMARY KEY` — идентичность строки, `UNIQUE` — дополнительную уникальность, `FOREIGN KEY` — корректность связей.

# Модуль 5. Введение в индексирование

## Принципы работы индексов

Индекс — отдельная структура доступа к данным. Он может уменьшить объём чтения, но не гарантирует ускорение сам по себе. Эффект зависит от того, совпадает ли структура индекса с реальными условиями `WHERE`, `JOIN`, `ORDER BY` и `GROUP BY`.

Избыточные индексы увеличивают размер базы и стоимость `INSERT`, `UPDATE`, `DELETE`. Поэтому индекс оценивают одновременно по пользе для чтения и цене обслуживания.

```sql
CREATE TABLE dbo.Orders
(
    OrderID INT NOT NULL,
    CustomerID INT NOT NULL,
    OrderDate DATETIME2 NOT NULL,
    Status NVARCHAR(20) NOT NULL,
    Amount DECIMAL(12,2) NOT NULL
);
```

```sql
CREATE INDEX IX_Orders_CustomerID
ON dbo.Orders(CustomerID);
```

```sql
SELECT
    OrderID,
    OrderDate,
    Amount
FROM dbo.Orders
WHERE CustomerID = 125;
```

Наличие индекса не означает его обязательное использование: план выбирает оптимизатор на основе статистики и стоимости альтернатив.

```sql
SELECT
    i.name,
    i.type_desc,
    i.is_unique
FROM sys.indexes AS i
WHERE i.object_id = OBJECT_ID('dbo.Orders');
```

Список индексов сам по себе не показывает их полезность. Для оценки нужна реальная рабочая нагрузка.

## Типы данных и индексы

Размер ключевых столбцов влияет на размер индекса. Узкие типы обычно требуют меньше страниц, а широкие строковые поля увеличивают объём хранения и чтения.

```sql
INT
```

```sql
NVARCHAR(200)
```

Особенно важен размер идентификаторов, потому что ключевые значения могут повторяться в нескольких индексных структурах.

```sql
SELECT
    c.name AS ColumnName,
    t.name AS DataType,
    c.max_length
FROM sys.columns AS c
JOIN sys.types AS t
    ON c.user_type_id = t.user_type_id
WHERE c.object_id = OBJECT_ID('dbo.Orders');
```

Сравниваемые и связанные столбцы желательно определять одинаковыми типами. Несовпадения могут вызвать неявные преобразования и ухудшить использование индекса.

```sql
VARCHAR
```

```sql
NVARCHAR
```

Практический пример: если `CustomerID` в родительской таблице имеет тип `INT`, внешний ключ того же назначения обычно тоже должен быть `INT`.

## Куча, кластеризованные и некластеризованные индексы

Таблица без кластеризованного индекса хранится как `heap`. Куча допустима для отдельных загрузочных, промежуточных и временных сценариев, но для активно читаемой рабочей таблицы это должно быть осознанным решением.

```sql
CREATE TABLE dbo.Logs
(
    LogID BIGINT,
    CreatedAt DATETIME2,
    Message NVARCHAR(500)
);
```

```sql
SELECT
    i.name,
    i.type_desc
FROM sys.indexes AS i
WHERE i.object_id = OBJECT_ID('dbo.Logs');
```

```text
HEAP
```

Кластеризованный индекс задаёт основную организацию строк таблицы. Он может быть только один.

```sql
CREATE CLUSTERED INDEX CX_Orders_OrderID
ON dbo.Orders(OrderID);
```

Такой индекс часто полезен для диапазонного и последовательного доступа.

```sql
SELECT *
FROM dbo.Orders
WHERE OrderID BETWEEN 100000 AND 110000;
```

```sql
SELECT *
FROM dbo.Orders
WHERE OrderDate >= '2026-09-01'
  AND OrderDate < '2026-10-01';
```

Ключ кластеризованного индекса желательно делать относительно компактным и стабильным. Широкие, часто изменяемые или случайно распределённые ключи увеличивают затраты.

Некластеризованный индекс хранится отдельно от основной структуры и содержит ключ доступа плюс способ найти исходную строку.

```sql
CREATE INDEX IX_Orders_Status
ON dbo.Orders(Status);
```

```sql
SELECT *
FROM dbo.Orders
WHERE Status = N'Paid';
```

Некластеризованных индексов может быть несколько, но индекс на каждый столбец почти всегда означает лишнюю стоимость записи и обслуживания.

## Простые и составные индексы

Простой индекс содержит один ключевой столбец.

```sql
CREATE INDEX IX_Orders_OrderDate
ON dbo.Orders(OrderDate);
```

Составной индекс содержит несколько ключей, и их порядок влияет на доступность индекса для разных запросов.

```sql
CREATE INDEX IX_Orders_Customer_Date
ON dbo.Orders
(
    CustomerID,
    OrderDate
);
```

```sql
SELECT *
FROM dbo.Orders
WHERE CustomerID = 100
  AND OrderDate >= '2026-01-01';
```

```sql
SELECT *
FROM dbo.Orders
WHERE CustomerID = 100;
```

Если запрос использует только второй ключ составного индекса, эффективность может резко снизиться.

```sql
SELECT *
FROM dbo.Orders
WHERE OrderDate >= '2026-01-01';
```

Это связано с принципом левого префикса: первые столбцы ключа определяют, какие варианты поиска индекс поддерживает лучше.

```sql
(CustomerID, OrderDate)
```

```sql
(OrderDate, CustomerID)
```

Поэтому эти варианты нельзя считать взаимозаменяемыми. Порядок выбирается по запросам, а не по расположению столбцов в таблице.

```sql
SELECT
    i.name AS IndexName,
    c.name AS ColumnName,
    ic.key_ordinal
FROM sys.indexes AS i
JOIN sys.index_columns AS ic
    ON i.object_id = ic.object_id
    AND i.index_id = ic.index_id
JOIN sys.columns AS c
    ON ic.object_id = c.object_id
    AND ic.column_id = c.column_id
WHERE i.object_id = OBJECT_ID('dbo.Orders')
ORDER BY
    i.name,
    ic.key_ordinal;
```

Индексирование всегда рассматривается в контексте нагрузки: фильтрации, соединений, сортировки, объёма данных, селективности и частоты изменений.

# Модуль 6. Разработка эффективных индексов

## Стратегия разработки индексов

Эффективный индекс проектируется под конкретную нагрузку, а не под таблицу «вообще». Сначала анализируются часто выполняемые запросы: условия фильтрации, соединения, сортировка, возвращаемые столбцы и частота выполнения.

```sql
SELECT
    OrderID,
    OrderDate,
    Status,
    Amount
FROM dbo.Orders
WHERE CustomerID = 150
  AND OrderDate >= '2026-01-01'
ORDER BY OrderDate DESC;
```

Для такого запроса ключ индекса может повторять основные условия поиска и сортировки, а столбцы, нужные только в результате, можно вынести в `INCLUDE`.

```sql
CREATE INDEX IX_Orders_CustomerID_OrderDate
ON dbo.Orders
(
    CustomerID,
    OrderDate DESC
)
INCLUDE
(
    OrderID,
    Status,
    Amount
);
```

`INCLUDE` помогает покрыть запрос без расширения ключевой части. Покрывающий индекс полезен только относительно конкретного запроса; слишком широкий индекс занимает больше места и дороже обновляется.

Селективность показывает, насколько сильно условие сокращает набор строк. Низкоселективный столбец с несколькими часто встречающимися значениями не всегда выгоден как самостоятельный индекс.

```text
New
Paid
Shipped
Cancelled
```

Для высокоселективного значения ситуация обратная:

```sql
WHERE OrderID = 81725122
```

Порядок столбцов составного индекса зависит от формы предикатов. Для сочетания точного условия и диапазона часто логично сначала разместить столбец равенства.

```sql
WHERE CustomerID = 150
  AND OrderDate >= '2026-01-01'
```

```sql
(CustomerID, OrderDate)
```

```sql
(OrderDate, CustomerID)
```

Это не универсальное правило «самый селективный — первым». Учитываются все запросы, диапазоны, сортировка и возможность использовать левую часть ключа.

Фильтрованный индекс хранит только строки, удовлетворяющие условию, и полезен для небольшого активно используемого подмножества.

```sql
SELECT
    OrderID,
    CustomerID,
    OrderDate
FROM dbo.Orders
WHERE Status = N'New';
```

```sql
CREATE INDEX IX_Orders_New
ON dbo.Orders(OrderDate)
INCLUDE
(
    OrderID,
    CustomerID
)
WHERE Status = N'New';
```

Для OLTP особенно важен баланс: каждый дополнительный индекс повышает стоимость изменений. Эффект от оптимизации лучше измерять, а не оценивать по ощущениям.

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT
    OrderID,
    OrderDate,
    Status,
    Amount
FROM dbo.Orders
WHERE CustomerID = 150
  AND OrderDate >= '2026-01-01';

SET STATISTICS IO OFF;
SET STATISTICS TIME OFF;
```

`STATISTICS IO` показывает логические чтения, `STATISTICS TIME` — процессорное и общее время. Сравнивать следует одинаковый запрос до и после изменения.

## Управление индексами

После создания важно проверить, используется ли индекс и сколько операций записи он обслуживает.

```sql
SELECT
    OBJECT_SCHEMA_NAME(i.object_id) AS SchemaName,
    OBJECT_NAME(i.object_id) AS TableName,
    i.name AS IndexName,
    us.user_seeks,
    us.user_scans,
    us.user_lookups,
    us.user_updates
FROM sys.indexes AS i
LEFT JOIN sys.dm_db_index_usage_stats AS us
    ON us.object_id = i.object_id
    AND us.index_id = i.index_id
    AND us.database_id = DB_ID()
WHERE i.object_id > 100
ORDER BY us.user_updates DESC;
```

Большое число `user_updates` при почти полном отсутствии чтений — повод для анализа, но не автоматического удаления. Счётчики DMV сбрасываются после некоторых событий, включая перезапуск Database Engine, поэтому период наблюдения имеет значение.

Физическое состояние rowstore-индексов оценивается вместе с размером объекта и плотностью страниц.

```sql
SELECT
    OBJECT_NAME(ps.object_id) AS TableName,
    i.name AS IndexName,
    ps.page_count,
    ps.avg_fragmentation_in_percent,
    ps.avg_page_space_used_in_percent
FROM sys.dm_db_index_physical_stats
(
    DB_ID(),
    NULL,
    NULL,
    NULL,
    'SAMPLED'
) AS ps
JOIN sys.indexes AS i
    ON ps.object_id = i.object_id
    AND ps.index_id = i.index_id
WHERE ps.index_id > 0
ORDER BY ps.page_count DESC;
```

Высокая фрагментация маленького индекса сама по себе не требует обслуживания. Влияние фрагментации сильнее проявляется при крупных последовательных и диапазонных чтениях.

Основные операции обслуживания:

```sql
ALTER INDEX IX_Orders_CustomerID_OrderDate
ON dbo.Orders
REORGANIZE;
```

```sql
ALTER INDEX IX_Orders_CustomerID_OrderDate
ON dbo.Orders
REBUILD;
```

`REORGANIZE` легче и работает с листовым уровнем; `REBUILD` перестраивает индекс и значительно тяжелее. Массовый `REBUILD` всех индексов по расписанию может создать лишний I/O, нагрузку на CPU и журнал транзакций.

`FILLFACTOR` уменьшает заполнение страниц при перестроении и может снизить число page split в подходящей нагрузке.

```sql
ALTER INDEX IX_Orders_CustomerID_OrderDate
ON dbo.Orders
REBUILD
WITH
(
    FILLFACTOR = 90
);
```

Снижать `FILLFACTOR` без измеренной причины невыгодно: меньшее заполнение означает больше страниц, памяти и чтения.

## План выполнения запросов

План выполнения показывает выбранный оптимизатором способ доступа к данным. SQL описывает требуемый результат, а не пошаговый алгоритм его получения.

```sql
SELECT
    OrderID,
    Amount
FROM dbo.Orders
WHERE CustomerID = 150;
```

Предполагаемый план строится без выполнения запроса; фактический дополняется runtime-данными. В DBeaver фактический план можно получить через XML.

```sql
SET STATISTICS XML ON;

SELECT
    OrderID,
    OrderDate,
    Amount
FROM dbo.Orders
WHERE CustomerID = 150;

SET STATISTICS XML OFF;
```

Предполагаемый XML-план:

```sql
SET SHOWPLAN_XML ON;
```

`Index Seek` не всегда означает хороший план, а `Index Scan` — плохой. Важнее объём обработанных данных и точность оценок оптимизатора.

```text
Estimated Number of Rows: 100
Actual Number of Rows: 5 000 000
```

Большая разница между `Estimated` и `Actual Rows` указывает на ошибку оценки кардинальности и может объяснять неудачный выбор дальнейших операторов.

`Key Lookup` возникает, когда некластеризованный индекс находит строки, но не содержит всех данных для результата.

```sql
CREATE INDEX IX_Orders_CustomerID
ON dbo.Orders(CustomerID);
```

```sql
SELECT
    OrderID,
    CustomerID,
    OrderDate,
    Status,
    Amount
FROM dbo.Orders
WHERE CustomerID = 150;
```

При небольшом числе строк lookup дёшев. При миллионах строк он может стать основной стоимостью. Один из вариантов — покрывающий индекс.

```sql
CREATE INDEX IX_Orders_CustomerID_Covering
ON dbo.Orders(CustomerID)
INCLUDE
(
    OrderDate,
    Status,
    Amount
);
```

Создавать покрытие только из-за самого факта `Key Lookup` не нужно: сначала оценивается число выполнений и стоимость.

Операторы соединения (`Nested Loops`, `Hash Match`, `Merge Join`) также выбираются по объёму, порядку и доступным индексам. `Sort`, spill в `tempdb` и расхождение оценок рассматриваются как сигналы для дальнейшего анализа.

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
```

План показывает способ выполнения, `STATISTICS IO` — объём чтения, `STATISTICS TIME` — временную и CPU-стоимость. Их нужно анализировать вместе.

## Советник по оптимизации СУБД

Database Engine Tuning Advisor (DTA) формирует рекомендации по физической структуре на основе переданной рабочей нагрузки. Это источник гипотез, а не автоматическая замена проектирования.

Нерепрезентативный workload может привести к индексам, выгодным одному запросу и дорогим для всей системы.

```sql
SELECT ...
FROM ...
WHERE ...
```

Для анализа SQL-файла можно использовать утилиту `dta`.

```text
dta -E -D TrainingDB -if workload.sql -s TrainingSession
```

Каждую рекомендацию нужно сопоставлять с уже существующими индексами, объёмом записи и стоимостью обслуживания. Почти одинаковые индексы часто лучше объединить, чем хранить параллельно.

```sql
(CustomerID, OrderDate)
INCLUDE (Amount)
```

```sql
(CustomerID, OrderDate)
INCLUDE (Amount, Status)
```

Особенно осторожно рекомендации применяются на таблицах с высокой интенсивностью записи.

## Хранилище запросов

Query Store хранит историю запросов, планов и runtime-статистики. Это позволяет исследовать регрессии, которые нельзя надёжно восстановить только по текущему plan cache.

Для новых пользовательских баз SQL Server 2022 и новее Query Store обычно включён по умолчанию, но фактическое состояние следует проверять.

```sql
SELECT
    actual_state_desc,
    desired_state_desc,
    current_storage_size_mb,
    max_storage_size_mb,
    query_capture_mode_desc
FROM sys.database_query_store_options;
```

При необходимости его можно включить явно.

```sql
ALTER DATABASE TrainingDB
SET QUERY_STORE = ON
(
    OPERATION_MODE = READ_WRITE
);
```

После накопления данных доступна история выполнения и потребления ресурсов.

```sql
SELECT TOP (20)
    qt.query_sql_text,
    q.query_id,
    p.plan_id,
    rs.last_execution_time,
    rs.count_executions,
    rs.avg_duration,
    rs.avg_cpu_time,
    rs.avg_logical_io_reads
FROM sys.query_store_query_text AS qt
JOIN sys.query_store_query AS q
    ON qt.query_text_id = q.query_text_id
JOIN sys.query_store_plan AS p
    ON q.query_id = p.query_id
JOIN sys.query_store_runtime_stats AS rs
    ON p.plan_id = rs.plan_id
ORDER BY rs.last_execution_time DESC;
```

Приоритет оптимизации определяется не только длительностью одного запуска, но и суммарной нагрузкой. Частый короткий запрос способен потреблять больше ресурсов, чем редкий длинный.

```text
10 000 раз в минуту × 5 мс
```

```text
1 раз в сутки × 10 секунд
```

Несколько `plan_id` для одного `query_id` позволяют сравнить, как менялся план одного запроса во времени.

```sql
SELECT
    q.query_id,
    qt.query_sql_text,
    p.plan_id,
    p.last_compile_start_time,
    p.avg_compile_duration
FROM sys.query_store_query AS q
JOIN sys.query_store_query_text AS qt
    ON q.query_text_id = qt.query_text_id
JOIN sys.query_store_plan AS p
    ON q.query_id = p.query_id
ORDER BY
    q.query_id,
    p.plan_id;
```

Если новый план совпадает с ростом длительности, CPU или чтений, можно исследовать регрессию. Query Store позволяет временно зафиксировать известный хороший план.

```sql
EXEC sys.sp_query_store_force_plan
    @query_id = 15,
    @plan_id = 32;
```

Отмена фиксации:

```sql
EXEC sys.sp_query_store_unforce_plan
    @query_id = 15,
    @plan_id = 32;
```

Plan forcing удобен как средство стабилизации, но причина регрессии всё равно требует анализа: статистика, распределение данных, изменения схемы, новые индексы, параметры или форма запроса.

Query Store также умеет собирать статистику ожиданий.

```sql
ALTER DATABASE TrainingDB
SET QUERY_STORE = ON
(
    WAIT_STATS_CAPTURE_MODE = ON
);
```

Для производственной оптимизации Query Store позволяет связать частоту запросов, их планы, чтение, CPU и изменение поведения во времени. Решение об индексе должно опираться на измеренную нагрузку, а не на предположение.

# Модуль 7. Колоночные индексы

## Введение в колоночные индексы

Rowstore оптимален для типичной OLTP-нагрузки с точечным доступом и частыми небольшими изменениями. Columnstore ориентирован на аналитику по большим наборам, когда обрабатывается много строк, но требуется ограниченное число столбцов.

```sql
dbo.SalesFact
```

```text
SaleID
SaleDate
ProductID
CustomerID
StoreID
Quantity
Price
Discount
Amount
```

Типичный аналитический запрос:

```sql
SELECT
    ProductID,
    SUM(Amount) AS TotalAmount
FROM dbo.SalesFact
WHERE SaleDate >= '2026-01-01'
GROUP BY ProductID;
```

В columnstore значения хранятся по столбцам и сжимаются. SQL Server может читать только нужные столбцы, обрабатывать данные пакетами и пропускать неподходящие сегменты.

Данные организованы в `rowgroup`; внутри них для каждого столбца формируется отдельный сегмент. Метаданные сегментов позволяют выполнять segment elimination.

```sql
WHERE SaleDate >= '2026-09-01'
  AND SaleDate < '2026-10-01'
```

Если диапазон сегмента не пересекается с условием запроса, его можно не читать. Поэтому columnstore — не просто ещё один B-tree индекс, а другой формат хранения и обработки.

## Создание колоночных индексов

Основные варианты — clustered columnstore и nonclustered columnstore. В clustered columnstore колоночный формат становится основным способом хранения таблицы.

```sql
CREATE TABLE dbo.SalesFact
(
    SaleID BIGINT NOT NULL,
    SaleDate DATE NOT NULL,
    ProductID INT NOT NULL,
    CustomerID INT NOT NULL,
    Quantity INT NOT NULL,
    Amount DECIMAL(14,2) NOT NULL
);
```

```sql
CREATE CLUSTERED COLUMNSTORE INDEX CCI_SalesFact
ON dbo.SalesFact;
```

Такой вариант подходит большим таблицам фактов с агрегациями, группировками и массовым чтением.

```sql
SELECT
    name,
    type_desc
FROM sys.indexes
WHERE object_id = OBJECT_ID('dbo.SalesFact');
```

```text
CLUSTERED COLUMNSTORE
```

Nonclustered columnstore добавляет аналитическую структуру поверх rowstore-таблицы.

```sql
CREATE NONCLUSTERED COLUMNSTORE INDEX NCCI_Orders_Analytics
ON dbo.Orders
(
    OrderDate,
    CustomerID,
    Status,
    Amount
);
```

Операционные запросы при этом могут продолжать использовать rowstore:

```sql
SELECT *
FROM dbo.Orders
WHERE OrderID = 150025;
```

а аналитические — columnstore:

```sql
SELECT
    Status,
    COUNT(*) AS OrderCount,
    SUM(Amount) AS TotalAmount
FROM dbo.Orders
WHERE OrderDate >= '2026-01-01'
GROUP BY Status;
```

Такой подход используется для operational analytics, когда аналитика выполняется по оперативным данным без полного переноса в отдельное хранилище.

В SQL Server 2025 поддерживаются упорядоченные clustered и nonclustered columnstore-индексы. Упорядочивание по часто фильтруемому столбцу может улучшить segment elimination.

```sql
CREATE CLUSTERED COLUMNSTORE INDEX CCI_SalesFact
ON dbo.SalesFact
ORDER (SaleDate);
```

Цена — дополнительные затраты на сортировку при построении и загрузке. `ORDER` должен соответствовать реальной нагрузке.

## Эксплуатация колоночных индексов

Для columnstore основным объектом диагностики является `rowgroup`, а не классическая фрагментация B-tree.

```sql
SELECT
    OBJECT_NAME(object_id) AS TableName,
    index_id,
    row_group_id,
    state_desc,
    total_rows,
    deleted_rows,
    size_in_bytes
FROM sys.dm_db_column_store_row_group_physical_stats
WHERE object_id = OBJECT_ID('dbo.SalesFact')
ORDER BY row_group_id;
```

Рабочие данные обычно должны находиться в сжатых группах.

```text
COMPRESSED
```

Новые строки могут временно находиться в `delta store`. Фоновый `tuple mover` переводит накопленные данные в сжатые rowgroup. Сам факт наличия открытого delta store не является ошибкой.

Удалённые строки могут оставаться логически помеченными до последующего обслуживания. Состояние оценивают по числу групп, их заполнению и количеству удалённых строк.

Для обслуживания доступны `REORGANIZE` и `REBUILD`.

```sql
ALTER INDEX CCI_SalesFact
ON dbo.SalesFact
REORGANIZE;
```

```sql
ALTER INDEX CCI_SalesFact
ON dbo.SalesFact
REBUILD;
```

`REBUILD` заново формирует rowgroup и является тяжёлой операцией. Выполнять его без диагностики не следует; часть слияния небольших групп современные версии SQL Server выполняют автоматически.

Для columnstore важен характер загрузки. Большие пакетные загрузки обычно формируют более качественные rowgroup, чем постоянный поток очень маленьких пакетов.

Эффект проверяется по фактическому плану и измерениям ввода-вывода.

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT
    ProductID,
    SUM(Amount) AS TotalAmount
FROM dbo.SalesFact
WHERE SaleDate >= '2026-01-01'
  AND SaleDate < '2027-01-01'
GROUP BY ProductID;

SET STATISTICS IO OFF;
SET STATISTICS TIME OFF;
```

На небольших таблицах преимущества columnstore могут быть незаметны. Выбор определяется не размером таблицы сам по себе, а характером запросов: точечная OLTP-нагрузка обычно остаётся на rowstore, массовые агрегации по большим наборам делают columnstore сильным кандидатом, а смешанный сценарий может использовать nonclustered columnstore.
